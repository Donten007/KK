# 排期压缩决策支持材料

> **目的**：把「砍哪些模块」从抽象争论变成可勾选的决策，供总监直接拿给用户选。
> **状态**：待用户决策。**这是解锁 Phase 1.5 Spec 锁定的唯一阻塞项。**
> **作者**：产品经理许清楚|日期：2026-10-15

---

## 一、决策背景

架构评估完整实现 26 个功能模块 = **28-38 人月（团队 4-6 人= 6-9 个月）**。

Phase 0 曾初判 18 周，架构核算后已修正——**漏算了「多租户 + 安全 + 可观测」对每个功能的乘法效应**。26 个模块不是「实现 26 个功能」，而是「实现 26 个功能 × 多租户 × 安全 × 可观测」。

总监已定压缩原则：**砍功能模块数，不砍治理层和安全**。本文件解决「具体砍哪些」。

---

## 二、我的核心建议：不砍 F6长任务引擎

我曾建议「若18 周硬约束则砍 F6」，**现撤回该建议**。

| 理由 | 说明 |
|---|---|
| 代价被我高估了 | 架构重估后，F6-lite 仅需 **1.5-2.5 人月**，是 28-38 人月中性价比最高的一块（**注：架构师后续发现其S1 设计有缺陷并修正，范围从「仅 S1」扩为「S1a + S2 双信号」，故区间上浮至 2.5，人月总量结论不变**） |
| 它是对撞竞品差评的核心 | Manus 最集中的两类差评是「半成品交付」和「死循环烧额度」，F6 的断点续跑 + 熔断正好挡这两类 |
| 砍它= 产品退化 | 没有断点续跑和熔断，产品就退化成 Manus，会完整重复它的全部差评 |

**结论**：若排期必须压缩，砍 F6 是**代价最高、收益最小**的选择之一。请从下方 A 组中砍。

**架构师补充论证（我认同并采纳）**：砍掉 F6 后**产品可能连 No-Go 都过不了**，这不是「换个功能做」，而是「Go/No-Go 判据本身失效」：
- **断点续跑是 F6 的不可分割部分**，砍掉就没有「40 步崩了从第 26 步续」，而这是正面对撞 Manus 差评的唯一能力
- PRD §8.4 已写明 TCR ≥ 85% 是生死线，**没有断点续跑，长任务失败率必然高，TCR 达不到 85%**

**若必须压缩，架构师原建议「先砍 F8 或减少岗位数量」。PM 反驳后，架构师已撤回原排序并采纳 PM 的版本。**

**PM 的反驳**：F8 是「老板每天早上收到汇报」这个通道，而**老板汇报打开率是最重要的留存指标**。砍掉 F8 后老板必须主动打开网页，**直接影响判据 6「7 日留存 ≥40%」与激活定义**（激活含 `first_report_viewed` + `daily_report_clicked`，推送是这些事件的触发器）。砍岗位数量只减少验证覆盖面（5→3），不影响任何判据。

**架构师复核确认 PM 是对的**，且我的原排序错在：只看了「F8 是渠道不是能力」，**忽略了渠道决定了判据 6 的事件能否发生**。这是工程视角与产品视角的差异，取舍排序不应由架构单方决定。

**修正后的排序（依据「砍掉会让哪条判据失效」，非「哪项实现便宜」）**：

```
1. 岗位数量（5 → 3）    代价：覆盖面        不影响任何判据
2. F8（企微推送）       代价：判据 6 + 激活定义
3. F6（最后才考虑）     代价：TCR 判据本身失效
```

> 架构师注：取舍排序请与 PM 共同定。架构侧评估「实现成本与判据影响」时容易漏掉「事件触发器」这一层——本轮即为例证。详见 ADR-018 §一。

## 三、砍模块候选清单（按「砍掉的产品后果」排序）

> 每一项都标注了**砍掉后会发生什么**，供判断代价。A 组为我的推荐顺序。

### A 组：砍掉不影响「雇 AI 员工」闭环（推荐优先砍）

| # | 候选 | 砍掉的产品后果 | 我的判断 |
|---|---|---|---|
| A1 | **多 Agent 协作 / Crew 编排** | 无法让多个 AI 员工协同完成一个复杂目标 | **推荐砍**。我们刻意走「窄而准」路线（差异化 2），多 Agent 是通用 Agent 路线。MVP 的 5 个岗位都是单员工可完成的任务 |
| A2 | **子 Agent 并发委派** | 一个任务内无法并行拆给多个子 Agent | **推荐砍**。架构已确认深度硬限 3 层且第 3 层须人工确认，说明这个能力本身收益有限、成本很高 |
| A3 | **L2 无头浏览器渲染 / L3 登录态操作** | 竞品监控无法抓 JS 重渲染的 SPA；无登录态操作能力 | **推荐砍**。架构 ADR-014 已论证 L1 抓取够用。**但注意：砍这条会影响竞品监控岗位的适用范围（见下方风险）** |
| A4 | **语音 / 电话 / 数字人** | 无电话客服能力 | **推荐砍**。硅基智能的主战场，依赖硬件与线路成本，与我们的自助 SaaS 形态不匹配 |
| A5 | **图片 / 视频生成** | 员工不能生成图片视频 | **推荐砍**。与「雇员工干活」无关，是范围蔓延第一大来源 |
| A6 | **代码生成 / 网页搭建** | 员工不能写代码、不���搭网站 | **推荐砍**。Manus 的 web-app 卖点，评测明确指出交付物「像 2005 年做的」且不可维护 |
| A7 | **可视化流程画布** | 用户无法拖拉编排 | **推荐砍**。一旦做成画布，产品就退化成 Dify/Coze，且老板不会用——我们的差异化正是「不做画布」 |

### B 组：砍掉会削弱差异化，但不至于产品不可用

| # | 候选 | 砍掉的产品后果 | 风险提示 |
|---|---|---|---|
| B1 | **通用浏览器代理（操作任意网站）** | 同A3 | 我们本来就不做（Out-of-Scope 已列） |
| B2 | **模型自建 / 训练** | 无 | 本来就不做（BYOK 是既定决策） |
| B3 | **AI 员工自我训练 / 优化闭环** | 员工不会从历史任务中自动改进 | **谨慎**：这会影响长期价值主张。但 MVP 阶段可砍，v2 再补 |
| B4 | **插件 / 技能市场** | 第三方无法扩展能力 | 本来就不做（Out-of-Scope 已列） |

### C 组：不建议砍（砍了会直接击穿商业模式）

| # | 候选 | 为什么不能砍 |
|---|---|---|
| C1 | **治理层（SSO / 审计日志 / 可观测性）** | **定价支撑不是成本项**。CrewAI 靠 SOC2 + FedRAMP + 审计日志卖 $60,000/年起；Dify 因付费支持不响应被 G2 批评。砍掉它，¥899/月 的定价锚点撑不住——客户买的是「敢把业务放上去」，不是「能跑起来」 |
| C2 | **安全（RLS 隔离 / 密钥分离 / 租户数据隔离）** | **一票否决**。多租户 SaaS 出现跨租户泄露 = 产品立即不可用。这是合规底线也是销售信任底线 |
| C3 | **F6-lite 断点续跑 + 熔断** | 见上方第二节 |
| C4 | **预算闸门 / 成本透明** | **Top1 差异化卖点**。没有它产品就退化成 Manus 的「烧钱机器」，竞品差评最集中的抱怨（成本不可预期）会直接砸掉我们 |
| C5 | **每日汇报** | **留存命脉**。没有它老板不知道员工干得怎么样，7 日留存判据 ≥40% 无法达成 |

## 四、推荐的压缩方案（供直接选择）

### 方案 A：砍 A 组全部（推荐）

**砍**：多 Agent 编排、子 Agent 并发、L2/L3 网页访问、语音数字人、图片视频生成、代码生成、可视化画布

**保留**：6 项 P0 功能 + 治理层 + 安全 + F6-lite

**预期效果**：保留完整「雇 AI 员工」闭环，产品定位不变，差异化卖点全部保留

**风险**：竞品监控岗位对 JS 重渲染站点无效（但企业官网/新闻/博客主体内容是服务端渲染 HTML，L1够用）

### 方案 B：砍 A 组 + B3

在方案 A 基础上，额外砍掉「AI 员工自我训练闭环」

**额外风险**：员工不会从历史任务自动改进，长期价值主张需在 v2 补齐

### 方案 C：极限压缩（需重新评估产品定位）

只保留 6 项 P0 功能 + 治理层 + 安全，其余全砍

**必须诚实的后果**：产品将从「AI 员工平台」缩小为「单岗位 AI 员工工具」，差异化卖点 1/2/3 全部保留但无法组合成完整闭环。**我不推荐这个方案**，因为它会让销售话术难以自洽。

## 六、我的补充建议

**如果用户坚持 18 周**，我建议采用方案 A，并同时明确：

1. **对外销售话术不得承诺被砍功能**（如不能说「支持多员工协作」）
2. **岗位上线顺序按难度递进**（已在 PRD §8.2），让前 4 个低难度岗位先上线建立信心
3. **F6-lite 必须保**——1.5-2 人月的投入换来对撞 Manus 核心差评的能力，这是整个压缩方案里性价比最高的一块
