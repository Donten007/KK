# 埋点守门方案（Phase 2 实施规范）

> **定位**：TRACKING-WHITELIST.md 的**服务端实现规范**。白名单定义「记什么」，本方案定义「怎么守住它」。
> **优先级**：P0（Phase 2 与后端脚手架同期落地）
> **契约对齐**：openapi.yaml 的 `/api/v1/analytics/events` 已含 `accepted` / `dropped` 计数字段（架构侧已实现）

---

## 一、为什么需要守门（而不是只靠前端自觉）

**前端不采集不够。** 前端不采集，只能保证「我们自己的代码不传」；**任何人加一行 `trackEvent('x', {任意字段})` 就能绕过隐私承诺**，而这不违反任何前端 lint 规则。

**守门的本质是把隐私承诺从「人记得」变成「结构上不可能违反」。**

---

## 二、四道防线（按请求流向）

```
客户端 POST /api/v1/analytics/events
  │
  ├─[防线1] Schema 层：事件名必须在白名单枚举内
  │
  ├─[防线2] 属性层：属性名必须在该事件的属性白名单内
  │
  ├─[防线3] 黑名单写入前过滤：命中即整条丢弃（不是清洗值）
  │
  ├─[防线4] 租户归属：无租户上下文的事件拒绝入库
  │
  └─> analytics_events 表（RLS 隔离，180 天保留）
```

### 防线 1：事件名白名单

| 项 | 内容 |
|---|---|
| 位置 | **API 入口（FastAPI Pydantic schema）**，不是 service 层 |
| 机制 | 请求体的 `event` 字段定义为 `Literal` 联合类型，**枚举 TRACKING-WHITELIST.md 第二节的 33 个事件名** |
| 拒绝行为 | 不在枚举内 → **整条拒绝**（不是「接受但不入库」），计入 `dropped` |
| 为什么在 schema 层 | 在 service 层做等于「已经进到业务代码里了」，而 schema 层拒绝意味着**非法事件根本进不了系统** |

**实现要点**：事件名清单必须是**单一数据源**。建议在代码中维护 `ALLOWED_EVENTS: Final = frozenset({...})`，与 TRACKING-WHITELIST.md 由 CI 校验一致（见 §五），**禁止在两处各写一份**。

### 防线 2：属性白名单

| 项 | 内容 |
|---|---|
| 位置 | schema 层，与事件名同层 |
| 机制 | **每个事件定义独立的属性模型**（不是统一的 `dict[str, Any]`）。例：`task_completed` 只接受 `job_template_id` / `step_count` / `cost_cny` / `duration_sec` |
| 拒绝行为 | 未知属性 → **丢弃该属性**（不是整条丢弃，否则一个多余字段会让整个事件丢失） |
| 多余属性是否告警 | **是**，计入 `dropped_attributes`，用于发现「有人想记白名单外的东西」 |

**为什么用每事件独立模型而不是统一 dict**：统一 dict 等于没有防线 2。**独立模型让「这个事件能记什么」成为类型定义，而不是运行时约定。**

### 防线 3：黑名单写入前过滤

| 禁记项 | 判定方式 | 处理 |
|---|---|---|
| **IP 地址** | 不进入埋点链路。**请求层不把 client IP 传入 analytics 上下文** | 源头不传 |
| **User-Agent** | 同上 | 源头不传 |
| **prompt 全文** | 属性名黑名单 + **值长度阈值** | 命中即整条丢弃 |
| **工具返回全文** | 同上 | 命中即整条丢弃 |
| **文档内容** | 同上 | 命中即整条丢弃 |
| **文件名** | 属性名黑名单（`file_name` / `filename` / `document_name` 等变体） | 命中即整条丢弃 |

**关键机制：值长度阈值。** 属性名可以变（`content` / `text` / `payload` / `body`），**但内容类字段的共性是很长**。所以：
- 单个字符串属性值 **> 500 字符 → 整条事件丢弃并计入 `dropped`**
- 理由：**本产品的合法属性（ID、状态码、时长、金额、模板 ID）都不超过 50 字符**。超长值大概率是内容，不是元数据。

**这条是防线 3 的核心**——它防的是「有人加了个叫 `context` 的字段塞进去」，而属性名黑名单防不住这种变体。

### 防线 4：租户归属

| 项 | 内容 |
|---|---|
| 机制 | 埋点请求必须带有效 JWT，`tenant_id` 从 token 解析，**不接受请求体传入** |
| 拒绝行为 | 无租户上下文 → 拒绝入库并**记 WARNING 告警**（不静默） |
| 为什么告警 | 与架构侧「租户上下文缺失记 WARNING 不静默」同一原则——**静默丢弃的埋点会变成另一种失控** |

## 三、表结构与 RLS

### analytics_events 表

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | uuid | 主键 |
| `tenant_id` | uuid | **从 JWT 解析，非请求体** |
| `user_id` | uuid | 租户内 ID，**非个人身份信息** |
| `event` | text | 事件名（白名单内） |
| `properties` | jsonb | 属性（已过滤） |
| `created_at` | timestamptz | |

### RLS 策略

```sql
-- 与其他业务表同一模式（架构侧多租户隔离方案）
ALTER TABLE analytics_events ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON analytics_events
  USING (tenant_id = current_setting('app.tenant_id')::uuid);
```

**`analytics_events` 必须与其他业务表走同一套 RLS**，不能因为是「分析表」就特殊处理——**租户隔离没有例外**。

### 保留期清理

| 项 | 内容 |
|---|---|
| 保留期 | **180 天** |
| 机制 | 定时任务（Hatchet cron）每日清理 `created_at < now() - interval '180 days'` |
| 清理方式 | **物理删除**（不是软删除 `deleted_at`）——埋点数据的生命周期就是 180 天，不存在「逻辑删除」语义 |
| 与风控数据的关系 | 本项目**无设备指纹采集**（删代付后风控需求消失），故不存在 90 天风控数据的独立保留期 |

## 四、可观测性（丢弃量必须可见）

**「静默丢弃」是另一种形式的失控。** 如果埋点一直被丢而没人知道，产品侧会以为有数据、实际没有。

| 计数器 | 含义 | 告警阈值 |
|---|---|---|
| `accepted` | 成功入库数 | — |
| `dropped` | 整条丢弃数（事件名非法 / 黑名单命中 / 无租户上下文） | **单日 > 100 触发告警** |
| `dropped_attributes` | 属性丢弃数 | 单日 > 500 触发告警 |

**这两个计数已在 openapi 的响应 schema 中**（架构侧已实现），产品侧只需在仪表盘上给一个视图：**「本周丢弃 N 条埋点，原因分布」**。

**告警阈值为什么这样定**：正常情况下 `dropped` 应该接近 0（所有埋点都由我们的代码发出，且都经过白名单）。**单日 >100 说明有人在传白名单外的事件**——这是要人去看的信号，不是自动扩容的信号。

## 五、CI 校验（白名单与文档不漂移）

**风险**：代码里的 `ALLOWED_EVENTS` 与 TRACKING-WHITELIST.md 各自演化，半年后不一致，而没人会发现。

**方案**：`scripts/verify-tracking.sh`

```bash
# 1. 从代码提取 ALLOWED_EVENTS 集合
# 2. 从 TRACKING-WHITELIST.md 第二节提取事件名集合
# 3. 双向差集，任一方向有差异即阻断
```

**阻断级别**：P0（与 `verify-openapi.py` 同级）。

**为什么值得做**：白名单文档是给人和 AI 看的，代码是给解释器看的。**两者的不一致不会报错，只会静默地让一边失效。**

## 六、与相邻约束的关系

| 约束 | 关系 |
|---|---|
| **AC-14b owner 接口不序列化 token** | **同源原则**。埋点守门守「不记内容」，AC-14b 守「不返回内容」——都是「承诺必须结构性成立，不靠自觉」 |
| **架构侧埋点事件表 RLS + 180 天** | 本文档 §三 与之对齐，无冲突 |
| **openapi `accepted`/`dropped` 字段** | 本文档 §四 的数据来源，契约已对齐 |

## 七、待架构师确认的两点

1. **防线 1 的 `Literal` 联合类型是否可维护**：33 个事件名的 Literal 会让 schema 文件变长。若架构侧倾向「schema 用 `str` + service 层校验」，**我要求至少在 service 层第一行就校验并拒绝**，不能到写库前才校验。
2. **值长度阈值 500 字符是否与现有属性冲突**：我按「合法属性都不超 50 字符」推的 500。若某个事件的合法属性确实更长（如 `error_type` 带长描述），需调高该事件的阈值——**但必须逐事件显式声明，不能全局放宽**。
