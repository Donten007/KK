## 1. 产品定义

### 1.1 一句话定义

**给中小企业老板一个按时上班、交不出活来自己负责、且花钱有硬上限的 AI 员工。**

展开：老板不需要会写 prompt、不需要懂 API，只需要像挑人一样挑一个岗位、看一次试跑结果、开一个定时开关，之后每天早上收一条汇报。

### 1.2 目标用户

| 层级 | 角色 | 在产品中的权限位置 | 是否付款 |
|------|------|-----------------|---------|
| 主要 | 企业决策者（老板/合伙人/CEO） | `owner` | **是，唯一付款人** |
| 次要 | 管理员（运营负责人/行政/IT 对接人） | `admin` | 否，但**有否决权** |
| 暂不服务 | 普通员工 | P2 的 `viewer` 复核入口 | 否 |

**MVP 只服务 owner + admin 两层。** 普通员工的「一键打回」需求（F12）延后到 Phase 2，理由见 PRD §3.4：过早展示半成品执行流会加剧抵触而非缓解。

### 1.3 核心问题（从 PRD 提取，非复述）

| # | 问题 | 量化证据 | 本产品的回答 |
|---|------|---------|------------|
| P1 | 关键流程挂在 1-2 个人身上，人走业务断 | 30-80 人企业普遍用工结构 | 岗位说明书把流程固化进模板，不依赖某个人的记忆 |
| P2 | 招人成本高且带不走知识 | 月薪 6-8K + 五险一金 ≈ 8-10K/月 | AI 员工 ¥899/月管 3 个编制，人均 ¥300/月（人类成本 15%） |
| P3 | **通用 Agent 任务完成率只有 65%**，35% 异常由客户自己消化 | 行业投资人评分卡 2026 | 用「岗位窄」换「准确率高」，目标 TCR ≥ 85% |
| P4 | **成本事前不可知**，是「不能放进财务流程的费用」 | Manus 官方承认费用预估是幻觉；有用户烧掉 88,000 积分未完成 | 预算闸门是一等公民：80% 预警 / 100% 停止并向人报告 |
| P5 | 长任务半成品交付，重复步骤、丢失进度 | Manus / AgentGPT 差评集中区 | 断点续跑 + 无进展熔断（F6-lite） |

**P3 与 P4 是本产品全部差异化的技术根**。P1/P2 是商业理由，P5 是信任前提。

## 2. MVP 范围（锁定）

### 2.1 范围裁定的三条原则

1. **砍功能模块数，不砍治理层与安全**（总监已定）。治理层是定价支撑不是成本项——CrewAI 靠 SOC2 + 审计日志卖 $60,000/年起；砍掉它，¥899/月 的定价锚点撑不住。
2. **F6 不可砍**。断点续跑是 F6 不可分割的部分。PRD §8.4 自己写了 TCR ≥ 85% 是生死线——没有断点续跑，长任务失败率必然高，**砍 F6 可能连 Go/No-Go 都过不了，这不是「换个功能做」，是判据本身失效**。
3. **每个被砍模块必须标注「销售话术禁用词」**（见第 3.3 节）。产品边界变更不同步销售口径，销售会用旧承诺签单，由交付还账。

### 2.2 P0 功能清单（依赖链顺序）

> **依赖链顺序 ≠ RICE 顺序。** RICE 最高的不等于先做：F6 的 RICE 仅 1.69（最低）却是 P0，因为它的 Effort 最高且 Confidence 最低，但砍它等于承认自己是 Manus。

| 序 | 功能 | RICE | MVP 交付形态 | 核心验收锚点 |
|----|------|------|------------|-------------|
| **F2** | BYOK 模型接入 + 平台代付双通道 | **15.00** | 四厂商（OpenAI/Anthropic/DeepSeek/智谱）密钥加密存储；能力前置校验 fail-closed | AC-7、AC-8、AC-15 |
| **F6** | 长任务引擎 | **1.69** | **F6-lite**：断点续跑 + 中止 + 步骤预估 + S1a/S2 双信号熔断 | AC-4、AC-5、AC-17 |
| **F1** | 岗位模板库 | **8.00** | **4 个岗位**（非 5 个，见 C4 裁决 + L3 依赖分析） | AC-1 |
| **F5** | 知识源上传与基础检索 | **6.00** | 上传 + 摄取可见 + 字段级确认 + 结构化精确过滤 + 向量检索 top-K。**完整 RAG 后置** | AC-1 |
| **F3** | 定时触发 + 预算闸门 | **10.80** | 预设四种类型；未试跑禁止开定时；80% 预警 / 100% 停止 | AC-2、AC-3 |

| **F8** | 企业微信推送 | **11.20** | **简版**：只推汇报文本，不做交互卡片 | AC-2 |

### 2.4 MVP 岗位清单（锁定 5 个）

> **5 个岗位，按「验证 TCR 的难度递进」排序，先做容易成功的。**
>
> **竞品监控日报是 #1**（DECISION-CHANGES 变更一，用户复看裁定推翻 C1 的收窄）。它是最能体现「AI 员工主动干活」的岗位——每天自己去看竞品变化并汇报，是差异化最直观的一个，也是 SMB 老板付费的核心价值感知。

| 序 | 岗位 | 难度 | 依赖能力 | 步骤数 | 验证什么 | TCR 阈值 |
|----|------|------|---------|--------|---------|----------|
| **1** | **竞品监控日报** | 低 | **L1 抓第三方公开网页** + HTML 解析 + 摘要 | 3-8 | 结构化抓取 + 摘要，最容易达到高 TCR，先验证基本链路 | **≥70%**（外部依赖类） |
| **2** | 周报汇总 | 低 | 表格解析 + 文档生成 | 3-6 | 「我们能做好」的信心基线，目标 95%+ | ≥85% |
| **3** | 发票信息核对 | 中 | 文档理解 + 字段抽取 | 8-15 | OCR 与结构化抽取 | ≥85% |
| **4** | 客户跟进催办 | 中 | 表格/CRM 读取 + 话术生成 | 5-12 | **「主动升级给人」机制**（差异化卖点 3 的载体） | ≥85% |
| **5** | 电商订单录入 | **高** | **L3 登录态客户自有系统**（写 ERP） | 20-40 | 最难场景——**放在最后做，因为它是决定项目成败的那个** | ≥85% |

**岗位 5 的特殊处理**：电商订单录入需 L3（登录态写客户 ERP），而 ADR-014 明确 **L3 不做自动登录**——**需登录场景的正式解法是客户自行导出上传，员工做分析**。这不是降级方案，是这个场景下唯一正确的做法（我们因此不承担客户账号密码的保管责任与安全风险）。

该岗位 20-40 步、高外部副作用，是 ADR-011 判定「**需 F6-full 而非 F6-lite**」的唯一岗位。**因此它在 MVP 的交付形态是「导出上传 + 员工核对录入」，而不是「自动登录 ERP 写入」**。Phase 2 补 F6-full 后再评估是否放开自动写入。

**排序的关键判断**：先做「文档 + 表格」类任务（准确率高、失败可恢复），最后做「外部系统操作」类任务（准确率低、失败代价高）。这样 MVP 前 4 个岗位上线时能拿到真实的 TCR 数据，而第 5 个岗位的失败不会拖垮产品口碑。

**岗位 #1 卡片五要素**：

| 卡片要素 | 内容 |
|---------|------|
| 岗位图标 | `Radar`（Lucide，24px） |
| 岗位名 | 竞品监控日报 |
| 一句话职责 | 每天早上 8 点，看完 5 家竞品的价格与动作，把变化写成一份日报 |
| 交付物 | 竞品日报-{日期}.xlsx + 异常波动清单 |
| 上岗前置条件 | **无需配置，今天就能上岗**（低难度档的唯一一个） |

**排序规则**：按**首次成功率降序**（老板第一次点击决定信心），难度靠边框粗细表达，**禁止置灰或降低透明度**（置灰暗示不可用，但这些岗位是真实可用的，只是需先配置）。

**每个岗位模板必须声明四组技术字段**（缺任一组则 F6 与 F2 无法落地）：

```yaml
required_caps: [tool_use, streaming]      # ADR-013 能力需求
optional_caps: [vision]
expected_idle_steps: 5                   # ADR-011 无进展阈值（岗位级，不硬编码）
expected_total_steps: 12                 # ADR-011 步骤数预估
baseline_minutes_per_run: 25             # ADR-015 ROI 折算参数（租户可覆盖）
```

### 2.5 MVP 成功判据（Go/No-Go，锁定）

> **观测窗口 ≥ 2 周，不看首日。** 外部依赖类任务的失败率随时间波动。

| # | 判据 | 阈值 | 口径定义（ADR-015 已消歧） |
|---|------|------|------------------------|
| 1 | TCR | **分组独立判定**：外部依赖类 ≥70%、内部文档/表格类 ≥85% | 分子 = 完成**且全程未经人工介入** |
| 2 | HITL | ≤ 2% | 分子 = `task_escalated_to_human` |
| 3 | Agentic ROI | ≥ 300% | `(节省人力 - 订阅费) ÷ 订阅费`，节省人力用租户可配参数 |
| 4 | 激活转化率 | ≥ 40% | 首个 AI 员工首次跑完 + 老板查看汇报，三个事件缺一不算 |
| 5 | 注册到首次跑完中位时长 | ≤ 15 分钟 | — |
| 6 | 7 日留存 | ≥ 40% | 以「雇了 AI 员工」的用户为分母 |
| 7 | 「成本不可预期」投诉占比 | **0** | **当前无采集路径，必须先改产品流程**：退款原因改结构化枚举 + 该字段客服不可编辑 |

**TCR 按岗位分组独立判定**（DECISION-CHANGES 变更一恢复）：

| 岗位组 | 岗位 | TCR 阈值 | 理由 |
|--------|------|---------|------|
| **外部依赖类** | **竞品监控日报** | **≥70%** | 目标站改版 / 加防护 / 要登录是客观现实，不由我们控制。用 85% 会导致「No-Go 但无法改进」 |
| 内部文档/表格类 | 周报汇总、发票信息核对、客户跟进催办、电商订单录入 | ≥85% | 依赖客户自有数据，结果可控 |

**聚合规则：每组独立判定，任一组不达标即整体 No-Go，不做加权平均。** 加权平均会导致「用一个岗位的成功掩盖另一个的失败」。

**恒等式（必须成立）**：`TCR + HITL + 失败率 = 100%`

**归属规则**（防止重复计算架空 HITL 约束）：

| 事件 | 进 TCR 分子 | 计 HITL | 计失败 |
|------|:---------:|:-------:|:-----:|
| 自主完成 | 是 | 否 | 否 |
| 软阈值拉人后完成 | **否** | **是** | 否 |
| 熔断（保留已完成步骤） | 否 | 否 | **是** |
| 失败 / 未执行 / 超时 | 否 | 否 | 是 |

**熔断一律计失败**。直觉上「保留了前 3 步成果」像成功，但若算成功，熔断率会伪装成成功率。

**聚合规则**：每组独立判定，**任一组不达标即整体 No-Go**，不做加权平均。加权平均会导致「用一个岗位的成功掩盖另一个的失败」。

## 3. 明确不做（Out-of-Scope，锁定）

> 本章是防蔓延清单。任何新增需求必须先回答「为什么不能进 MVP」。

### 3.1 架构不可行项（6 项，非难度问题）

> 这 6 项不是「排不下」，是**在云端 SaaS 多租户形态下架构上不可行或无意义**。 EvoFlow 是 Tauri 桌面单机，依赖这些能力成立；搬到共享服务器上，它们从「便利」变成「灾难」。

| # | 不做 | 架构原因 | 何时考虑 |
|---|------|---------|---------|
| **O1** | **访问宿主机本地文件系统** | SaaS 服务器是所有租户共享的。能挂载或读取宿主机文件系统 = **跨租户文件泄露**，且无技术手段在应用层兜底（内核层已越权）。**架构绝对禁止，不是难度问题。** | **永不做。** 即便私有化部署，也不允许 Agent 访问宿主机文件系统；需要文件时走对象存储 + 租户前缀 |
| **O2** | **本地模型推理** | 需要 GPU。云 GPU 是**持续成本**（按小时计费、闲置也计费），与「按月订阅、人均一 ¥300」的定价模型根本冲突。且多租户共享 GPU 需额外隔离层（CUDA 级隔离不成熟）。 | Phase 3，且仅作为「私有部署 + 本地推理」的整包方案，不在云端 SaaS 内提供 |
| **O3** | **桌面系统托盘常驻** | Web 形态无此概念。托盘常驻的价值是「本地 Agent 后台待命」，我们的后台任务由服务端 Hatchet 调度，不需要客户端常驻。 | 永不做（除非回到桌面形态） |
| **O4** | **读取本地剪贴板 / 系统级文件拖拽** | 浏览器权限受限且需用户主动授权，**授权粒度是「整类文件」而非单文件**，无法满足「精确指定一个文件」。且拖拽上传在移动端不可用。 | Web 侧用「文件选择器 + 拖拽到上传区」替代（浏览器原生能力，已在 PRD §7.3 F5 范围内） |
| **O5** | **系统级文件锁** | 多租户共享文件系统下无意义——租户之间本就不该看到对方的文件，不存在「抢同一个文件」的语义。租户内的并发写冲突由数据库事务解决，不是文件锁。 | 永不做 |
| **O6** | **单机 SQLite 零配置** | 与多租户 + RLS **根本冲突**：RLS 依赖 `SET LOCAL app.current_tenant` 的会话/事务上下文，SQLite 无角色体系、无 RLS、无并发写。零配置的代价是失去隔离，而隔离是这个产品的底线。 | 永不做 |

### 3.3 被砍模块的销售话术红线（总监硬规则）

> **产品边界变更不同步销售口径，销售会用旧承诺签单，由交付还账。**

> **规则升级（总监采纳 PM 提议）**：只说「不许说 X」会让销售无所适从反而更可能说错。

| 禁止说 | 为什么 | **允许说** |

| 「支持任意网站自动操作」 | 只做明确定义的数据抓取，不做通用浏览器代理 | 「每天自动抓取你指定的站点，把变化写成日报」 |
| 「能自动登录你的后台 / ERP 并写入」 | L3 不做自动登录，**要承担客户账号密码的保管责任** | 「你导出文件上传，员工负责核对、比对和录入」 |
| 「支持多 Agent 协作」 | 已砍（PM 方案 A 全砍采纳） | 「一名员工负责一个岗位，按岗位分工」 |
| 「可视化编排 / 拖拽搭建流程」 | 已砍。**「不做画布」本身就是差异化** | 「选岗位、配一次、它每天自己干活」 |
| 「企业级知识库」 | 只做基础检索（结构化过滤 + 向量 top-K） | 「上传你的表格和文档，员工基于它们干活」 |
| 「支持飞书 / 钉钉群推送」 | MVP 只做企微 | 「每日汇报推送到企业微信」 |
| 「桌面客户端」 | 纯 Web，无 Tauri 壳 | 「打开浏览器就能用，不用安装」 |
| 「平台代付 / 充多少送多少」 | **已删。纯 BYOK + 线下收款** | 「用你自己的模型 Key，费用付给模型厂商；开通走线下签约」 |
| ~~「我们不采集 IP」~~ | **已不再是问题**——纯 BYOK 下无充值即无薅羊毛，设备指纹采集已删除，隐私承诺恢复为**无例外的绝对表述** | 「我们不采集 IP、不采集设备指纹、不记录你的模型调用内容」 |

**「自动盯竞品」恢复为允许表述**（DECISION-CHANGES 变更一）：G1-G4 护栏已在，法律敞口可控。正确表述示例：
> 「每天早上自动看完你指定的几家竞品，把价格与动作的变化写成日报推给你。」

**但禁止说「全网监控 / 全网抓取」**——范围是客户指定的站点列表，不是全网。

### 4.3 认证方案（锁定）

| 项 | 规格 |
|----|------|
| 密码哈希 | `argon2-cffi`（优于 bcrypt，抗 GPU 破解），**禁止 bcrypt** |
| Access Token | JWT，**有效期 15 分钟** |
| Refresh Token | **有效期 7 天** |
| Refresh Token Rotation | **每次刷新都轮换**：旧 refresh token 立即失效，签发新 pair。若检测到旧 token 被复用（重放），**该用户所有 refresh token 立即吊销**并记安全日志 |

| 传输 | 全链路 TLS |
| RBAC | 四租户角色：`owner`(4) > `admin`(3) > `member`(2) > `viewer`(1)；五全局角色独立于租户角色 |
| 权限收敛 | 子 Agent 有效权限 = `min(自身权限, 所有祖先权限)`，用递归 CTE + `MIN()` 一句实现 |
| **权限感知 Function Calling** | **过滤必须在发送给 LLM 之前完成**，让 LLM 看不到无权工具。禁止「知道有这个工具但调用时拒绝」——后者诱导模型反复尝试，既浪费 token 又有越权风险 |

| 标识 | 格式 | 用途 | 示例 |
|------|------|------|------|
| `tenant_id` | UUID v4 | 内部主键，数据库关联 | `a3f2c8e1-...` |
| `tenant_code` | `AC-` + 8 位 Base32 | 对外账套号，客服/工单用 | `AC-8F3K2M9W` |

**三层防护**：

```
+---------------------------------------------------------------+
| 校验层：越权自动化测试（17 条，阻断级）                          |
|  pytest（应用层） + pgTAP（数据库层）→ 进 CI，失败即阻断发布      |
+---------------------------------------------------------------+
| 查询层：强制显式 tenant_id                                        |
|  Repository 层签名强制带 tenant_id                                |
|  SQL 中显式 WHERE tenant_id = :tenant_id                          |
|  目的：查询计划可见 + RLS 之外的纵深防御                            |
+---------------------------------------------------------------+
| 连接层：PostgreSQL RLS（不可绕过）                                |
|  每请求事务开始 SET LOCAL app.current_tenant = :tenant_id          |
|  ENABLE + FORCE ROW LEVEL SECURITY                                 |
|  USING (tenant_id = NULLIF(current_setting(                       |
|            'app.current_tenant', true), '')::uuid)                 |
+---------------------------------------------------------------+
```

**四条硬规则**：

| # | 规则 | 违反后果 | 实测数据 |
|---|------|---------|---------|
| R1 | 必须 `FORCE ROW LEVEL SECURITY`（不只是 ENABLE） | 只写 ENABLE 时**表 owner 依然能看到全部数据**——不报错、不告警、静默绕过。而表 owner 恰恰是应用最可能使用的连接身份 | — |
| R2 | 策略里**禁用 PL/pgSQL 函数**，用内联式 `NULLIF(current_setting(...), '')::uuid` | PL/pgSQL 未标 STABLE 时是 VOLATILE，对每行调用一次 → 索引失效 → 顺序扫描 | **170x**（11.0ms → 1,877ms，200 万行 / 1000 租户）。中位租户（534 行）同样受害（1,860ms） |
| R3 | 必须 `SET LOCAL`，不能 `SET` | 会话作用域在连接池复用时泄漏给下一个用户。PgBouncer transaction 模式下 `set_config` 第三参数必须传 `true` | — |
| R4 | 视图必须显式 `security_invoker = true` | PG 15+ 视图默认以 owner 权限运行，**绕过 RLS** | — |

**fail-closed 语义（易被忽略的硬约束）**：`app.current_tenant` 未设置时策略求值为 NULL，查询返回 **0 行而非全部行**。这是**正确的安全默认**，但会让「忘记设置租户上下文」的 bug 表现为「列表页空了」而非报错。

> **必须在 Repository 层检测 `current_setting('app.current_tenant', true)` 为空时记录显式告警日志（level=WARNING, tag=`tenant_context_missing`），并配告警规则。不能让它静默发生。**

**越权响应语义**：

```
资源属于当前租户  ->  200 OK
资源属于其他租户  ->  404 Not Found        ← 不可区分于「真的不存在」
资源不存在        ->  404 Not Found
未认证            ->  401 Unauthorized     （不泄露任何资源信息）
已认证但租户内无权限 ->  403 Forbidden      （仅限「知道资源存在且属自己租户」的场景）
```

**403 的泄露机制**：403 本身就在泄露信息——攻击者可通过响应码差异做资源枚举（403 = 该 ID 存在但你无权访问，404 = 该 ID 不存在）。用 403 等于提供一个可批量扫描的 oracle。

**必须同时防时序侧信道**：跨租户访问（走 RLS 后 0 行）与真实不存在（走索引未命中）的**响应时间应有量级一致性**，不能让攻击者通过响应时间差异区分。

**实现约束**：
- Repository 层对 `tenant_id` 不匹配与「记录不存在」**返回同一种结果**（抛同一个 `NotFound`），不允许在服务层区分
- **RLS 天然满足这一点**：`SET LOCAL app.current_tenant='A'` 后查 B 的记录，SQL 返回 0 行，服务层看到的就是「不存在」
- 所有跨租户拒绝**必须记安全日志**（`audit_logs`，level=WARN，事件类型 `cross_tenant_denied`），但**日志中不记录目标资源的标题/名称/文件名**，只记录 ID 与租户对

### 4.5 沙箱隔离（锁定）

**五层防护**：

| 层 | 措施 | 防什么 |
|----|------|--------|
| **L5 网络** | 出网 default-deny + 租户级白名单；DNS 限制到内部解析器（阻断 C2 域名解析）；沙箱网段与生产网段隔离 | 数据外泄、C2 通道 |
| **L4 资源** | cgroups v2：CPU 配额 / 内存上限 / `pids-limit` / 磁盘配额；**超限即杀**（不是排队） | 资源耗尽打垮共享宿主 |
| **L3 凭据** | **凭据不进环境变量**（`ps` / `/proc/*/environ` 可读）；经 stdin 或一次性 token 文件注入，任务结束立即销毁；**每租户独立解密密钥** | 凭据泄露 |
| **L2 容器加固** | `--cap-drop=ALL` · 禁止 privileged · `--read-only` rootfs · seccomp + AppArmor + user namespace；可写路径仅 `/workspace` | 提权与持久化后门 |
| **L1 隔离** | gVisor runsc：用户态内核拦截 syscall；宿主机内核攻击面 = 经审核的 syscall 最小子集 | 容器逃逸 |

**纵深防御**：L1 不构成「绝对安全」，gVisor 自身有过 CVE。**所以 L2-L5 是强制的，不是可选的加固。**

**基线配置**：

```bash
  --security-opt seccomp=sandbox.json \
```

**出网策略 + G1-G4 四条护栏（ADR-014 恢复 L1 抓第三方公开网页）**：

```yaml

  - { host: "api.openai.com",     port: 443, reason: "LLM API（BYOK 时不需要）" }
  - { host: "api.anthropic.com",  port: 443, reason: "LLM API" }
  - { host: "api.deepseek.com",   port: 443, reason: "LLM API" }

```

| 护栏 | 内容 | 防什么 |
|------|------|--------|
| **G1** robots.txt 合规 | 抓取前检查目标站 robots.txt，`Disallow` 命中即跳过并记录，**不允许绕过** | robots 协议违规（法律风险） |
| **G2** 频率限制 | 单域名 ≥2s 间隔；单租户 ≤20 请求/分钟；全平台 ≤200/分钟。**服务端强制，不靠 Agent 自觉**（LLM 会因重试高频请求） | 压垮目标站（可能被封禁我们 IP） |
| **G3** UA 声明 | `OPCAgentAI/1.0 (+https://...; contact=...)`，**不伪装成 Chrome**（伪装本身在很多站点 ToS 里违规） | 身份隐瞒 |
| **G4** 失败显式化 | 抓取失败 / 被 robots 拒绝 / 内容为空，**必须记入「我停下来过」板块**，禁止返回空日报冒充成功 | **静默失败是外部依赖类岗位最伤信任的错误** |

**G4 是四条中最重要的一条**：最危险的失败模式不是「抓不到」，而是「**抓不到但报告说今天没有异常**」——老板会据此做商业决策。**返回空日报等于撒谎。**

> **G4 不许因范围变化而放松**：C1 收窄时我们说过「客户自有站点同样会挂」；范围恢复到第三方后这条**只会更重要**——目标站改版、加防护、要登录都是常态。G1/G3 的定位是「**约束平台行为**」而非「取悦客户」。

**镜像策略**：基线镜像 `python:3.13-slim-bookworm`、`node:22-slim-bookworm`；**客户自定义镜像 MVP 不支持**（自定义镜像是攻击面）；依赖预装进镜像，沙箱内动态 `pip install` 默认禁用；CI 阶段 `trivy` 扫描，HIGH/CRITICAL 阻断发布。

**孤儿沙箱清理**：每 60 秒扫描 `--label ttl_epoch < now` 的容器并强制销毁。

**不做内存快照**：Firecracker 的 snapshot/restore 能把冷启动压到 28ms，但**跨租户复用快照有数据残留风险**。MVP 不用。

### 4.6 长任务引擎（F6-lite，锁定分期）

**采用三层状态模型，而非三选一**：

```
+--L3 业务层: task_steps 表---------------------------------------+
|  业务步骤状态机: pending/running/succeeded/failed/skipped       |
|  消费者: F4 每日汇报、费用归集、用户可见的「卡在第 N 步」         |
|  粒度: 业务可读（「读取竞品页面 3/10」）                          |
+----------------------------------------------------------------+
+--L2 执行层: LangGraph Checkpointer ----------------------------+
|  图节点状态快照 + 增量 delta, schema: langgraph_checkpoints     |
|  消费者: 崩溃恢复、interrupt/resume                            |
|  粒度: 图节点（fetch_url / parse / llm_decide）                 |
+----------------------------------------------------------------+
+--L1 正确性层: 幂等键---------------------------------------------+
|  task_steps.PRIMARY KEY (goal_id, step_ordinal)                 |
|  L2 checkpoint 写入同样幂等                                      |
+----------------------------------------------------------------+
```

**F6-lite 的五条硬约束**：

| # | 约束 | 理由 |
|---|------|------|
| F6-1 | **节点内业务写入必须幂等**（最高优先级）。幂等键 = `thread_id + node_name + attempt_ordinal` | checkpoint 与业务数据**不在同一事务**，「业务成功但 checkpoint 未落盘」必然发生 |
| F6-2 | **孤儿巡检不可省**，心跳阈值 30 分钟 | worker 崩溃后 run 永久 `running` 是可用性灾难 |
| F6-3 | checkpoint 表膨胀控制：活跃 run 全量保留；终止 run 只留最近 3 个或 7 天后归档到对象存储 | — |
| F6-4 | **`thread_id` 必须等于 `goal_id`** | 否则用户刷新页面找不到自己的任务 |
| F6-5 | **LLM 调用必须在图节点内部** | LangGraph 重放语义是「已完成节点不重跑」，图外循环会被重复执行并重复计费 |

**无进展检测：C6 裁决后的双信号方案**

| 信号 | 判定 | 强度 | 阶段 |
|------|------|------|------|
| **S1a** 签名序列完全重复（**含归一化参数摘要**）连续 5 步 | 硬熔断 | 误报极低 | F6-lite |
| **S1b** 签名序列重复但参数在推进（如 url 索引递增） | **不熔断，只计数** | — | F6-lite |
| **S2** 产出物增量连续 N 步为 0 | 熔断（hard）/ 软暂停（soft） | 强 | **F6-lite 新增** |
| S3 外部副作用连续 N 步为 0 | 熔断 | 中 | F6-full |
| S4 状态指纹 | 辅助 | 弱（易骗过） | F6-full |

**S1a 签名必须含归一化参数摘要**（C6 裁决，这是原设计的缺陷修正）：

```python
PATH_LIKE_KEYS = {"url", "page", "index", "offset", "id"}   # 循环索引参数

def tool_signature(step) -> str:
    """工具名 + 参数归一化摘要。参数不同则签名不同。"""
    parts = []
    for k in sorted(step.args.keys()):
        v = step.args[k]
        if k in PATH_LIKE_KEYS:
            parts.append(f"{k}={v}")        # 保留原值——区分「循环推进」与「原地打转」正靠它们
        else:
            parts.append(f"{k}={hash(v)}")  # 内容参数用哈希（内容每次都变）
    return f"{step.tool_name}({','.join(parts)})"
```

| 场景 | 仅含 tool_name（错误实现） | 含参数摘要（正确） |
|------|--------------------------|------------------|
| 下载 50 个页面（url 每次不同） | **误杀**（第 5 步命中） | **正确放行** |
| 原地重试同一失败 url | 误杀 | **正确熔断** |
| 死循环调同一工具同参数 | 误杀 | **正确熔断** |

**F6-lite 必须同时含 S1a 与 S2**。S1a 收窄后不足以单独承担熔断职责——这是 C6 裁决的直接后果，也是 Effort 从 1.5-2 修正为 **1.5-2.5 人月**的原因。

**阈值由岗位模板声明，不硬编码**：`expected_idle_steps` 默认 5，软阈值 = 岗位预期，硬阈值 = 岗位预期 × 2。
- 「下载 100 个页面」每步产出物相同是正常的（N=100）
- 「读一份 Excel」第 3 步没产出就是卡死

**软阈值是「暂停等确认」，不是直接熔断**。这是 HITL 的正确用途。最多允许 2 次连续软暂停（防止无限问）。

**实现方式（v1.1 实测对齐，原 `interrupt()` 方案已替换）**：软暂停通过 `SoftPauseSignal` 异常 → `StatusTransitions.set_soft_pause` 置 `waiting_approval` 状态 + 落 `needs_human_input` 事件实现；恢复走 `resume()`（校验状态 → `resumed_count+1` → checkpoint 从断点继续）。**不使用 LangGraph 原生 `interrupt()`** —— 原生 interrupt 需要审批 UI 回传 `Command(resume=...)`，Phase 3 接审批流时再评估切换。

**租户级上限（soft pause DoS 防护）**：同一租户同时处于 `waiting_approval` 的任务超过 `SOFT_PAUSE_TENANT_LIMIT=5`（**未实测，Phase 3 按真实岗位并发量校准**）时，不再新增暂停而是转为熔断（error_code=`soft_pause_limit`），文案只讲业务事实（AC-F3）。

**已知技术边界**：无进展检测窗口只在**节点边界**落盘与恢复，节点内部的无进展（单步 LLM 长时间重试）检测不到 —— 这是 checkpoint 粒度的固有限制，Phase 3 若需更细粒度再评估。

**熔断判定必须在下次 LLM 调用之前完成**：

```python
async def guarded_node(ctx):
    verdict = await progress_guard.evaluate(ctx.goal_id, ...)
    if verdict.level == "circuit_break":
        raise CircuitBroken(verdict.reason, verdict.user_message)   # 不再调 LLM
    if verdict.level == "soft_pause":
        interrupt_for_human(verdict.user_message)
    return await real_node(ctx)
```

若等模型返回再判定，熔断时那一次的 token 已经花了——**且死循环场景下每轮都是完整 LLM 调用，这是漏损最大的一处**。

**检测窗口状态（`idle_streak` / `seen_tool_windows`）必须随 checkpoint 持久化**。否则崩溃重启后窗口归零，死循环会重复触发 N 次才熔断，每轮都是真金白银。

**资源上限**：

| 项 | 默认值 |
|----|-------|
| Goal 最长运行时长 | 24 小时 |
| Goal 最大节点数 | 1000 |
| Goal 最大 LLM 调用次数 | 5000 |
| Goal 最大花费 | ¥50（超额降级为只读模式） |
| 同时运行 Goal（租户级 / 全局） | 5 / 200 |

### 4.7 成本可见性与预算闸门（锁定，纯 BYOK 语义）

> **本节已按 DECISION-CHANGES 变更二 + ADR-019 重写。** 原「预占-确认-释放两阶段账本防超卖」随平台代付删除而**整块作废**——平台不经手资金，无余额可预占、无超卖可能。

#### 7.1 为什么不需要防超卖

代付时代的超卖是 read-then-write 竞态：N 个并发任务同时读到同一 `remaining`、各自校验通过、各自扣费，实际消耗远超余额。

**纯 BYOK 下这个问题不复存在**：钱在客户与模型厂商之间流动，平台没有「余额」这个共享标量。**没有余额，就没有超卖。**

#### 7.2 成本数据从哪来——不是平台账本，是厂商返回的 usage

```
每次 LLM 调用 → 厂商响应带 usage: { input_tokens, output_tokens, cache_hit_tokens? }
成本 = Σ(input_tokens × 单价_in + output_tokens × 单价_out)
```

**这与谁付钱无关。** 因此 `usage_events` / `usage_records` 两张表完全保留，用途从「平台计费流水」变为「**客户成本可见性**」。

**这恰好是纯 BYOK 下的新卖点**：平台不经手钱，但**平台比客户更清楚他的钱花在哪**——客户只有厂商的月度总额，我们能给按岗位/按员工下钻的明细。

#### 7.3 单价权威来源与三个精度限制

| 途径 | 可用性 | 结论 |
|------|--------|------|
| 厂商官方 price API | **不存在** | 各家价格只在文档网页 |
| 抓取厂商文档页 | 可行但脆弱 | 页面结构变动即失效，且价格随时可变（DeepSeek 明确保留调价权） |
| **LiteLLM `model_prices_and_context_window.json`** | **可用** | 行业事实标准，3850+ 模型，社区每日同步 |

**裁定：采用 LiteLLM 价格表，每日同步 + 本地快照兜底**（拉取失败时用上次快照，不得中断服务）。

**三个精度限制必须写进 Spec，前端禁止假装精确**：

| 限制 | 影响 | 缓解 |
|------|------|------|
| **峰谷定价** | DeepSeek 峰时段单价翻倍，LiteLLM 表不含峰谷规则 | 预估标注「按非峰时段估算」 |
| **缓存命中差异** | DeepSeek 缓存命中输入 ¥0.02 vs 未命中 ¥1，**差 50 倍** | 预估按「部分命中」加权，标注区间而非单值 |
| **长上下文阶梯** | 超阈值后涨价 | 预估标注「不含长上下文阶梯加价」 |

> **结论：预估是「量级估算」不是「精确报价」。** 预算闸门用它是合理的（判断是否超预算），但**绝不能用于「这个任务确切要花 ¥3.42」这种表述**。

#### 7.4 预算闸门：语义从「平台止损」变为「帮客户盯自己的钱」

| 维度 | 原语义（代付） | 新语义（纯 BYOK） |
|------|--------------|------------------|
| 闸门目的 | 平台止损（防止平台亏钱） | **帮客户盯自己的模型账单** |
| 超预算后果 | 任务不执行 + 通知 | **警告 + 明确后果告知**，不硬拦 |
| 超预算必要性 | 必须 | **仍然必要**（见下） |

**纯 BYOK 下的新风险场景**：客户配了高频定时任务 + 不设预算的 AI 员工，几天下来 DeepSeek 账单烧掉几百块。**这正是预算闸门的新价值。**

**为什么警告而不阻断**：客户花的是自己的钱，我们无权替他决定不能花。但**我们必须让他知道**——「本月已用 ¥180/¥200，接下来 3 个定时任务预计再花 ¥60，你确定吗？」

**触发后行为**：任务不执行 + 通知 + **提供加额指引（引导联系客户经理）**。加额是线下动作（额度由线下谈判决定），不是线上自助。

#### 7.5 简化的账务架构

| 组件 | 处置 |
|------|------|
| `credit_accounts` | **删除**（无平台余额） |
| `credit_reservations` | **删除**（无预占对象） |
| `credit_ledger` | **删除**（无平台流水） |
| `usage_events` | **保留**（append-only，幂等键 `request_id`） |
| `usage_records` | **保留**（小时聚合） |
| `model_pricing` | **新增**（LiteLLM 价格表落地，版本化） |
| `agent_budgets` | **保留**（月度预算上限，性质改为「提醒阈值」） |

#### 7.6 ADR-012 三条设计原则的重新表述

| 原原则 | 纯 BYOK 下的形态 |
|--------|-----------------|
| 权威数据在 PG 不用 Redis 计数器 | 成本归集权威在 `usage_records`，Redis 只做缓存 |
| 幂等防重复 | **完全保留，且更重要**——见下 |
| 预占防超卖 | **不适用**（平台无超卖） |

> **幂等这条在纯 BYOK 下升级为最高优先级**：代付时代重复记账坑的是平台的钱，纯 BYOK 时代重复记账坑的是**客户对平台的信任**——他看到自己账单虚高 3 倍会立刻失去信任。**所以幂等约束在纯 BYOK 下更重要，不是更不重要。**

#### 7.7 四个计价维度保留

按 **租户 / 用户 / Agent / 模型** 四个维度归集。这是纯 BYOK 下的核心卖点——客户只能拿到厂商的月度总额，只有我们能给按岗位下钻的明细。

#### 7.8 账套号：零改动

用户原话「不要考虑充值问题，只要能在 SaaS 里做出客户公司账套号区分，可以线下收款开户」。

**ADR-003 的 `tenant_id` + `tenant_code` 完全满足，零改动：**

| 标识 | 格式 | 用途 |
|------|------|------|
| `tenant_id` | UUID v4 | 内部主键，数据库关联 |
| `tenant_code` | `AC-` + 8 位 Base32 | **对外账套号，客户身份识别码，用来登录**；一码两用（线下收款凭据） |

**用户已明确「账套号跟财务没有关系，是客户身份识别码」**，即标准多租户账号体系。**不要加 `external_account_no` / `company_name` 字段。**

`tenant_code` 的现有设计恰好匹配：可口述可截图（老板线下付款时能报出「AC-8F3K2M9W」）、不可枚举（40 bit）、不含业务信息。**唯一建议**：在账套设置页顶部大字展示 + 复制按钮 + 线下付款说明（当前在设置页里不够显眼）。

### 4.8 模型能力前置校验（锁定）

**双层判定，严格优先级**：

```
1. model_capabilities 表（显式声明，最高权威）    ← 能力表在数据库不在代码
2. 厂商 API metadata 探测（缓存 24h）             ← 补充
3. 保守默认（假设不支持）                          ← fail-closed 兜底
```

**五个能力维度**：`vision` / `tool_use` / `long_context` / `json_schema` / `streaming`

**五条硬约束**：

| # | 约束 |
|---|------|
| M1 | **判定必须 fail-closed**。探测失败/超时/异常**一律判为不支持**，绝不能 fail-open（fail-open 会让用户跑到一半失败，直接违反 AC-1「不需要任何配置就能跑」） |
| M2 | **探测必须低成本**。vision 探测用 1×1 像素 PNG；tool_use 用最小 tool 定义；`max_tokens=1`。探测费用计入成本（一次性，每模型约 ¥0.001） |
| M3 | **探测结果缓存 24h**。不能每次任务都探测（网络开销 + 限流风险） |
| M4 | **`long_context` 不主动探测**（发长请求成本高，一次可能 ¥0.5+）。用 `model_id` 启发式匹配已知长上下文模型 |
| M5 | **降级必须检查能力**。厂商故障切换到备用模型前必须校验能力是否满足，**不满足则中止而非静默降级** |

**能力表在数据库而非代码常量**：新模型上市时运营在后台填一行记录即可，**不发版**。

**节点粒度校验，不做岗位级整体校验**：单任务可能只需 `tool_use` 不需 `vision`，岗位级过严会阻塞合法任务。

**校验时机三处**：岗位配置时（阻断保存无效配置）+ 试跑/任务提交时（调度器权威阻断）+ 每个图节点执行时（只影响该节点）。

### 4.9 流式与事件（SSE，不引入 WebSocket）

**决定性因素是 `Last-Event-ID`**：Goal 长任务跑 3 小时，用户手机必然断网重连，SSE 的规范级重连+续传是决定性优势；WebSocket 的重连质量完全取决于我们自己写的代码。

**Redis Streams 事件总线**：

```
所有 worker / Hatchet / LangGraph 节点
        |
        v
  XADD goal:events:{tenant_id}:{goal_id}
        |  { seq: <单调递增>, type, payload, visibility, ts }
        v
  Redis Stream (MAXLEN ~ 10000)
        |
        +--> SSE 端点 XREAD（带 last_event_id）
        +--> 费用聚合消费者（消费组 A）
        +--> 可观测性消费者（消费组 B）
        +--> 审计消费者（消费组 C）
```

**Seq 生成**：必须单调递增且可比较。用 Redis `INCR goal:seq:{tenant}:{goal}` 分配，**不用 Stream 自身 ID**（Stream ID 是时间戳，同毫秒事件排序不稳定）。

**单条聚合连接**：前端**只开一条 SSE 连接**（`GET /api/v1/events/stream`），服务端按用户订阅的所有 goal 多路复用。不按任务分流——那会导致连接数爆炸（HTTP/1.1 下浏览器 6 连接硬上限）。

**SSE 四个必踩的坑**：

| 坑 | 现象 | 解法 |
|----|------|------|
| **Nginx 缓冲** | 流式完全失效，结束时一次性返回 | `X-Accel-Buffering: no` + `proxy_buffering off` |
| **Cloudflare 100s 空闲超时** | Agent 调工具时 90s 无输出，连接被静默掐断 | 每 30 秒发 `: keepalive\n\n` 注释行 |
| **ALB 60s 空闲超时** | 同上 | 目标组调至 300s |
| **HTTP/1.1 六连接限制** | 多个任务各开一条流后浏览器拒绝新连接 | **单条聚合 SSE 连接 + 服务端多路复用**；全站 HTTP/2 |

### 4.10 中止态与事件可见性（锁定）

**`stopping` 是独立状态，不是 flag**：

```
queued → running → stopping → cancelled
       └────────────→ completed  （中止生效前恰好跑完）
```

| 项 | 要求 |
|----|------|
| 状态枚举 | `goal_status` 增 `stopping`（**独立状态，不是 `is_cancelling` 布尔标志**） |
| **cancel 幂等** | **重复调用返回同一状态不报错**。UI 的 disabled 按钮是最后防线但**不能是唯一防线**（用户可能开两个标签页、或网络重试） |
| 实现顺序 | **先置 `stopping` 再发取消信号**（顺序不可颠倒）。否则用户点中止到看到反馈有 1-3 秒延迟，UI 无法显示中间态，用户会以为按钮坏了重复点 |
| 超时兜底 | `stopping` 最长 **5 秒**，超时由巡检器强制收敛为 `cancelled`。**保证 UI 永不卡在中间态** |
| 已完成步骤 | 保持原样，不回滚不置灰，**且不扣费** |
| 边界三种 | 恰好完成→直接 `completed` 不闪 `stopping`；`queued` 态中止→零延迟 `cancelled`；已 `cancelled`→幂等返回 |

**事件可见性分级**：

| 级别 | 内容 | 事件类型 | UI 呈现 |
|------|------|---------|---------|
| **L1 主叙事**（owner 可见） | 任务级里程碑 | `task_started` / `step_completed` / `task_completed` / `task_failed` / `needs_human_input` | 时间轴一行摘要 |
| **L2 细节**（owner 可见，折叠） | 单步输入输出、耗时、命中文档名 | `tool_called` / `retrieval_hit` / `file_written` | 折叠节点 |
| **L3 审计**（仅 admin） | 原始 prompt / 完整响应体 / 重试记录 / token 明细 | `raw_prompt` / `raw_completion` / `retry_attempt` / `token_usage` | **owner 界面绝不出现** |

```sql
ALTER TABLE goal_events ADD COLUMN visibility TEXT NOT NULL DEFAULT 'admin';
```

**默认值方向是这条设计的核心**：新增事件类型时若忘记标 `owner`，会**默认落在 admin 侧（安全）**，而不是默认泄漏给老板。

**SSE 端点按调用方角色在服务端过滤**（不依赖前端过滤）。

**L1 禁止项**：不得含 `[INFO]` / `elapsed=` / token 数——这是「禁止系统日志语汇」的落地。

**用量接口两个独立 endpoint（C5 裁决）**：

```
GET /api/v1/usage/summary      → OwnerUsageSchema  { task_count, cost_cents, breakdown_by_job }
                                                    （无 token / 无 model / 无 duration）
GET /api/v1/settings/usage     → AdminUsageSchema  { ..., input_tokens, output_tokens, model, ... }
```

**owner 口径的数据源不读 token 表**，从聚合路径上断开，不是「读了再剔除」。

```
1. 认证 + 租户上下文
2. 成员权限（viewer 禁止创建）
3. 模型能力校验（ADR-013，fail-closed）
4. 预算校验（调度器权威，ADR-012）
5. 排队入队 Hatchet
→ 立即返回 202 { goal_id, status: "queued", estimated_steps, estimated_cost_cents }
```

#### `GET /api/v1/usage/summary` vs `GET /api/v1/settings/usage`

**这是 C5 裁决的落地，两个 schema 必须完全独立**：

| | `usage/summary` | `settings/usage` |
|---|---|---|
| 角色 | owner | admin |
| Schema | `OwnerUsageSchema` | `AdminUsageSchema` |
| 含 `task_count` / `cost_cents` / `breakdown_by_job` | 是 | 是 |
| 含 `input_tokens` / `output_tokens` / `model` / `duration_ms` | **否（连 nullable 都不行）** | 是 |
| 数据源 | `tasks` + `cost_ledger` 聚合 | `usage_records` |
| 前端组件 | `OwnerSummaryView` | `UsageBreakdownView` |

**禁止用 `oneOf` 在同一 endpoint 表达**。owner 组件访问 token 必须**编译报错**。

#### `GET /api/v1/events/stream` — SSE

```
Content-Type: text/event-stream
Cache-Control: no-cache
X-Accel-Buffering: no
```

- 心跳：每 30 秒发 `: keepalive\n\n`
- 续传：支持 `Last-Event-ID` 请求头
- **按调用方角色在服务端过滤 `visibility`**
- Nginx 必须 `proxy_buffering off`

#### `DELETE /api/v1/tenants/current` — 彻底删除

**必须连带删除（AC-16，最易漏项）**：

```
[必删] business tables（RLS 强制）      [必删] kb_chunks（pgvector 向量表）
[必删] auth_refresh_tokens             [必删] langgraph_checkpoints.*（任务 checkpoint）
[必删] analytics_events                [必删] tenant_egress_allowlist
[必删] 对象存储前缀 tenants/{code}/     [必删] Redis key 前缀 tenant:{id}:
[必删] 沙箱：按 --label tenant_id 批量销毁
```

- **过程可审计**：每一步写 `audit_logs`，事件类型 `tenant_purge_step`
- 失败即中止，不允许部分删除后返回成功

### 6.1 RLS 全局规则（违反即阻断发布）

| 项 | 规则 |
|----|------|
| 适用范围 | **除 `users` / `model_capabilities` / `job_templates` 外的所有表** |
| 启用方式 | `ALTER TABLE x ENABLE ROW LEVEL SECURITY;` **紧跟** `ALTER TABLE x FORCE ROW LEVEL SECURITY;`（缺 FORCE 等于没开） |
| 策略写法 | 内联式 `USING (tenant_id = NULLIF(current_setting('app.current_tenant', true), '')::uuid)`，**禁用 PL/pgSQL 函数** |

#### 老板汇报页（`/`，密度 4）

四板块固定顺序（**顺序本身承载信息**：先看成绩，再看要处理的，再看协作，最后才看钱）：

| 板块 | 空状态 | 折叠 |
|------|--------|------|
| ① 今天做完了什么 | **不隐藏**，写「今天没有需要产出的活，员工在待命」+ `Pause` | MVP **不折叠**（阈值 = ∞） |
| ② 要你管 | 为 0 时**整个板块不渲染**（不是写「一切正常」） | 不折叠 |
| ③ 我停下来过 | 为 0 时渲染「今天没有员工打断你。」+ `CircleCheckBig` | 不折叠 |
| ④ 花的钱 | 必渲染。`Coins` + 「今天没有产生模型调用费用。」（**不用「¥0.00」**） | 不折叠 |

**底层原则：省略比报错更伤信任。** 老板无法区分「没活干」和「被跳过了」，所以必须显式区分。

**验收标准 10 的两段式渲染**：顶部**必须先声明总数**（`在岗 X / 待命 Y`），待命员工**必须列出姓名 + 原因**（排班结束/无任务/未配置完成），**禁止「+2 名待命」式折叠计数**。若某员工本应执行但未执行（异常），必须显式标出。

**信任闭环指标**：首页展示「本月你的员工停下来问过你 N 次，每次你都做了决定。它们没有一次是猜的。」

> **数据真实性硬要求**：N **必须来自真实事件流统计**（`task_escalated_to_human` × `escalation_resolved` 配对计数），**禁止硬编码、禁止取整凑数、禁止在无数据时编造**。为 0 时显示「本月你的员工没打断过你，说明它拿得准」——**不用空洞的庆祝文案**。硬编码或无数据时编造均视为 **P0 缺陷**（信任指标造假等于在信任指标里投毒）。

#### 待确认队列（`/pending`）

| # | 硬约束 | 理由 |
|---|--------|------|
| 1 | **禁止使用 `--warn` / `--danger` 作为容器色，禁止告警图标**，改用 `Hand`（举手） | 这是本产品**唯一会被「非故障」触发的红/黄场景**。一旦建立「红色=有问题」的映射，老板看到红色就紧张，而这条队列不是问题，是协作。**用红色会让一个正向设计变成信任负债。** |
| 2 | **每条必须含「依据」行**（引用具体文件与位置） | 把「它不确定」转成「它查过且发现了矛盾」的唯一手段。**没有依据行，问问题就等于甩锅** |

### 8.1 设计语言与对标

| 项 | 结论 |
|----|------|
| 寄存器 | **Product**（工具界面，非营销页） |
| 一句话 | 把「管理一支 AI 团队」做成一台精密仪器——每个数字都可追溯，每个员工都在你能看见的状态里 |

### 8.4 质感规则（5 条，不可违背）

| # | 规则 | 做法 | 为什么 |
|---|------|------|--------|
| **T1** | **层级用「1px 边框 + 亮度递进」，不用投影** | 深色下靠 surface 亮度递进（`#0B0D0E → #111618 → #171D20 → #1F2629`，每级 1.07:1），需要边界时加 1px `--border` | 投影有方向，暗示「光从上面来」，多层级界面会造成视觉噪音与「贴纸感」。亮度递进无方向，永远成立。**唯一例外**：真正的浮层（Popover/Modal/拖拽层）才用一层 `0 8px 24px rgba(0,0,0,0.4)` |
| **T2** | **表格优先，卡片是例外** | 员工列表、任务列表、资产列表、用量明细四类一律表格。判定：一页 ≥5 个同类结构化对象 → 表格；<5 且需富描述 → 卡片。**混用禁止** | Retool 纪律。表格行高 40px（任务中心 36px），`px-3 py-2`，行分隔 1px，**不用斑马纹**（廉价感主要来源） |
| **T3** | **三级字重 400 / 510 / 590，禁 700** | 正文 400 / 小标题与表格头 510 / 页面主标题 590。**强调顺序：先改字号 → 再改字重 → 最后才用颜色**。禁止用强调色写标题。**等宽字体承载所有标识类信息**（员工 ID、任务 ID、Token 数、时间戳、金额） | 700+ 是营销页的东西。510 是 Inter 的「强调但不喊叫」层级手段 |
| **T4** | **留白小-小-大对比序列** | 同组元素 8px；标签与控件 6px；卡片内边距 16px；卡片之间 12px；**页面主区块之间 48px**。**硬规则：若所有间距相等，界面就没有层级可言。** 内容最大宽度：会话区/汇报区 `max-width: 720px`（约 65 中文字符） | 「小—小—大」的节奏对比是层级的唯一来源 |
| **T5** | **深度只有两级（L0 平 + L1 浮）** | L0（95% 界面）：无投影，1px 边框或无边框。L1（Popover/Modal/Toast/拖拽中）：`0 8px 24px rgba(0,0,0,.4)`。**不存在 L2。** 禁用毛玻璃装饰（`backdrop-filter` 仅允许 Modal 遮罩 `backdrop-blur:2px` 且必须配 `rgba(0,0,0,0.6)`） | 无限制的层级会导致「什么都能浮」，界面失去重点 |

**补充规则**：
- 间距仅允许 4px 网格：`4 / 8 / 12 / 16 / 20 / 24 / 32 / 48 / 64 / 80`。禁止 5/7/13/15/22/30
- 圆角阶梯：`4px`（Badge/状态点/输入框）/ `8px`（按钮/卡片默认）/ `12px`（弹窗/大面板）/ `9999px`（仅 Avatar 与状态胶囊）。**禁止卡片圆角 ≥24px**
- 字号：`11 / 13 / 14 / 16 / 20 / 24 / 32px`。**UI 默认 13-14px**（监看场景密度优先），但**正文段落与知识库内容不低于 16px**
- 动效仅 3 条：`80ms`（按下/状态点变色）、`150ms`（hover/选中/展开）、`200ms`（面板进出/模态框）。持续进行用 `1000ms` 循环（运行中脉冲点、进度条推进）。**禁止弹跳缓动 `cubic-bezier(0.68,-0.55,0.265,1.55)` 及其等价变体**
- **必须实现 `@media (prefers-reduced-motion: reduce)`**：所有 transition/animation 降为 `0.01ms`，运行中脉冲点改为静态实心 + 文案「运行中」

### 8.5 字体（锁定，全 OFL-1.1）

## 9. 验收标准（锁定）

> **来源**：PRD §12 全部 **18 条**（非任务交底所说的 16 条，见 C2 裁决），**原文照录，一字不改**。
> **格式说明**：PRD 原文为 Given/When/Then，本节在保留原文的同时给出 EARS 表述（Easy Approach to Requirements Syntax），便于工程侧直接转为测试用例。

### 9.1 阻断级验收标准（必须 100% 通过，否则禁止发布）

#### AC-1 快速激活

> **Given** 新老板（不懂技术），已知公司 11-30 人
> **When** 完成注册 → 选「给我建议岗位」→ 选「电商订单录入」→ 上传订单 Excel → 不改任何默认值点「跑一次试试看」
> **Then** **10 分钟内**看到试跑结果页，含步骤流水、待确认记录、本次费用三项；不需要写任何 prompt，不需要看任何文档

**EARS**：`When` 用户完成注册并选定岗位模板、上传知识源、且未修改任何默认配置，`Then` 系统应在 10 分钟内返回试跑结果页，且该页必须同时包含步骤流水、待确认记录、本次费用三个区块。

> **Phase 1.5 适配说明**：PRD 原文以「电商订单录入」为例。**当前 MVP 岗位 #1 已恢复为「竞品监控日报」**（DECISION-CHANGES 变更一，用户复看推翻 C1 收窄），且它是 5 个岗位中**唯一零配置就能跑**的，恰好是 AC-1「不改任何默认值」这一验收条件的最佳载体。验收时岗位名取「竞品监控日报」，**验收逻辑与 10 分钟阈值不变**。

#### AC-2 上生产

> **Given** 已成功试跑 ≥ 1 次的 AI 员工
> **When** 开启定时「工作日 9:00」
> **Then** 定时配置成功；次日 9:30 收到企微推送的每日汇报；当日费用计入本月累计

**EARS**：`When` 已成功试跑至少 1 次的 AI 员工被设置为「工作日 9:00」定时，`Then` 系统应在次日 9:30 通过企业微信推送每日汇报，且当日费用必须计入本月累计。

#### AC-3 预算阻断

> **Given** AI 员工本月预算 ¥200 已用满
> **When** 次日定时任务到达
> **Then** 任务**不执行**；收到「预算用完了，我停下来问你了」；待办里出现「加到 ¥400 继续 / 下月再说」；**未产生任何模型调用费用**

**EARS**：`When` 某 AI 员工的本月累计费用已达到其预算上限，`Then` 系统必须阻断该员工的定时任务执行，推送预算用尽通知，在待办中提供两个选项，且不得产生任何模型调用费用。

> **纯 BYOK 语义修正（ADR-019）**：PRD 原文「任务不执行」在纯 BYOK 下语义已变——**平台止损改为帮客户盯自己的钱**。
> 实现分两档：
> - **达 100% 上限**：定时任务**不执行** + 推送待办 + 加额指引（引导联系客户经理，**加额是线下动作**）。
> - **达 80% 预警**：任务**正常执行**，但推送预警并告知「接下来 3 个定时任务预计再花 ¥60」。
>
> **为什么达 100% 仍阻断**：客户设了这个数就是他的意图，越过它等于无视他的决定。但**若客户主动发起**（非定时），只警告不阻断——他有权花自己的钱。区分「客户主动」与「系统定时」是这条的落地关键。

#### AC-4 断点续跑

> **Given** 一个 40 步任务执行到第 25 步时服务进程崩溃
> **When** 用户次日重新打开任务
> **Then** 任务状态为「已中断，可续跑」；点「继续」后从第 26 步执行；1-25 步成果和费用都保留

**EARS**：`When` 任务执行中断，`Then` 系统应将该任务标记为可续跑状态，从最后一个已持久化的 checkpoint 恢复，且此前已完成步骤的成果与费用不得丢失或重复计费。

#### AC-5 熔断保护

> **Given** 一个任务反复执行同一步且状态无变化
> **When** 触发无进展检测
> **Then** 系统熔断停止；**已完成步骤成果保留**；收到「我卡在第 N 步，已停下，今天做完了 1-24 步」；**不产生熔断后的额外费用**

**EARS**：`When` 无进展检测达到熔断阈值，`Then` 系统必须停止任务、保留全部已完成步骤、向用户报告卡在第几步，且熔断判定必须发生在下一次 LLM 调用之前以确保不产生额外费用。

#### AC-6 诚实的失败

> **Given** AI 无法判断某条记录
> **When** 执行中触发异常处理规则
> **Then** 该记录**不猜测**，进入待确认队列；试跑/汇报中明确列出「这 N 条我不敢处理，需要你看一眼」；**不把部分成功包装成全部成功**

**EARS**：`When` AI 在执行中遇到无法判断的记录，`Then` 系统必须将该记录放入待确认队列而非猜测处理，必须在试跑结果与汇报中显式列出，且不得将部分成功呈现为全部成功。

#### AC-7 自带密钥

> **Given** 用户填入有效 DeepSeek 密钥
> **When** 发起任务
> **Then** 任务正常完成；结果页显示「本次消耗 ¥0.00（你自带密钥）」+ 模型调用次数；密钥在设置页以掩码显示且可随时更换

**EARS**：`When` 用户配置有效的 BYOK 密钥，`Then` 任务应使用该密钥完成，结果页显示平台代付费用为 ¥0.00 与调用次数，且密钥在设置页必须以掩码显示并支持随时更换。

#### AC-8 余额不足阻断

> **Given** 用户未填密钥，平台代付余额 ¥0.5，单任务预估需 ¥3
> **When** 提交任务
> **Then** 系统在**执行前**阻断并提示预估费用；要求充值或改用 BYOK；**不允许透支执行**

**EARS**：`When` 用户提交任务且平台代付可支出余额低于任务预估费用，`Then` 系统必须在执行前阻断并提示预估费用，要求充值或改用 BYOK，严禁透支执行。

> **纯 BYOK 语义修正（ADR-019）**：**本条的平台代付部分已作废**——纯 BYOK 下无平台余额可透支。
> 保留的核心是「**执行前提示预估费用**」与「**密钥无效即阻断**」：
> - 用户未配置任何密钥 → **阻断**并引导至「连接你的模型」页（**首次接入摩擦的三个处理方案见 ADR-019**）
> - 密钥配置但**探测失败** → **阻断**（fail-closed，ADR-013 M1），提示「这个 Key 现在用不了，请检查或更换」
> - 密钥有效但**模型能力不足** → **阻断**（ADR-013），列出缺失能力
>
> **「平台代付余额不足」场景已不存在**，改为「**平台代理 Key 的线下签约额度用尽**」——此时任务不执行 + 引导联系客户经理。

#### AC-9 部分成功

> **Given** 48 条任务中 2 条重复被跳过，46 条成功
> **When** 任务结束
> **Then** 汇报显示「完成 46 / 48，2 条已跳过」；46 条的成果正常交付；**不因 2 条失败而丢弃 46 条成果**

**EARS**：`When` 任务中部分记录成功、部分记录被跳过，`Then` 汇报必须显示成功与跳过的准确数量，成功部分必须正常交付，且不得因部分失败丢弃已成功的成果。

#### AC-10 每日汇报完整性

> **Given** 租户有 3 个 AI 员工，其中 1 个当日执行失败
> **When** 查看当日汇报
> **Then** 三条汇报齐全；失败的那条显示「今天没跑成，卡在第 3 步」+ 重试入口；**不得静默跳过**

**EARS**：`When` 租户当日存在执行失败的 AI 员工，`Then` 汇报必须为每个员工各生成一条，不得静默跳过失败员工，失败条目必须显示卡在第几步并提供重试入口。

#### AC-11 成本透明

> **Given** 任意 AI 员工任务完成
> **When** 打开结果页或汇报
> **Then** 必现本次费用、调用次数、累计费用/预算的对比；**无需进入设置页即可看到**

**EARS**：`When` 任意 AI 员工任务完成，`Then` 结果页或汇报中必须展示本次费用、调用次数与累计费用对预算的占比，且用户无需进入设置页。

#### AC-12 越权隔离

> **Given** A 租户与 B 租户均已开通
> **When** A 租户尝试通过修改请求参数访问 B 租户的任务或文件
> **Then** 访问被拒绝；记录安全日志；**不泄露 B 租户任何数据存在性**

**EARS**：`When` A 租户尝试通过修改请求参数访问 B 租户资源，`Then` 系统必须拒绝访问、记录安全日志，且不得以任何形式泄露该资源的存在性。

#### AC-13 越权响应码

> **Given** A 租户尝试访问属于 B 租户的资源
> **When** 服务层返回响应
> **Then** **返回 404 而非 403**。403 会泄露「该 ID 存在但无权限」，攻击者可用响应码差异批量枚举其他租户的资源 ID 与规模。同时需防时序侧信道：响应时间不得因资源是否存在而显著差异

**EARS**：`When` A 租户访问属于 B 租户的资源，`Then` 系统必须返回 404 而非 403（403 会泄露资源存在性形成扫描 oracle），且跨租户访问与真实不存在的响应时间不得有显著差异。

#### AC-14 可观测性数据边界

> **Given** 任意任务执行
> **When** 检查该任务的 trace 与日志
> **Then** **允许记录**：模型名、token 数、延迟、费用、工具名、参数摘要、chunk ID 与相似度
> **禁止记录**：prompt 全文、工具返回全文、文档内容、检索到的 chunk 原文。OTel 的 `gen_ai.prompt` / `gen_ai.completion` 语义约定属性**不得用于承载内容**，只用 `gen_ai.usage.*` 与 `gen_ai.request.model`

**EARS**：`While` 任务执行中，`Then` 可观测性系统必须仅记录模型名、token 数、延迟、费用、工具名、参数摘要、chunk ID 与相似度；且禁止记录 prompt 全文、工具返回全文、文档内容与检索到的 chunk 原文，OTel 语义约定属性不得承载内容。

#### AC-14b owner 视图接口层剔除 token 字段

> **Given** 老板访问用量类接口
> **When** 检查响应体
> **Then** **owner 视角的用量接口在接口层就不序列化 token 字段**——不是置空、不是 null、**是不返回**。用 OpenAPI 不同 schema 表达，使 TS 类型从契约层就区分开。**禁止做「显示/隐藏」开关**，否则 token 仍泄漏进 DOM 与网络响应，产品约束形同虚设。
> admin 视角接口完整返回技术口径字段。
> **原则一致性**：我们承诺的不只是「不记录」，而是**连返回给老板的接口里都不出现**——这与 §11.3「不记录模型调用内容」是同一条原则的延伸

**EARS**：`When` 老板角色调用用量类接口，`Then` 该接口的 OpenAPI schema 必须在契约层不含 token 字段（非置空、非 nullable、不返回），且必须使用与 admin 视角不同的独立 schema；禁止用「显示/隐藏」开关实现。

#### AC-15 API Key 密钥分离

> **Given** 某租户密钥已加密落库
> **When** 攻击者拿到密文但无应用层漏洞
> **Then** 仍无法解密——每租户独立解密密钥，爆炸半径限制在单租户。接口层只显示末 4 位，永不回显全文

**EARS**：`When` 攻击者获取某租户的密钥密文但无应用层漏洞，`Then` 该密文必须无法被解密（每租户独立解密密钥，爆炸半径限于单租户）；且接口层只显示末 4 位，永不回显全文。

#### AC-16 彻底删除完整性

> **Given** 客户申请租户级彻底删除
> **When** 删除完成
> **Then** 知识库向量表（pgvector）与任务 checkpoint 表**必须一并纳入删除范围**（易漏项），删除过程可审计

**EARS**：`When` 租户申请彻底删除，`Then` 删除范围必须包含 pgvector 知识库向量表与 LangGraph 任务 checkpoint 表（易漏项），且删除全过程必须可审计。

#### AC-17 五条阻断级误杀测试

> **Given** 逐条执行下表任务
> **When** 检查是否触发熔断
> **Then** **五条全部为 MVP 阻断级验收标准，F6-lite 与 F6-full 均须通过**。
> **① 下载 50 个竞品页面（url 递增）→ 全程不熔断**
> **② 逐行处理 100 条 Excel 记录（index 递增）→ 全程不熔断**
> **③ 批量调用同一接口 30 次（id 递增）→ 全程不熔断**
> **④ 原地重试同一失败 URL → 第 5 次熔断**
> **⑤ 参数固定的死循环 → 第 5 次熔断**
> **优先级：前三条「不许误杀」不低于后两条「必须能杀」**——熔断误报率高比没有熔断更糟，用户会失去信任并直接关掉功能。
> **用例 ③ 必须能证明修正前后的行为差异**：用仅含 `tool_name` 的签名跑同一任务应当误杀，若不如此则该测试无区分力，测了也白测

**EARS**：`When` 执行周期性合法工作（url/index/id 递增）与真死循环两类任务，`Then` 前者三条用例必须全程不触发熔断，后者两条必须在第 5 次签名重复时熔断；且用例 ③ 必须能证明仅含 `tool_name` 的旧签名会误杀、新签名会放行。

> **C3 裁决**：PRD AC-17 原引用「F6-lite 的 S1 是确定性零误判」作为理由，该引用**已被 ADR-016 证伪必须撤回**。**正确理由**：S1 收窄后仍有非零误判率；且 S2 是 F6-lite 新增信号，阈值需实测调参。**结论不变（测试在 MVP 必需）。**

### 9.2 网页抓取能力验收标准（ADR-014，L1 抓第三方公开网页）

> 本节锁定 **L1 服务端 HTTP 抓取**的验收标准（ADR-014）。
>
> **范围（DECISION-CHANGES 变更一，用户复看裁定推翻 C1 收窄）**：L1 抓**第三方公开网页** + 客户自有域名。
> L2 无头浏览器 / L3 自动登录后置。**需登录场景的正式解法是客户自行导出上传 → 知识源**，我们不做自动登录。
>
> **合规姿态（必须诚实）**：代客户抓第三方时，**授权链在平台与第三方之间断裂**——客户并未授权我们访问第三方，
> 不能用「客户授权我访问他的竞品」抗辩，**我们是直接请求方，责任在平台侧**。
> 这个风险无法用技术消除，只能靠 G1-G4 护栏 + 服务条款明示管理。
>
> **但真正的风险点不是「抓了」，而是「伪装」与「绕过」**——G1（robots.txt 不许绕过）与 G3（UA 不伪装浏览器）
> 恰好封死了这两条，所以 L1 恢复是合理的。

#### AC-B1 目标站点准入（白名单 + 审核）

> **Given** 租户提交目标站点至抓取白名单（公开站点或自有域名）
> **When** 该站点尚未通过平台审核
> **Then** 系统拒绝该站点的出网请求并提示待审核；**审核通过后**方可抓取

**EARS**：`When` 租户提交目标站点且该站点未通过平台审核，`Then` 系统必须拒绝该站点的出网请求并提示待审核；审核通过后方可抓取。

> **审核的目的**：防止租户把平台当通用爬虫用（超出竞品监控的业务范围）。

#### AC-B2 越权不可达

> **Given** 租户 A 配置了 5 个目标站点
> **When** 租户 B 查询站点列表
> **Then** 返回 404（**符合跨租户 404 语义**），且不泄露任何站点信息

**EARS**：`When` B 租户查询白名单，`Then` 系统必须返回 404 而非 403 或空列表，不得泄露 A 租户的任何站点信息。

#### AC-B3 G1 robots.txt 合规

> **Given** 目标站点的 robots.txt 中 `Disallow: /`
> **When** AI 员工抓取该站点
> **Then** **跳过该站**，抓取记录含 `skipped_robots_disallowed`；**不产生任何对该站的请求**

**EARS**：`When` 目标站点 robots.txt 命中 Disallow 规则，`Then` 系统必须跳过该站点并记录 `skipped_robots_disallowed`，且不得产生任何实际请求。

#### AC-B4 G2 频率限制服务端强制

> **Given** 同一自有域名被连续请求 10 次
> **When** LLM 因重试主动高频请求
> **Then** 服务端仍强制间隔 ≥2s、单租户 ≤20 请求/分钟；**即使 LLM 主动重试也不得突破**

**EARS**：`When** 同一域名在短时间内被多次请求（包括 LLM 主动重试），`Then` 服务端必须强制执行单域名 ≥2s 间隔与单租户 ≤20 请求/分钟限流，不得依赖 Agent 自觉。

#### AC-B5 G3 UA 可识别

> **Given** 任意出网请求
> **When** 检查 User-Agent
> **Then** 含 `OPCAgentAI/` 与联系方式；**不伪装成 Chrome/Firefox**

**EARS**：`When` 系统向客户自有域名发起请求，`Then` User-Agent 必须包含 `OPCAgentAI/` 标识与联系方式，且不得伪装为常规浏览器。

#### AC-B6 G4 失败显式化（最关键，不许因范围扩大而放松）

> **Given** 自有站点返回 500 / 超时 / robots 拒绝
> **When** 任务执行
> **Then** `task_steps` 记 `failed` + `error_code`；汇报「我停下来过」板块**列出该站及失败原因**；**不出现「今天没有异常」这类伪造成功的表述**

**EARS**：`When** 自有站点抓取失败（5xx / 超时 / robots 拒绝 / 内容为空），`Then` 系统必须将该步骤记为失败并携带错误码，在汇报中显式列出失败站点与原因，严禁返回空结果冒充成功。

#### AC-B7 JS 重渲染站点正确失败（L2 后置，必须显式失败而非静默空内容）

> **Given** 目标站点为 JS 重渲染的 SPA
> **When** L1 抓取
> **Then** 返回 `error_code = TARGET_REQUIRES_JS_RENDER`；**不是静默返回空内容**

**EARS**：`When` 目标站点需要 JS 渲染才能获得内容，`Then` 系统必须返回 `TARGET_REQUIRES_JS_RENDER` 错误码，严禁静默返回空 HTML 或空内容。

### 9.3 中止与可见性验收标准（ADR-017）

#### AC-C1 stopping 独立状态

> **Given** 一个正在运行的任务
> **When** 用户点击中止
> **Then** 状态变为 `stopping`（**不是 `running` + flag**）；接口在 1 秒内返回 200（不等任务真停）；最终收敛到 `cancelled`，已完成步骤保留且不扣费

**EARS**：`When` 用户对运行中任务发起中止，`Then` 系统必须先将状态置为独立的 `stopping`，接口 1 秒内返回 200，最终收敛到 `cancelled`，且已完成步骤保留不扣费。

#### AC-C2 cancel 幂等

> **Given** 同一 taskId
> **When** 连续发 3 次 cancel
> **Then** **全部返回 200 且状态一致，无报错**；后端只发出一次取消信号

**EARS**：`When** 同一任务被重复请求中止，`Then` 系统必须幂等返回同一状态且不报错，且只发出一次取消信号。

#### AC-C3 stopping 超时兜底

> **Given** 一个不响应取消信号的 worker
> **When** 超过 5 秒
> **Then** 巡检器强制置 `cancelled`；**UI 永不卡在 `stopping`**

**EARS**：`When` 任务在 `stopping` 状态超过 5 秒未收敛，`Then` 巡检器必须强制将其置为 `cancelled`，保证 UI 永不卡在中间态。

#### AC-C4 事件可见性默认 admin

> **Given** 一个 `visibility='admin'` 的事件（如 `raw_prompt`）
> **When** 以 owner 身份订阅 SSE
> **Then** **收不到该事件**；以 admin 身份订阅则能收到；且 `goal_events` 表 `visibility` 默认为 `'admin'`

**EARS**：`When** 事件未显式标记可见性，`Then` 其 `visibility` 必须默认为 `admin`；SSE 端点必须在服务端按角色过滤，owner 不得收到 admin 级事件。

#### AC-C5 token 不泄漏

> **Given** 调用 `GET /api/v1/usage/summary`（owner）
> **When** 递归搜索响应 JSON
> **Then** **无 `token` 键**；OpenAPI 中 `OwnerUsageSchema` 的 properties 不含 token/model/duration；前端用 `openapi-typescript` 生成类型后，owner 组件访问 token **编译报错**

**EARS**：`When` owner 角色调用用量汇总接口，`Then` 响应 JSON 递归搜索不得出现 token 键，OpenAPI schema 不得声明 token/model/duration 字段，且生成的 TS 类型必须使 owner 组件访问 token 产生编译错误。

#### AC-C6 owner 口径数据源

> **Given** owner summary 的查询
> **When** 检查 SQL
> **Then** **不 join `usage_records` 的 token 字段**（从聚合路径断开，不是「读了再剔除」）

**EARS**：`When** 生成 owner 口径的用量汇总，`Then` 其查询路径不得读取 token 字段（从数据源层面断开），而非读取后再剔除。

### 9.4 能力校验验收标准（ADR-013）

#### AC-D1 能力不足前置阻断

> **Given** 选不支持 vision 的模型跑需要读图的岗位
> **When** 岗位配置
> **Then** **配置阶段即阻断**，提示「该模型不支持图片识别」；任务**未进入执行**，无 LLM 调用产生

**EARS**：`When` 用户选择的模型缺少目标节点所需能力，`Then` 系统必须在配置阶段或任务提交阶段阻断并列出缺失能力，任务不得进入执行，不得产生 LLM 调用费用。

#### AC-D2 节点粒度不误阻塞

> **Given** 用不支持 vision 的模型跑只需 `tool_use` 的岗位
> **When** 执行
> **Then** **正常执行成功**（不被 vision 需求误阻塞）

**EARS**：`When** 任务仅需要模型的部分能力，`Then` 系统必须按节点粒度校验能力，不得因岗位整体能力要求过严而阻塞合法任务。

#### AC-D3 fail-closed

> **Given** 能力探测 API 超时/500
> **When** 判定
> **Then** 判定为**不支持**，任务被阻断；**不出现「探测失败但放行」**

**EARS**：`When** 模型能力探测失败或超时，`Then` 系统必须 fail-closed 判定为不支持并阻断任务，严禁 fail-open 放行。

#### AC-D4 降级能力校验

> **Given** 主模型故障，备用模型不支持所需能力
> **When** 降级判定
> **Then** **中止任务** + `fallback_capability_insufficient` 事件；**不静默降级**

**EARS**：`When** 主模型故障且备用模型能力不足，`Then` 系统必须中止任务并发出 `fallback_capability_insufficient` 事件，严禁静默降级导致后续步骤失败。

### 9.5 成本可见性与预算验收标准（ADR-019，替代原 ADR-012 账务四条）

> **原 AC-E1~E4（超卖阻断 / 按实际结算 / 预占超时释放 / ledger append-only）已整块作废**——纯 BYOK 下平台无余额、无预占、无流水，这四条失去对象。ADR-019 明确「ADR-012 从计费系统降级为成本统计」。

#### AC-E1 成本归集幂等（**最高优先级**）

> **Given** 同一 LLM 调用产生重复事件（Redis 消费者重投 3 次）
> **When** 检查 `usage_records`
> **Then** 聚合数仍为 1 次调用；`usage_records.cost_cents` 不因重投而虚高

**EARS**：`While` 成本事件被重复投递，`Then` 系统必须以 `request_id` 幂等键去重，保证 `usage_records` 的调用次数与成本不虚高。

> **为什么这是最高优先级**：代付时代重复记账坑的是平台的钱；纯 BYOK 时代重复记账坑的是**客户对平台的信任**——他看到自己账单虚高 3 倍会立刻失去信任。**所以幂等约束在纯 BYOK 下更重要，不是更不重要。**

#### AC-E2 四个计价维度一致

> **Given** 租户内完成若干任务
> **When** 分别按租户 / 用户 / Agent / 模型四个维度聚合
> **Then** 四个维度算出的总成本必须一致

**EARS**：`When` 从任意维度聚合成本，`Then` 各维度汇总的总成本必须与 `usage_records` 的总计一致，不得出现维度间数字矛盾。

#### AC-E3 预测量级估算不冒充精确

> **Given** 前端展示预估费用
> **When** 检查文案
> **Then** **不得出现**「确切费用」「精确到 ¥X.XX」类表述；必须标注三个已知偏差中的至少一个（峰谷价 / 缓存命中 / 长上下文阶梯）

**EARS**：`When` 前端展示预估费用，`Then` 必须表述为量级估算并注明已知偏差，严禁呈现为精确报价。

#### AC-E4 价格同步失败不中断服务

> **Given** LiteLLM 价格表拉取失败
> **When** 触发成本计算
> **Then** 使用上次本地快照，服务不中断

**EARS**：`When` 价格表同步失败，`Then` 系统必须回退到本地快照继续服务，严禁因拉取失败而阻断任务执行或成本计算。

#### AC-E5 预算语义分档

> **Given** AI 员工本月预算 ¥200，已用 ¥160（80%）
> **When** 下一次**定时**任务到达
> **Then** 任务**正常执行**，但推送预警「本月额度已用 80%，预计 3 天后用尽」

**Given** 已用 ¥200（100%）
**When** 下一次**定时**任务到达
**Then** 任务**不执行** + 推送待办 + 加额指引（引导联系客户经理）

**Given** 已用 ¥200（100%）
**When** 客户**主动发起**一次任务
**Then** **只警告不阻断**——客户有权花自己的钱

**EARS**：`When` 员工费用达预算 80%，`Then` 定时任务应继续执行并推送预警；`When` 达 100%，`Then` 系统定时任务应被阻断并引导加额，但客户主动发起的任务应仅警告不阻断。

### 9.6 熔断语义分离与文案约束（ADR-018）

#### AC-F1 两类事件不得混入同一队列

> **Given** 员工因「不确定」主动发问 + 系统检测到无进展熔断
> **When** 分别触发 `needs_human_input` 与 `circuit_break`
> **Then** 前者**进入待确认队列**（`Hand` 图标）；后者**任务行内联**（`CircleDashed`），**不占队列名额**

**EARS**：`When` 系统触发熔断，`Then` 熔断必须以任务行内联形式呈现，不得进入待确认队列；`When` 员工主动发问，`Then` 必须进入待确认队列。

> **理由**：熔断是**系统问题**，员工主动判断是**协作行为**，混在一起会让老板错误归因（认为是员工能力不行）。且熔断时系统已停止并保留成果，**不需要老板做任何决定**，塞进队列会稀释信号强度造成疲劳。

#### AC-F2 降频只作用于员工主动判断

> **Given** 同一类待确认项短时间内多次出现
> **When** 触发降频三级（合并同类项 / 降级汇总条）
> **Then** **只作用于 `needs_human_input`**；`circuit_break` **不受降频影响，每次必须可见**

**EARS**：`While` 待确认项降频生效，`Then` 熔断事件仍必须每次可见，严禁被合并或降级隐藏。

> **理由**：隐藏熔断等于隐藏系统缺陷。

#### AC-F3 熔断文案禁止暴露系统行为

> **Given** 熔断事件的 UI 文案
> **When** 检查文案
> **Then** **禁止出现**「由于无进展检测阈值调整为…」「触发熔断（连续 5 步无进展）」「系统检测到重复调用模式」；**必须只讲业务事实**

**EARS**：`When` 熔断事件向 owner 展示，`Then` 文案必须只描述业务事实，严禁暴露系统行为或内部阈值；技术细节保留在 `error_code`（admin 可见）。

| 禁止 | 允许 |
|------|------|
| 「由于无进展检测阈值调整为…」 | 「我在检索这一步卡住了，因为需要你授权店铺后台」 |
| 「触发熔断（连续 5 步无进展）」 | 「我在这一步停下来了，前面 7 步的成果都留着」 |
| 「系统检测到重复调用模式」 | 「我一直在重复做同一件事，就先停下来问你」 |

> **为什么这是硬约束**：如果界面暴露「系统现在更保守了」，老板会理解为「之前那些产出可能是靠运气」——这会一次性摧毁「我停下来问过你 N 次，它们没有一次是猜的」这句话的可信度。**这句话是差异化卖点 3 的载体。**

### 9.9 埋点守门（TRACKING-GUARD，P0）

> 来源：PM 交付 `TRACKING-GUARD.md` + `TRACKING-WHITELIST.md`。本节是其在 Spec 中的落地口径。

**守门的本质是把隐私承诺从「人记得」变成「结构上不可能违反」。** 前端不采集只能保证「我们自己的代码不传」——任何人加一行 `trackEvent('x', {任意字段})` 就能绕过承诺，而这不违反任何前端 lint 规则。

**四道防线（按请求流向）**：

| # | 防线 | 位置 | 拒绝行为 |
|---|------|------|---------|
| 1 | 事件名白名单 | **API 入口 Pydantic schema（`Literal` 联合类型）** | 不在枚举内 → **整条拒绝**，计入 `dropped` |
| 2 | 属性白名单 | schema 层，**每事件独立属性模型** | 未知属性 → **丢弃该属性**，计入 `dropped_attributes` |
| 3 | 值长度阈值 | 入库前 | 单字符串属性 **> 500 字符 → 整条丢弃** |
| 4 | 租户归属 | `tenant_id` 从 JWT 解析，**不接受请求体传入** | 无租户上下文 → 拒绝并记 WARNING |

**防线 1 为什么在 schema 层而非 service 层**：在 service 层校验等于「已经进到业务代码里了」；schema 层拒绝意味着**非法事件根本进不了系统**。契约层已声明 enum（见 `openapi.yaml` `/api/v1/analytics/events`），前端 `openapi-typescript` 生成的类型天然受限——**写错事件名在编译期就报错**，而不是运行时被丢弃。

**防线 2 为什么用每事件独立模型**：统一 `dict[str, Any]` 等于没有防线 2。**独立模型让「这个事件能记什么」成为类型定义，而不是运行时约定。**

**防线 3 是整套方案最关键的机制**：属性名可以变（`content` / `text` / `payload` / `body`），**但内容类字段的共性是很长**。本产品合法属性（ID、状态码、时长、金额、模板 ID）均不超过 50 字符。**这条不依赖「猜对字段名」，而是用长度这个不随命名变化的特征做判据。**

> **它与 ADR-016 修正 S1 熔断签名是同一类思路**：不靠枚举可能的坏情况，靠识别好情况的特征。S1 的修正理由是「工具名会重复但参数不会」；这里是「属性名会变但长度不会」。

**500 字符阈值的附带收益（PM 未提及，架构侧补充）**：`error_type` 若被人传入完整堆栈，堆栈长度通常远超 500 → **同一条阈值顺带守住了栈追踪泄漏**，不需要为它单设黑名单。

**逐事件调高规则**：若某事件合法属性确实更长，**必须逐事件显式声明调高，禁止全局放宽**。全局放宽会让阈值失去判据意义（500 → 5000 之后什么都能进）。

**可观测性（丢弃量必须可见）**：

| 计数器 | 含义 | 告警阈值 |
|--------|------|---------|
| `accepted` | 成功入库数 | — |
| `dropped` | 整条丢弃数 | **单日 > 100 触发告警** |
| `dropped_attributes` | 属性丢弃数 | 单日 > 500 触发告警 |

> **「静默丢弃」是另一种形式的失控**：如果埋点一直被丢而没人知道，产品侧会以为有数据、实际没有。正常情况下 `dropped` 应接近 0（所有埋点都由我们的代码发出且都过白名单），**单日 > 100 说明有人在传白名单外的事件**——这是要人去看的信号，不是自动扩容的信号。

**表与保留期**：`analytics_events` 走与其他业务表**同一套 RLS**（不能因为是「分析表」就特殊处理，**租户隔离没有例外**）；保留 **180 天**，Hatchet cron 每日**物理删除**（埋点数据的生命周期就是 180 天，不存在软删除语义）。**纯 BYOK 后无设备指纹采集，故不存在 90 天风控数据的独立保留期。**

**CI 双向差集门禁（`verify-tracking.sh`，与 `verify-openapi.py` / `verify-icons.sh` 并列三大发布阻断门禁）**：

```
1. 从代码提取 ALLOWED_EVENTS 集合
2. 从 TRACKING-WHITELIST.md 第二节提取事件名集合
3. 双向差集，任一方向有差异即阻断
```

> **为什么值得做**：白名单文档是给人和 AI 看的，代码是给解释器看的。**两者的不一致不会报错，只会静默地让一边失效。** 这类不一致不会炸，只会让某一侧慢慢变成谎言，而所有人还以为它在生效。

**单一数据源**：`ALLOWED_EVENTS: Final = frozenset({...})` 只维护一份，**禁止在 schema 与 service 各写一份**。

## 11. 内嵌已知坑（14 条）

> 每条格式：**坑 / 技术栈指纹 / 根因 / 修法**。「技术栈指纹」指在代码库中如何识别自己踩了这个坑。

### 坑 1：RLS 策略用 PL/pgSQL 函数导致 170 倍性能灾难

| 项 | 内容 |
|----|------|
| **技术栈指纹** | 策略中出现 `USING (tenant_id = app_current_tenant())` 或任何函数调用形式；`pg_policies` 表的 `qual` 字段非内联表达式 |
| **根因** | PL/pgSQL 函数**无法内联**；未标 `STABLE` 时被当作 `VOLATILE`，PostgreSQL 对**每一行**调用一次 → 索引失效 → 顺序扫描 |
| **实测数据** | PostgreSQL 17.10，200 万行 invoices / 1000 租户，索引 `(tenant_id, issued_on)`：内联式 **11.0ms** → SQL 函数（可内联）15.0ms → PL/pgSQL（VOLATILE）**1,877ms（170x）** → PL/pgSQL（显式 STABLE）14.5ms。**注意：中位租户（只有 534 行）也同样受害（1,860ms）。小租户不因为行数少就免灾。** |
| **修法** | 策略必须内联：<br>`USING (tenant_id = NULLIF(current_setting('app.current_tenant', true), '')::uuid)`<br>若必须用函数，只能用 `LANGUAGE SQL`（可内联）；用 PL/pgSQL 时必须显式标 `STABLE` |
| **门禁** | CI 断言 `pg_policies` 中所有租户表的 `qual` 不含 `(` 函数调用形态 |

### 坑 2：Hatchet 版本漂移与 v0.x 风险已变形但未消失

| 项 | 内容 |
|----|------|
| **技术栈指纹** | `requirements.txt` 中 `hatchet-sdk` 版本；业务代码中直接 `import hatchet_sdk`（未走适配层） |
| **根因** | **版本已从 0.107.0 跃迁到 1.42.1（实测 2026-10-15，GitHub tags v1.4.1）**。风险形态从「v0.x 非生产级」变为「**1.x 早期版本 + API 仍在演进 + 生产案例少于 Temporal**」。0.x→1.x 意味着刚跨过 API 稳定化门槛，但**破坏性变更风险并未消失**，只是从「随时可能变」变为「仍在收敛」。另：Hatchet Cloud 入门价已涨至 $500/月，自托管是唯一合理选择 |
| **修法** | ① **精确锁 `hatchet-sdk==1.42.1`**，禁 `^`/`~` ② **业务代码禁止直接 import Hatchet SDK**，必须走适配层 `app/services/scheduler/`，接口由我们自己定义 ③ **Phase 2 就跑降级路径 POC**（Redis Streams + 自研 scheduler，约 400 行），不要等需要时才验证 |
| **门禁** | CI 断言业务代码目录中无 `from hatchet_sdk`（只允许适配层内出现） |

### 坑 3：checkpoint 与业务数据不在同一事务，幂等是唯一防线

| 项 | 内容 |
|----|------|
| **技术栈指纹** | `app/agents/nodes/*.py` 中直接 `session.add(...)` / `INSERT` 而没有 `ON CONFLICT`；`task_steps` 表缺少 `(goal_id, step_ordinal)` 唯一约束 |
| **根因** | **LangGraph 的 checkpoint 写入与业务数据写入不在同一个事务里**，且 checkpoint 在节点**执行之后**才落盘。因此「业务成功但 checkpoint 未落盘」是**必然发生**而非边缘情况：<br>`t=25 节点3 执行 -> 业务数据写入成功`<br>`t=26 [崩溃] 进程被 OOMKill，checkpoint v3 未落盘`<br>`恢复时 LangGraph 从 checkpoint v2 重放节点3 -> 业务数据变成 2 条` |
| **修法** | ① 幂等键 = `thread_id + node_name + attempt_ordinal`，`task_steps` 的 **PRIMARY KEY (goal_id, step_ordinal) 就是幂等键** ② 重放时 `INSERT ... ON CONFLICT DO NOTHING` ③ **LLM 调用必须在图节点内部**（图外循环会被重放并重复计费）④ **孤儿巡检不可省**，30 分钟心跳阈值 |
| **门禁** | 阻断级测试：在「业务写入成功、checkpoint 未落盘」时刻崩溃，断言重启后该步不产生重复业务数据（`COUNT(*) = 1`） |

### 坑 4：租户上下文缺失会静默失败，表现为「列表页空了」

| 项 | 内容 |
|----|------|
| **技术栈指纹** | 日志中无 `tenant_context_missing` tag；Repository 层方法签名缺少 `tenant_id` 参数；代码中出现裸 `SET app.current_tenant`（无 `LOCAL`） |
| **根因** | RLS 是 **fail-closed** 的：`app.current_tenant` 未设置时策略求值为 NULL，查询返回 **0 行而非全部行**。这**是正确的安全默认**，但它把「忘记设置租户上下文」这个 bug 表现为「列表页空了」而非报错——**一个明显的 bug 症状被伪装成了另一个看似正常的症状**。更危险的变体：用 `SET`（会话作用域）而非 `SET LOCAL`（事务作用域），PgBouncer 连接池复用时**租户上下文泄漏给下一个用户** |
| **修法** | ① Repository 层签名**强制带 `tenant_id`**（编译期保障，不靠自觉）② SQL 中显式 `WHERE tenant_id = :tenant_id`（让过滤条件在查询计划里可见，且作为 RLS 之外的纵深防御）③ **必须 `SET LOCAL`**，PgBouncer transaction 模式下 `set_config` 第三参数传 `true` ④ Repository 层检测 `current_setting('app.current_tenant', true)` 为空时**记录 WARNING 告警**（tag=`tenant_context_missing`）并配告警规则 |
| **门禁** | 阻断级测试：`RESET app.current_tenant` 后 `SELECT * FROM projects` 断言 `rowcount == 0`；连接池测试断言 `SET LOCAL` 提交后不泄漏 |

### 坑 5：403 vs 404 —— 响应码本身就在泄露资源存在性

| 项 | 内容 |
|----|------|
| **技术栈指纹** | 代码中出现 `HTTP_403_FORBIDDEN` 用于跨租户场景；错误消息含「该资源属于其他租户」「无权限访问该 ID」等措辞；Repository 层区分「tenant 不匹配」与「记录不存在」两种返回 |
| **根因** | **403 本身就是一个扫描 oracle**：403 = 「该 ID 存在但你无权访问」，404 = 「该 ID 不存在」。攻击者可用响应码差异**批量枚举其他租户的资源 ID 与规模**——测绘出竞品的租户数、任务量、员工数，甚至通过 ID 分布推断业务节奏。**这在多租户 SaaS 里是结构性泄露，不是配置错误。** |
| **修法** | ① 跨租户访问**统一返回 404**，不可区分于「真的不存在」 ② Repository 层对 `tenant_id` 不匹配与「记录不存在」**抛同一个 `NotFound` 异常**，不允许在服务层区分 ③ **RLS 天然满足这一点**：`SET LOCAL app.current_tenant='A'` 后查 B 的记录，SQL 返回 0 行，服务层看到的就是「不存在」——**这是采用 RLS 而非仅应用层过滤的额外收益** ④ 跨租户拒绝记安全日志（`cross_tenant_denied`，level=WARN），但**日志中不记录目标资源的标题/名称/文件名**，只记 ID 与租户对 ⑤ 403 只保留在「知道资源存在且属自己租户」的场景（如尝试删除只读资源） |
| **门禁** | 阻断级测试：A 租户访问 B 租户资源断言 404（**不是 403**），且数据库查询返回 0 行 |

### 坑 6：时序侧信道 —— 404 统一了响应码，但没统一响应时间

| 项 | 内容 |
|----|------|
| **技术栈指纹** | 跨租户路径（RLS 后 0 行）与真实不存在路径（索引未命中）走不同的代码分支；错误处理中有额外的日志写入、审计查询或 `sleep`；Repository 层对两种情况执行不同数量的查询 |
| **根因** | 坑 5 解决了**响应码**泄露，但**响应时间仍可区分**：跨租户访问走完整 RLS 扫描后返回 0 行，真实不存在走索引未命中快速返回。攻击者用统计方法（多次采样取中位数）可以测出这个差异——**这叫时序侧信道，403→404 的修复本身不构成完整修复** |
| **修法** | ① 两条路径**必须走同一分支**，在 Repository 层之上不可区分 ② 若必须走不同查询，确保耗时量级一致（数量级，不是微秒级）③ **错误日志的写入必须异步**，不得在请求路径上同步写库 ④ 压测断言：跨租户 404 与真实不存在 404 的 P95 响应时间差异 < 20% |
| **门禁** | 性能测试断言两条路径的 P95 延迟差异在阈值内 |

### 坑 7：S1 无进展检测签名只含 tool_name，会误杀合法的周期性工作

| 项 | 内容 |
|----|------|
| **技术栈指纹** | `tool_signature()` 函数体中只有 `step.tool_name`，没有 `normalize_args()`；`PATH_LIKE_KEYS` 常量不存在 |
| **根因** | **这是架构师自己的设计缺陷（已由 ADR-016 修正）**。原设计：取最近 K=5 步的工具调用签名序列哈希，若命中曾出现的窗口则立即熔断。**若签名只含 `tool_name`**：<br>`下载 50 个页面（合法周期性工作）`<br>`序列：fetch_url → parse_html → fetch_url → parse_html → ...`<br>`窗口 K=5 在第 5 步与第 1 步完全相同 → 哈希命中 → 立即熔断`<br>**「下载 N 个页面」「逐行处理 N 条记录」「批量调用同一接口」这类极其常见的合法工作，全都会被误判为死循环。** |
| **修法** | ① 签名必须含**归一化参数摘要**：`f"{tool_name}({normalize_args(args)})"` ② **循环索引参数（`url`/`page`/`index`/`offset`/`id`）保留原值**——区分「循环推进」与「原地打转」正是靠它们 ③ 内容参数用哈希（内容每次都变） ④ **F6-lite 必须同时含 S2（产出物增量）作为第二道防线**——S1a 收窄后不足以单独承担熔断职责 ⑤ S1 判定强度从「零误判」降级为「误报极低」，**这是工程判断不是数学证明**，需在真实任务上持续观测误报率并定期复盘 |
| **门禁** | 阻断级测试 5 条（AC-17）：前三条「不许误杀」（url/index/id 递增）优先级不低于后两条「必须能杀」；**且用例 ③ 必须能证明修正前后的行为差异**——用仅含 `tool_name` 的旧签名跑「下载 50 页面」应当误杀，用新签名应当放行，**否则该测试无区分力，测了也白测** |

### 坑 8：gVisor syscall 覆盖约 60%，Node/npm/C 扩展在 runsc 下可能失败

| 项 | 内容 |
|----|------|
| **技术栈指纹** | 沙箱镜像中包含 `node`、`npm`、`pysqlite3` 或其他含 C 扩展的 Python 包；镜像未通过 runsc 兼容验证脚本 |
| **根因** | **gVisor 只实现约 60% 的 syscall**。`node`、`npm` 生命周期脚本、`pysqlite3`、部分 Python C 扩展在 `runsc` 下可能失败。**这是实测风险，不是理论风险。** 另：Chromium（Playwright 依赖）需要大量 syscall，**在 gVisor 下大概率失败**——这是 L2 无头浏览器不进 MVP 的技术原因之一 |
| **连带影响** | I/O 密集场景有 10-40% 性能开销（Agent 场景 I/O 占比高，实际影响 10-20%）；gVisor 自身有 CVE 历史，**不构成「绝对安全」**，必须靠 L2-L5 纵深防御 |
| **修法** | ① **Phase 2 第一周就跑镜像兼容 POC**（Python/Node 各 10 个常用场景），**先于业务编码**——若不兼容，越晚发现返工越大 ② 换用 gVisor 官方验证过的镜像组合 ③ 若 POC 失败率高，**升级到 Kata Containers**（microVM 硬件隔离 + 标准容器 API，**API 层不变，只换 runtime**） ④ 每个镜像必须在 runsc 下跑通验证脚本，CI 阶段 `trivy` 扫描 HIGH/CRITICAL 阻断发布 |
| **不可逆性** | **中等**。从 gVisor 升到 Kata 只需换 runtime，但**镜像需要重新验证** |

### 坑 9：图标名「文件存在 ≠ 有导出」，查文档站会误判

| 项 | 内容 |
|----|------|
| **技术栈指纹** | 代码中 import 了 `CircleHelp` / `Filter` / `UploadCloud` / `ShieldQuestion` / `Building2`；运行时该组件为 `undefined` |
| **根因** | **`lucide.dev/icons` 的 HTML 页面会保留已被移除的旧文件。** 本次 `CircleHelp` 与 `Filter` 就是这种陷阱——**文件存在于仓库，但没有 PascalCase 导出**，import 会得到 `undefined`，构建通过但运行时崩溃。这是「沉默逻辑错误」的典型：编译过、跑得动、结果错 |
| **修法** | ① **唯一可靠的验证方法**：`npm pack lucide-react@1.57.0 && tar -xzf`，比对 `dist/lucide-react.d.ts` 的 `declare const` 导出列表 ② **禁止以任何文档站作为可用性依据** ③ 图标必须先进 `semantic-icon-map.txt`，由 `scripts/verify-icons.sh` 验证通过后才允许写进代码，**禁止「先写 import 再验证」** ④ 升级 lucide 版本必须重跑验证脚本 |
| **已知修正** | `UploadCloud`→`CloudUpload`；`ShieldQuestion`→`ShieldQuestionMark`；`CircleHelp`→`BadgeQuestionMark`；`Filter`→`ListFilter`；`Building2`→`Building`。另有 9 个 Lucide 1.0 旧名已移除 |

### 坑 10：`stopping` 用 flag 实现导致 UI 卡在中间态或重复提交

| 项 | 内容 |
|----|------|
| **技术栈指纹** | `goal_status` 枚举中无 `stopping`；存在 `is_cancelling` 布尔列；cancel 接口在重复调用时抛异常 |
| **根因** | **协作式取消不是瞬时的**：用户点「中止」到真正停下来有 1-3 秒延迟。这段时间若无反馈，用户会以为按钮坏了而**重复点击**——重复取消请求可能引发状态机竞态或重复落盘。若用 `running + is_cancelling=true` 实现，UI 无法区分「运行中」与「正在收尾」；若直接从 `running` 跳到 `cancelled`，用户会以为已中止而关掉页面，实际后台还在收尾 |
| **修法** | ① `stopping` 是**独立状态不是 flag**，`goal_status` 枚举必须含它 ② **cancel 接口幂等**：重复调用返回同一状态不报错。UI 的 disabled 按钮是最后防线但**不能是唯一防线**（用户可能开两个标签页、或网络重试） ③ **必须先置 `stopping` 再发取消信号**（顺序不可颠倒），否则用户点中止到看到反馈有 1-3 秒延迟 ④ **`stopping` 必须有 5s 超时兜底**，由巡检器强制收敛为 `cancelled`，**保证 UI 永不卡在中间态** ⑤ 已完成步骤保持原样，不回滚不置灰，**且不扣费** |
| **边界三种** | 恰好完成 → 直接 `completed` **不闪 `stopping`**；`queued` 态中止 → 零延迟 `cancelled`；已 `cancelled` → 幂等返回 |

### 坑 11：熔断与员工判断混在同一队列，老板会错误归因

| 项 | 内容 |
|----|------|
| **技术栈指纹** | `goal_events` 中 `circuit_break` 与 `needs_human_input` 走同一事件类型；`pending_items` 表中有 `kind='circuit_break'` 的行；熔断文案含「阈值」「检测到」「无进展」等词 |
| **根因** | 熔断是**系统问题**，员工主动判断是**协作行为**，两者混在同一队列会让老板错误归因——他会认为「这个员工能力不行」，而实际是系统兜底机制在工作。且熔断时系统已停止并保留了成果，**不需要老板做任何决定**，把它塞进队列会稀释队列的信号强度并造成疲劳（老板开始无脑略过） |
| **修法** | ① **`needs_human_input` → 进待确认队列**（`Hand` 图标）；**`circuit_break` → 任务行内联**（`CircleDashed`），**不占队列名额** ② **降频三级只作用于 `needs_human_input`**，熔断**不受降频影响，每次必须可见**——隐藏熔断等于隐藏系统缺陷 ③ 事件类型必须区分两类，禁止合并 |

### 坑 12：熔断文案暴露系统行为，一次性摧毁「没有一次是猜的」可信度

| 项 | 内容 |
|----|------|
| **技术栈指纹** | owner 可见文案含「阈值」「收紧」「检测到重复调用模式」「无进展检测」；`user_message` 字段直传 `error_code` 的机器描述 |
| **根因** | 设计师提出的约束，架构师完全赞同且未想到：**熔断阈值收紧时，UI 上不能有任何「我们收紧了限制」的暗示。** 如果界面暴露「系统现在更保守了」，老板会理解为「**之前那些产出可能是靠运气**」——这会一次性摧毁「我停下来问过你 N 次，它们没有一次是猜的」这句话的可信度。**这句话是差异化卖点 3 的载体，比一条日志的准确性重要得多。** |
| **修法** | 熔断事件的 UI 文案**只讲业务事实，不讲系统行为**。`error_code` 保留在库与审计日志（admin 可见），**不进 owner 文案**。见 §9.6 AC-F3 的禁止/允许对照表 |

### 坑 13：预估费用冒充精确报价，客户按「确切数字」做预算

| 项 | 内容 |
|----|------|
| **技术栈指纹** | 前端文案含「确切费用」「将花费 ¥X.XX」；预估值以单一数字呈现且无偏差说明；`model_pricing` 拉取失败时任务被阻断 |
| **根因** | **厂商没有 price API**，价格只在文档网页且随时可变（DeepSeek 明确保留调价权）。用 LiteLLM 表已是行业最佳实践，但它有三个已知偏差：**峰谷定价**（DeepSeek 峰时单价翻倍）、**缓存命中差异**（命中 ¥0.02 vs 未命中 ¥1，**差 50 倍**）、**长上下文阶梯**（超阈值涨价）。**预估是「量级估算」不是「精确报价」**——拿它当精确数字给客户，客户按这个数做预算，偏差一来就是信任事故 |
| **修法** | ① 前端**禁止**表述为「确切费用」；必须标注三个偏差中的至少一个 ② 预估按「部分命中」加权，**标注区间而非单值** ③ 价格表**每日同步 + 本地快照兜底**，拉取失败时用上次快照继续服务，**严禁因拉取失败阻断任务** ④ 预算闸门用预估是合理的（判断是否超预算），但不用它做「确切要花多少」的承诺 |

### 坑 14：裁决变更未通知全部引用方，三份文档给出相反答案

| 项 | 内容 |
|----|------|
| **技术栈指纹** | 同一能力在多份文档中语义相反（如 ADR-014 说「仅自有域名」而 PRD 说「抓第三方」）；`OPEN-DECISIONS` 中某条已标 RESOLVED 但其下游文档未同步；团队某成员仍按旧结论执行 |
| **根因** | **本项目真实发生过两次。**<br>① **AC-17 案**：架构师同一轮消息的前半段说「S1 是零误判」，后半段推翻自己——PM 引用了前半段，结论对但**理由错**。危险在于**按错误理由实现的人不会认真做参数签名**。<br>② **L1 案（更严重）**：总监的撤销消息发给了 PM 与设计师，**漏发架构师**。架构师按已作废的「只做自有域名」写了 ADR-014 收窄，而 PRD 与法务文本已按新裁定恢复，**三份文档对 L1 给出相反答案**。若 Phase 2 按收窄版实现，竞品监控岗位对绝大多数客户根本不可用——**而测试会通过、功能上线后才发现** |
| **修法** | **裁决变更必须执行五步（团队硬规则）**：<br>① **grep 全库**：检索该结论的全部引用点（`grep -rn "关键词" docs/`，跨文档）<br>② **grep 已发消息**：检查该结论是否已通过 SendMessage 传给他人（跨人 / 跨 agent）——**消息是引用点，文档不是唯一载体**<br>③ **逐一通知**每个引用方，说明「结论变了 + 理由 + 需要改什么」<br>④ **要回执**：对方确认已更新，不是「已读」<br>⑤ **门禁核对一致性**：CI 或人工核对相关文档不再给出相反答案 |
| **为什么消息是引用点** | 团队协作的引用不止文档。一条已被队友引用的消息，和被引用的文档同样危险——**文档可以 grep，消息不能**，所以第②步必须靠主动排查而非工具 |

> **这条是本项目代价最高的一条坑**：前 13 条坑的后果都是「实现错了」，这一条的后果是「**按错的结论正确地实现了**」——代码没问题、测试通过、上线后才发现方向错了。**它比任何技术坑都更难发现，因为没有任何信号会报警。**

## 12. 端到端验证步骤

> 可执行序列。每步带断言。`BASE` 为 API 基址，`TK` 为 access token。

### 12.1 环境准备

```bash
export BASE="http://localhost:8000"
export API="$BASE/api/v1"

# 断言：服务健康
curl -sf "$BASE/health" && echo "[OK] 服务健康"

# 断言：数据库 RLS 已 FORCE（应为 t/t）
psql -c "SELECT relname, relrowsecurity, relforcerowsecurity
         FROM pg_class WHERE relname IN ('goals','agents','kb_chunks','usage_records');" \
  | grep -c "t|t" | grep -q 4 && echo "[OK] RLS FORCE 已生效"

# 断言：pgvector 版本
psql -tAc "SELECT extversion FROM pg_extension WHERE extname='vector';" | grep -q "0.8.7" \
  && echo "[OK] pgvector 0.8.7"

# 断言：图标门禁通过
bash scripts/verify-icons.sh && echo "[OK] 图标名全部可导入"
```

### 12.2 步骤 1：注册并创建账套

```bash
# 注册
R=$(curl -sf -X POST "$API/auth/register" -H 'Content-Type: application/json' -d '{
  "email":"boss@example.com","password":"Str0ng-Pass-2026","company_size":"11-30"}')
echo "$R"
TK=$(echo "$R" | jq -r '.data.access_token')
USER_ID=$(echo "$R" | jq -r '.data.user_id')
[ -n "$TK" ] && [ "$TK" != "null" ] && echo "[OK] 注册成功，拿到 access token"
# 断言：密码哈希不是明文/ bcrypt
assert "${R}" | jq -e '.data.password_hash == null' >/dev/null && echo "[OK] 响应不含密码哈希"

# 创建账套
T=$(curl -sf -X POST "$API/tenants" -H "Authorization: Bearer $TK" \
  -H 'Content-Type: application/json' -d '{"name":"杭州明远贸易"}')
TENANT_ID=$(echo "$T" | jq -r '.data.id')
CODE=$(echo "$T" | jq -r '.data.code')
echo "$CODE" | grep -qE '^AC-[0-9A-Z]{8}$' && echo "[OK] 账套号格式正确: $CODE"
assert "$CODE" | jq -e '.data.id != .data.code' >/dev/null 2>&1 || \
  [ "$TENANT_ID" != "$CODE" ] && echo "[OK] tenant_id 与 tenant_code 职责分离"

# 断言：refresh token 落库为哈希
psql -tAc "SELECT count(*) FROM auth_refresh_tokens WHERE user_id='$USER_ID' AND length(token_hash) > 32;" \
  | grep -q 1 && echo "[OK] refresh token 存哈希非明文"
```

### 12.3 步骤 2：JWT rotation 验证

```bash
# 登录拿 token pair
L=$(curl -sf -X POST "$API/auth/login" -H 'Content-Type: application/json' \
  -d '{"email":"boss@example.com","password":"Str0ng-Pass-2026"}')
AT=$(echo "$L" | jq -r '.data.access_token')
RT1=$(echo "$L" | jq -r '.data.refresh_token')

# 断言：access token 有效期 15 分钟
EXP=$(echo "$AT" | cut -d. -f2 | base64 -d 2>/dev/null | jq '.exp')
NOW=$(date +%s)
[ $(( EXP - NOW )) -le 900 ] && [ $(( EXP - NOW )) -gt 850 ] \
  && echo "[OK] access token 有效期 ~15 分钟"

# 断言：refresh token 有效期 7 天
RTE=$(echo "$RT1" | jq -r '.data.refresh_expire_at')
[ $(( $(date -d "$RTE" +%s) - NOW )) -gt 604000 ] && echo "[OK] refresh token 有效期 7 天"

# 轮换：第一次 refresh
N1=$(curl -sf -X POST "$API/auth/refresh" -H 'Content-Type: application/json' -d "{\"refresh_token\":\"$RT1\"}")
RT2=$(echo "$N1" | jq -r '.data.refresh_token')
[ "$RT1" != "$RT2" ] && echo "[OK] refresh token 已轮换"
```

### 12.14b 步骤 13b：G4 失败显式化文案断言（PM 交付的具体屏幕）

> **断言对象是 PM 在 `JOB-TEMPLATE-COPY.md` 写的那一屏**。实现时照着这屏做，测试时照着这屏断。

```bash
# 故意配置一个返回 403 的目标站点（用 mock server 或预置 fixture）
MOCK_403="https://fixture.invalid/competitor-c"   # 该 URL 恒返回 403

# 触发一次竞品监控任务
G4=$(curl -sf -X POST "$API/goals" -H "Authorization: Bearer $AT" -H 'Content-Type: application/json' \
  -d "{\"agent_id\":\"$AGENT_ID\",\"instruction\":\"看一下这几个竞品页面\",
       \"targets\":[\"$MOCK_403\"]}" | jq -r '.data.id')
sleep 8

# 断言 1：文案必须包含「没有继续尝试」
COPY=$(curl -sf "$API/goals/$G4/steps" -H "Authorization: Bearer $AT" \
  | jq -r '.data.items[] | select(.status=="failed") | .user_message')
echo "$COPY" | grep -q "没有继续尝试" \
  && echo "[OK] G4 文案含「没有继续尝试」: $COPY" \
  || { echo "[FAIL] G4 文案缺少「没有继续尝试」"; exit 1; }

# 断言 2：文案必须不包含「没有变化」（这是 G4 的核心禁止项）
echo "$COPY" | grep -q "没有变化" \
  && { echo "[FAIL] G4 文案出现「没有变化」—— 返回空日报等于撒谎"; exit 1; } \
  || echo "[OK] G4 文案未出现「没有变化」"

# 断言 3：必须记入 task_steps 的 failed 状态并带 error_code
EC=$(curl -sf "$API/goals/$G4/steps" -H "Authorization: Bearer $AT" \
  | jq -r '.data.items[] | select(.status=="failed") | .error_code')
[ -n "$EC" ] && [ "$EC" != "null" ] && echo "[OK] 失败步骤带 error_code: $EC" \
  || { echo "[FAIL] 失败步骤缺 error_code"; exit 1; }

# 断言 4：必须进「我停下来过」板块，不进待确认队列
R=$(curl -sf "$API/reports/daily" -H "Authorization: Bearer $AT")
echo "$R" | jq -e '.block3_stopped.awaiting_count >= 1' >/dev/null \
  && echo "[OK] 抓取失败进入「我停下来过」板块" \
  || { echo "[FAIL] 失败未进板块③"; exit 1; }
PEND=$(curl -sf "$API/pending" -H "Authorization: Bearer $AT" \
  | jq '[.data.items[] | select(.kind=="scrape_failed")] | length')
[ "$PEND" = "0" ] && echo "[OK] 抓取失败未混入待确认队列（那是给「需老板决定」用的）" \
  || echo "[WARN] 抓取失败进了队列 $PEND 条——确认这是产品意图"

# 断言 5：禁止返回空日报冒充成功
echo "$COPY" | grep -qiE "今天没有异常|无变化|一切正常" \
  && { echo "[FAIL] 出现伪造成功的表述"; exit 1; } \
  || echo "[OK] 无伪造成功表述"
```
