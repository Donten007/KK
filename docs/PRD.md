## 1. 产品定位

### 1.1 一句话价值主张

**给中小企业老板一个不用招人、按时上班、交不出活来自己负责的 AI 员工。**

展开说：一个普通员工入职第一天，我们要交代背景、给流程手册、盯着他干一周才敢放手。AI 员工在平台上被「配置好岗位说明书」的那一刻就已经完成入职——它按时上班（定时触发）、自己拆解任务（长任务编排）、干活留痕（可观测执行流）、干完交汇报（交付物 + 成本账单）。老板的唯一动作是：看它交了什么。

### 1.2 定位陈述（内部用，不对外投放）

现有市场把「AI 智能体」当成**开发者的工具**在卖——Dify、Coze 卖的是画布和节点，Manus 卖的是通用浏览器代理。它们的用户画像是开发者或极客，商业形态是 per-seat 订阅（Manus Team $20/席位/月，Dify Professional $590/年）。

我们把「AI 智能体」当成**老板的岗位**在卖。用户画像是中小企业老板（1-50 人，年营收 500 万-5000 万），商业形态是**按岗位编制计费的 outcome-based 订阅**——客户买的不是「几个人能用」，是「我雇了几个 AI 员工、它们替代了几个真人岗位」。

### 1.3 品类归属

不是 AI 对话工具（chatbot），不是低代码编排平台（no-code builder），是 **AI 员工的雇佣与调度平台**——对标人力资源与 RPA 采购，而非对标 AI 编程工具。

## 2. 问题陈述

### 2.1 主要问题：中小企业老板雇不到、也雇不起「能自己干完活的人」

30-80 人的中小企业（电商、贸易、制造代工、专业服务）有一个反复出现的用工结构问题：**关键流程依赖 1-2 个岗位，这 2 个人请假、离职或被竞争对手挖走，业务就断。** 这类岗位的共同特征是：流程标准化程度高（订单录入、对账、开票、客户跟进、竞品监控、周报汇总），但重复劳动多、招人难、培训成本高。

老板的三种现有应对方案全部不可持续：

| 现有方案 | 真实成本 | 为什么不行 |
|---|---|---|
| 再招一个人 | 月薪 6-8K + 五险一金 ≈ 8-10K/月（约人类员工成本的 1/1） | 招不到人；招到了也要盯三个月才敢放权；人员流失带走流程知识 |
| 外包给代运营/代账公司 | 月费 3-8K | 业务核心数据出域；响应慢（按自然日）；不做定制 |
| 用通用 AI 工具（Manus / ChatGPT / Kimi）自己顶 | 订阅 $20-40/月 + 老板自己的时间 | **不是「雇人」，是「老板自己加班」**：需要老板反复下指令、盯着进度、核验结果。实测反馈：「花 1.5 小时盯着 AI 干 15 分钟的活」（Reddit r/AI_Agents）；「以为买了个员工，其实雇了个实习生还得自己带」 |

### 2.2 次要问题：现有 Agent 平台的可靠性与成本不可控，阻塞了商业化

这是我们调研中最重要的发现，它不是「体验不好」，而是**结构性的商业阻断**：

- **通用 Agent 任务完成率（TCR）不足。** 行业投资人评分卡（2026）显示：通用型 Agent 的任务完成率典型值约 **65%**，而经过垂直领域数据训练后的专用 Agent 可达 **98%**。65% 意味着客户运营团队要自己消化 35% 的异常——「隐藏人力」会吃掉购买时算的那笔 ROI。
- **成本事前不可知。** Manus 官方帮助中心明确写着：Agent 给出的任何费用预估都应被视为幻觉（hallucination）。用户实测：一个复杂任务 500-900 积分；有用户烧掉 88,000 积分仍未完成；有人一个月内两次升级套餐只为拿更多积分。这是「不能放进财务流程的费用」。
- **长任务半成品交付。** 同一提示词两次运行结果不一致；长任务会重复步骤、丢失进度、产出不完整结果。「置信度已经宣布任务完成，却拿不出任何完成过的证据」。

**结论：中小老板不是不想用 AI 员工，是不敢把业务交给一个会烧钱、会半途而废、还说不清自己在干什么的东西。**

## 3. 目标用户画像

### 3.1 主要用户：企业决策者（老板 / 合伙人 / CEO）

| 维度 | 描述 |
|---|---|
| 年龄 / 城市 | 35-52 岁，一二线及强三线城市 |
| 公司规模 | 20-80 人；电商/贸易/制造代工/财税/跨境电商/本地服务 |
| 年营收 | 500 万 - 5000 万人民币 |
| 技术水平 | **不会写代码。看不懂 API、能看懂 Excel 和微信。** 决策周期 2-4 周，需要看到同行案例。 |
| 日常 | 早上处理消息，中午被拉进客户群，晚上被报表追。全年 200 天在「救火」和「被问进度」中度过。 |
| **痛点** | ① 关键流程挂在一个人身上，人一走就断；② 招人成本高、周期长、还带不走知识；③ 想上 AI 但不知道从哪下手，投了一堆工具没一个真正在干活；④ 最怕的不是花钱，是花的钱打了水漂还说不清花在哪。 |
| **真实诉求（原话，不是功能）** | 「我想要一个能替我盯着的人，不是一个要我伺候的东西。」 |
| **付费意愿** | **高，但要求 ROI 可当场算清。** 锚点：替代 1 个岗位 = 每月省 8K。数字员工月费只要明显低于 4K（人类成本的 1/2 以下），就有采购冲动。参照行业共识「数字员工定价通常为人类员工的 1/5~1/10」——我们主动定在 1/6~1/7，把省下的部分留成老板的确定性。 |
| **决策障碍** | 「AI 会不会胡说八道害了我」「钱会不会越花越多停不下来」「出错了谁负责」。这三条必须在产品层面回答，不能靠销售 PPT。 |

### 3.2 次要用户 A：管理员（运营负责人 / 行政 / IT 对接人）

| 维度 | 描述 |
|---|---|
| 角色 | 40% 是运营总监/行政主管，40% 是懂一点电脑的老板亲戚，20% 是兼职 IT |
| 技术水平 | 会用 SaaS 后台、能配企业微信机器人、能读懂文档；**不写代码，反感命令行和 Docker** |
| 痛点 | ① AI 工具买回来没人会用，员工不用；② 要给不同岗位配不同工具，配置成本高；③ 出错不知道找谁，供应商答「重启试试」；④ 没有统一入口管理成本。 |
| 付费意愿 | **低（不是付款人）**，但**否决权高**。他一句「这玩意没人会维护」能直接否掉老板的采购。 |
| **对他的诉求** | 「一个人管一个团队的事，而不是一个人管十种工具的事。」 |

### 3.3 次要用户 B：普通员工（被 AI 员工影响的人）

| 维度 | 描述 |
|---|---|
| 角色 | 客服、运营助理、财务助理、跟单 |
| 技术水平 | 会用微信和 Excel；不主动学习新工具 |
| 痛点 | ① 担心被替代、抵触；② 不相信 AI 的产出，不敢直接发给客户；③ 不知道什么时候该查 AI 员工的活。 |
| 付费意愿 | **无（不是付款人）** |
| **对他的诉求（反直觉）** | 他要的**不是**更多工具，而是**一个可信的复核入口**——「AI 做完我能一键核对，不对就打回重做」。这个需求进 P1，但不进 MVP（见第 9 章 Out-of-Scope）。 |

### 3.4 三类用户的关系（关键产品判断）

老板付钱，管理员否决，员工抵触。这三者的诉求**不一致且部分冲突**——这是本产品最大的产品设计难点，也是最容易被做错的地方。

我们的取舍：**MVP 阶段只服务老板 + 管理员，把「员工抵触」当作 P1 的核心问题显式记录下来，而不是假装它不存在。** 理由：老板是唯一付款人；员工的抵触最真实的解法是「让员工看到 AI 干了什么并能打回」，这需要执行流可观测能力成熟后才能做，做早了只会让员工更早看到「机器替代我」而加剧抵触。

## 4. 核心用户旅程

### 4.1 旅程总览（老板视角，首次 7 天）

```
Day 0  注册（邮箱/手机，30 秒）
  ↓   ① 平台直接问「你公司多少人」，不要求填任何配置
  ↓
Day 0  选岗位（不做空白画布，做岗位卡片墙）
  ↓   ② 点「电商订单录入」→ 看到：这个员工每天 9:00 自动做、
  ↓      交付什么、你要准备什么（一份 Excel 模板）
  ↓
Day 1  配置（3 步，不写 prompt）
  ↓   ③ 上传一份订单 Excel 作为知识源 → 填自己的 API Key
  ↓      → 填「贵司发货地址格式」
  ↓
Day 1  试跑一次（不是直接开定时，先干一次给你看）
  ↓   ④ 3 分钟看到：它分了几步、每步做了什么、交付物长什么样、
  ↓      本次花了多少钱
  ↓
Day 2  开定时（此时才允许上生产）
  ↓   ⑤ 「每天 9:00 自动执行」开关 + 到点手机/企微推送交付物
  ↓
Day 3-7 看汇报（形成习惯，这是留存的关键）
      ⑥ 每天早上收到：昨日完成 / 异常 / 待你确认事项 / 本周节省人力折算
  ↓
Day 14 雇第二个 AI 员工（按岗位复制配置，一键生效）
```

### 4.2 逐步骤详述（含成品界面文案）

#### 步骤 ①：注册后第一个问题——不问公司规模，问「你公司多少人」

**设计意图**：注册表单是转化率杀手。传统做法要填公司名、行业、规模、职位、邀请码。本产品只在注册后问一句话，且这句话**有实际用途**——它直接决定推荐哪些岗位模板。

界面文案（可直接投产）：

> 标题：`先知道一件事：你公司现在有多少人？`
> 副标题：`用来决定先给你派哪个 AI 员工，不是问卷。`
> 选项：`1-10 人` / `11-30 人` / `31-80 人` / `80 人以上`
> 按钮：`给我建议岗位`
> 底部小字：`跳过也行，直接进岗位库`

#### 步骤 ②：岗位卡片墙（替代空白画布，这是全产品最重要的设计决策）

**问题**：Dify/Coze 的入口是「新建应用」——一块空白画布。这是开发者语言，对老板是劝退。

**我们的做法**：入口是**岗位卡片墙**。老板不需要理解「Agent」「Workflow」「节点」，只需要理解「我要雇一个干什么活的人」。

卡片信息结构（每张卡片必须包含以下 5 项，这是硬性要求）：

> **顺序已调整（设计部建议，已采纳）**：「交付物」提到「上岗前置条件」**之前**。
> 理由是老板的决策心理顺序——「有没有东西交给我」比「我要先做什么」更重要。先看到「每天早上8 点给你一份竞品日报」这个产出，再看到「需要授权品牌资料库」这个门槛；反过来第一眼就是配置要求，容易被吓退。
> **「交付物」视觉权重降级为低，但位置在分隔线之后。**「交付物」必须带图标（ / ）+ 文件名，这是「真有产出物」的证据，比纯文字可信。
> **埋点影响**：若按旧顺序做，转化数据会被顺序污染。 埋点需记录用户是否展开了交付物区。

> **排序依据（设计部修正，已采纳）**：卡片顺序**不按难度，按「首次成功率」降序**。老板的第一次点击决定他对产品的信心，第一个岗位必须是他不需要任何配置就能看到产出的那个，递进才是真递进，否则是从难到易、开局劝退。
> **高难度卡片不置灰、不降透明度**——置灰会暗示「不可用」，但它们真实可用，只是需要先配置。**用边框粗细表达「需要留意」，不用透明度表达。**

| 卡片元素 | 内容示例（成品） |
|---|---|
| 岗位图标 | `订单录入图标`（文字描述，图标方案为统一 SVG 图标库） |
| 岗位名 | `电商订单录入` |
| 一句话职责 | `每天 9:00 自动把订单表录入你的 ERP，录完发你一份对账表` |
| 上岗前置条件 | `准备：一份格式固定的订单 Excel` |
| 交付物 | `ERP 录入结果 + 当日对账差异清单` |

MVP 首批 5 个岗位模板（不是 20 个，5 个足够验证）：

1. `竞品监控日报` —— L1 抓取指定公开网页 → 变化摘要 → 企微推送（**Phase 2 B 模式唯一实现岗位**）
2. `周报汇总` —— 读团队提交的表格 → 汇总成周报草稿 → 待负责人确认
3. `发票信息核对` —— 读发票影像 → 提取关键字段 → 与账目三方核对 → 输出异常清单
4. `客户跟进催办` —— 读客户自有 CRM 或表格 → 找出超期未跟进客户 → 生成话术草稿 → 企微推送待办
5. `电商订单录入` —— **客户导出上传订单文件 → 员工核对录入 → 对账差异清单**（见下方岗位 5 形态说明）

> **顺序已与 Spec §2.4 对齐。** 顺序依据是难度递进（PRD §8.2）：竞品监控（3-8 步）→ 周报汇总（3-6）→ 发票核对（8-15）→ 客户催办（5-12）→ 订单录入（20-40）。
> **「客户自有渠道数据监控」已移除** —— 它是 L1 收窄裁决期间的临时补位岗位，L1 恢复后不再需要。
>
> **【岗位 5 形态说明，架构裁定】电商订单录入在 MVP 内的形态是「客户导出上传 → 员工核对录入」，不是「自动登录 ERP 写入」。**
> 理由：自动写入需 L3 登录态，而 ADR-014 明确 L3 不做自动登录——**我们因此不承担客户账号密码的保管责任**。
> **这不是降级，是这个场景下唯一正确的做法**（与「需登录站点由客户导出」是同一个设计）。
> Phase 3 实现时**必须按「客户导出上传」做，不得按「自动写入 ERP」做。**

**文案（岗位库页）**：
> 标题：`先雇一个`
> 副标题：`5 个岗位现在可用。每个都说清楚它干什么、你要准备什么、交什么给你。`
> 空状态：`这 5 个都不合适？` + `说说你想雇个干什么的` → 提交需求，7 个工作日内回复

#### 步骤 ③：三步配置（不写 prompt）

**设计意图**：任何要求用户写 prompt 的步骤都是把开发成本转移给了客户。老板的输入应该是**文件**和**选项**，不是文字指令。

第一步 · 喂知识（上传文件，替代「学习文档」这种含糊说法）
> 标题：`给这个员工喂资料`
> 副标题：`它做判断时会翻你上传的这些文件。格式不限，Excel / Word / PDF / 图片都行。`
> 主按钮：`上传文件`
> 辅助说明：`还差 1 份就能上岗，现在还不能跑正式任务`

第二步 · 接模型（**纯 BYOK，不提供平台代付**）
> 标题：`接上大脑`
> 两个并列选项卡：
> **自带密钥**（推荐标签）
>   说明：`用你自己的 OpenAI / DeepSeek / 智谱 密钥。模型费直接付给模型厂商，不经过我们。`
>   输入框：`API Key`  + 下拉 `用哪家模型`
>   辅助说明：`密钥加密存储，我们不记录你的调用内容。随时可以在设置里换掉。`
> **纯自带密钥（BYOK），不提供平台代付**
>   说明：`用你自己的 OpenAI / DeepSeek / 智谱 密钥。模型费用直接付给模型厂商，不经过我们。`
>   辅助说明：`密钥加密存储，我们不记录你的调用内容。随时可以在设置里换掉。没有可用的密钥？请到模型厂商官网注册后获取。`
>   按钮：`填我的 API Key`

> **【产品决策变更，2026-10-15】删除平台代付，改为纯 BYOK + 线下收款**
>
> **用户原话**：「不要考虑充值问题，只要能在 SaaS 系统里做出客户公司账套号区分，可以线下收款开户」
>
> **变更后的产品形态**：
> - **模型费用完全由客户自付**，平台不经手任何模型费用
> - **客户账号开通采用线下收款**（对公转账等），SaaS 系统内以「公司账套号」区分客户主体
> - **平台零资金风险**：不存在赠送额度池、不存在透支、不存在坏账
>
> **连带删除**：原「平台代付三条风控前置条件」（代付租户熔断阈值更严 / 赠送额度与首笔充值绑定 / 赠送池总量上界）**全部作废**，因它们只对代付场景有意义。
>
> **连带作废**：PRD §8.4 的「平台代付最大成本上界 ¥5,000/月」及其三步倒推方法**一并作废**（依赖赠送额度池）。
>
> **【预算闸门的语义变化 —— 这条从成本控制变成卖点】**
>
> | | 原（代付模式） | 新（纯 BYOK） |
> |---|---|---|
> | 闸门作用 | 平台防止代付额度烧光 | **客户防止自己的 API 账单超支** |
> | 触发后行为 | 任务不执行 + 通知 | 任务不执行 + 通知 + **引导「需要更多额度请联系客户经理」** |
> | 平台资金风险 | 有（赠送池是平台成本） | **零** |
>
> **这个转变强化了卖点而非削弱它**：Manus 差评最高频就是「成本不可预期」，**而 BYOK 客户同样面临这个问题——他自己的 DeepSeek 账单也会烧**。闸门从「平台止损」变成「帮你盯自己的钱」，**用户价值感更强，平台零资金风险。**
>
> **销售话术调整**：可以说「我们不赚你模型费的钱，也不碰你的模型账户。**我们只帮你盯着别烧超。**」

第三步 · 告诉它贵司规矩
> 标题：`你们公司的规矩`
> 副标题：`这三条填完它就能上岗。留空的部分它会用通用做法。`
> 字段（3 个，全部可选，有默认值）：
> - `你们的单号长什么样`（示例默认值：`订单号 + 日期`）
> - `哪个字段用来判重`（下拉：从上传文件字段自动生成）
> - `什么情况必须停下来问你`（多选：金额超过 5000 / 客户信息缺失 / 识别置信度低于 80% / 一律不问）
>
> 按钮：`跑一次试试看`

#### 步骤 ④：试跑结果页——「干完了，你自己看」（全产品最重要的信任建立页）

**问题**：这是全行业最没做好的一页。竞品的试跑结果是一堆 thinking 日志 + 一个下载链接。

**我们的做法**：试跑结果页要回答老板的三个问题，顺序不能变：**你干了什么 → 你干了多少 → 你花了多少钱。**

页面结构（自上而下）：

**区块 A · 干了什么（步骤流水，非技术日志）**
> `订单录入` · `09:14` 开始 · `用了 2 分 18 秒` · `结论：完成 46 / 48 条，2 条需要你确认`
>
> | 步骤 | 做了什么 | 结果 |
> |---|---|---|
> | 1 读表 | 读取 `9月订单.xlsx`，识别到 48 行 | 完成 |
> | 2 查重 | 用订单号 + 日期比对 6 月以来记录 | 发现 2 条重复，暂停这 2 条 |
> | 3 录入 | 逐行写入 ERP（绕过人工，无需登录你自己的 ERP 后台） | 完成 46 条 |
> | 4 对账 | 与你的发货金额表比对 | 发现 1 条金额差异 |

**区块 B · 干得怎么样（反直觉但关键的设计）**
> `这 2 条我不敢自己处理，需要你看一眼`
> 列出 2 条待确认记录，每条给两个按钮：`按我这样处理` / `我自己改`
> 按钮：`确认完这 2 条，这批就录完了`

**为什么这段设计是关键**：老板对 AI 的信任不来自成功率数字，来自**它知道自己什么时候不该自信**。一个诚实报告「我不敢处理这 2 条」的 AI 员工，比一个声称 100% 完成的 AI 员工可信十倍。这直接对应我们给自己定的 TCR ≥ 85% 目标——剩下 15% 必须以「升级给人」的方式闭环，而不是假装不存在。

**区块 C · 花了多少钱（放在结果页，不藏在设置里）**
> `本次消耗：¥0.00（你自带密钥）` —— **平台不经手模型费用，此处显示 ¥0 是因为费用直接付给了模型厂商，不是我们免了。**
> 展开：`本次调用了 7 次模型 · 费用由 DeepSeek 直接向你收取 · 你可以在模型厂商后台看到明细`

#### 步骤 ⑤：开定时（上生产前的强制缓冲）

**设计意图**：绝不允许用户跳过试跑直接设定时。这是防止「一上线就烧掉预算」的第一道闸。

> 开关文案：`让它每天自己干活`
> 副标题：`先开着。每天 9:00 自动执行，干完推给你。跑满 3 天你再决定要不要加码。`
> 时间选择：`工作日 9:00`（默认）
> 预算上限（默认自动计算，可手调）：
> `每月最多花` `[¥200]` `[建议 ¥200，覆盖约 40 次运行]`
> 提示：`超过这个额度它会停下来问你要不要加钱，绝不自己继续烧。`

**预算闸门文案（超预算时）**：
> 标题：`预算用完了，我停下来问你了`
> 正文：`本月「订单录入」已用 ¥200 / ¥200（跑了 3 次，共 142 次调用）。我停下等你决定，不会继续花。`
> 按钮：`加到 ¥400 继续` / `下月再说`

#### 步骤 ⑥：每日汇报（留存命脉）

**设计意图**：留存不靠「功能多」，靠**每天早上有一条值得看的信息**。如果 AI 员工三天没有值得看的东西，老板就会忘记它——那时候 TCO 就失败了。

推送渠道（MVP 支持：站内 + 企业微信机器人；P1 加飞书/钉钉）：

> **9月14日 · 订单录入 AI 员工 · 昨日汇报**
>
> **老板汇报页两处数值（PM 裁定，回应设计部「拍出来的数字」质疑）**
>
> 设计部主动标注了汇报页的两个参数「没有依据，是拍出来的」，这个做法是对的——**产品该给依据，而不是让设计背锅**。PM 裁定如下：
>
> | 项 | 裁定 | 依据 |
> |---|---|---|
> | **产出条目折叠阈值** | **6 条**（维持设计部数值） |依据 PRD §4.2 用户旅程：老板在企微里每日扫读汇报的场景下，注意力窗口约在 5-7 条。**低于 6 条会造成不必要的滚动，高于 6 条会让「今天做了很多事」变成负担而非成就感。** 6 条是「成就感」与「扫读成本」的平衡点 |
> | **日期回看窗口** | **30 天**（维持设计部数值） | 依据两项：① 月度复盘的自然周期是 30 天，超出后老板不会再翻 ② PRD §4.2 定性为「每天早上花一分钟」的日常工具，而非历史档案系统。**若客户需要历史数据，走知识源留存，不依赖汇报页** |
>
> **设计部若认为 6 / 30 需调整，请给出这两个数值的用户场景反例，我重新裁定。** 但在有反例之前，这两个数按上表执行。
>
> **做完了**：`订单 48 条录入 46 条 · 与上月同期 +12%`
> **要你管**：`2 条单号重复已跳过 · 1 条金额与你表里差 ¥230`
> **我停下来过**：`9月12日 检测到 ERP 返回 500，自动重试 2 次后跳过 3 条，已记录`
> **花的钱**：`¥1.26`（今日）· `¥13.80`（本月累计 / 预算 ¥200）
> **算给你看**：`本月这个员工干掉的活，按 1 个兼职岗位估约省 ¥1,180`

最后一行是留存钩子——**把老板的语言从「AI 工具」翻译成「一个人」**。这是与所有竞品最重要的心理差异：竞品汇报「调用次数」，我们汇报「省了几个人的钱」。

### 4.3 旅程中的三个决定成败的体验断点

| 断点 | 用户当时的心理 | 产品必须做到的 |
|---|---|---|
| 岗位卡片墙 | 「我看得懂这个员工干什么」 | 每张卡片必须含「前置条件」和「交付物」，缺一不可 |
| 试跑结果页 | 「它知道自己什么时候不行，而且成本我能看懂」 | 步骤流水用业务语言（不出现 token / agent / loop）；成本必现在结果页 |
| 每日汇报 | 「这东西在替我干活」 | 汇报用「人」的语汇，不用「调用/任务/会话」的技术语汇 |

| **定价** | 社区版免费；SaaS 按数字员工个数/业务量付费，**1 个数字员工 SaaS 许可约 1-2 万元/年**；私有化入门版首年控制在 10 万以内 |
| **优势** | 屏幕语义理解能「像人一样点」，无需 API 即可打通 ERP；信创适配（麒麟/统信/飞腾/鲲鹏）；信通院等背书 |
| **实战案例强度** | 中国华电财务共享中心：92 个业务类型全覆盖，初审替代率 66%，年处理单据 25 万+ |
| **劣势** | 商业化靠销售和项目交付（免费需求诊断/方案/报价），非自助；财务/合规类场景仍需人工兜底（替代率 66% 意味着 34% 要人接） |
| **对我们的启示** | 它替我们验证了两件事：① **「1 个数字员工 1-2 万/年」是市场已验证的价格锚点**（我们定价必须低于它）② **GUI 操作类任务（点 ERP、填表单）确实是真需求**，但它的替代率只有 66%——我们的 TCR 目标定在 85%，靠的不是更狠的鼠标模拟，而是**更窄的场景 + 更好的失败处理**。 |

#### 赛道代表 C：Ema（美国，通用 AI 员工，融资 7,700 万美元 / 累计 1.4 亿）

| 维度 | 内容 |
|---|---|
| 定位 | **通用 AI 员工**（universal AI employee）：统一平台为不同职能部门配置可定制 Agent，承接 HR/IT/财务的重复流程工作；多 Agent 编排 150+ 前沿与开源模型 |
| **规模** | 50+ 企业客户，含**谷歌和微软**；两年营收增长 50 倍；净收入留存率 180% |
| **模式** | **outcome-based 定价，明确主张替代 per-seat SaaS**。客户不再买工具许可，而是买「Agent 顶了多少工作量」。CEO 原话：客户「正在摆脱对 SaaS 产品的依赖，因为这些应用越来越像一个数据库」 |
| **它的做法（关键）** | ① 强调**先部署后定制**——预制 Agent 开箱即用，不依赖昂贵的专业服务 ② **自检机制**——Agent 自己核查工作成果 ③ **敏感操作主动通知监督者**审批 ④ 定位是「能力层」，先叠加在企业现有应用之上，逐步替代 |
| **它的软肋** | 服务的是**大型企业**（谷歌、微软、PwC），客单价对应 Ema 的 outcome 定价，普通中小企业买不起；无中文市场 |
| **对我们的启示** | **它验证了我们的核心商业假设（outcome-based 替代 per-seat 是趋势），但它的客户层级 ours 够不到。** 我们做「Ema 的中小版本」：把 outcome 定价落到月费 899 元这个量级，让 30 人公司也能雇 AI 员工。 |

### 5.3 替代方案（3 个 —— 客户不买我们会买什么）

替代方案不是竞品，是**客户目前正在用、或者不作为就会继续用的东西**。要打败它们。

#### 替代方案 1：n8n（开源工作流自动化）

| 维度 | 内容 |
|---|---|
| 形态 | 500+ 节点连接器的流程自动化引擎，AI 节点是后加的 |
| **为什么客户在用它** | 同一评测中的实测记录：同一个「每天抓竞品更新」任务，n8n 用 HTTP 节点 + 调度 + AI 节点串起来**跑通度最高，连失败重试都能设** |
| **致命短板（差评来源）** | 学习曲线最陡，全是管道和扳手、没有对话感；AI 只是「凑数的」，让它做「理解内容、做判断」的事直接歇菜（实测：筛文章把广告文全选进来了）；首次打开「愣了五分钟」 |
| **我们的胜法** | n8n 解决的是「连接」，我们解决的是「判断 + 交付 + 责任」。**客户真正怕的不是流程断了，是 AI 判断错了没人负责。** |

#### 替代方案 2：ChatGPT / Kimi / 豆包等通用 AI 订阅

| 维度 | 内容 |
|---|---|
| **为什么客户在用它** | 价格极低甚至免费，会用的人已经在用了，不换的动力很小 |
| **致命短板** | **它是「你自己干活」，不是「雇人干活」。** 用它做长任务需要人反复下指令、盯进度、核验结果——「花 1.5 小时盯着 AI 干 15 分钟的活」 |
| **我们的胜法** | **同样的模型，我们的用户一个月花 899 元且不需要自己盯；他们花 40 元但周末要花 10 小时。** 我们卖的不是模型，是「我不用管」。定价页必须直接把这个对比摆出来。 |

#### 替代方案 3：RPA + 外包代运营（影刀/UiBot + 代账代运营公司）

| 维度 | 内容 |
|---|---|
| **为什么客户在用它** | 真的能用，真的在用RPA 在大量企业跑流程（发票审核、订单录入），而且流程稳定 |
| **致命短板** | ① RPA **不处理判断类任务**——页面一变就废（实测：网站改个版，抓取节点就废了）② RPA 厂商近年集体转向 AI，**传统 RPA 的维护成本上升** ③ 外包代运营**数据出域 + 按自然日响应** ④ RPA 上手仍是「懂流程」的人，不是老板 |
| **我们的胜法** | RPA 覆盖「判断」，我们覆盖「判断 + 长任务 + 交付 + 成本可见」。**RPA 的价格（数万至数十万实施费）要和我们（899 元/月）的对比写在定价页上。** |

### 5.5 定价策略调研总结（行业水位）

| 定价方式 | 代表 | 水位 |
|---|---|---|
| 按席位 | Manus Team $20/席位/月、Dify Pro $59/工作区/月、阿里云百炼 198-1398 元/坐席/月、WorkBuddy 198-316 元/人/月 | **正在被行业主动抛弃**（Ema 明确主张 per-seat 正在失效） |
| 按额度/积分 | Manus $0.005/额度、Coze 积分制、Dify 消息额度 | 主流但被用户痛恨：事前不可预估、事后说不清 |
| 按数字员工岗位 | 实在智能 1-2 万/年、硅基智能 5,500-25,000 元/标准品 | **最接近我们的形态，且客户已接受** |
| 按 outcome / 成果 | Ema（金额不公开，方向明确）、行业案例「0.5 元/次线索清洗」「10 元/份财务分析报告」「数字员工年薪为人类 1/5~1/10」 | 毛利与信任最佳，但**要求极高的 TCR 才敢承诺** |
| 项目制 | 硅基智能、实在智能私有化、绝大多数「AI 员工」公司 | 中小企业嫌贵、嫌重、嫌不透明 |

**我们的定价决策：混合制 —— 席位不限（因为员工不登录），按「岗位编制」计费，内含硬预算上限。** 理由：① 席位对 AI 员工无意义（AI 自己干活，没有人登录），按席位收费会惩罚我们的核心价值主张 ② 按岗位编制最贴合老板的采购语言（「我雇了几个人」）③ 必须内含硬预算上限——这是我们与 Manus 式「你烧吧我收你钱」模式的根本分野，也是老板敢付钱的前提。

## 6. 我们的差异化

### 6.1 差异化排序（Top 3，按「能挡住多少竞争」排序）

#### 差异化 1：成本是产品功能，不是计费副产品

**竞品的做法**：成本是一个月结账单，出现在设置页。Manus 官方说费用预估是幻觉。

**我们的做法**：预算是产品的一等公民。
- 试跑结果页必现本次费用
- 每个 AI 员工有独立月度预算上限（默认自动建议）
- 达 80% 预警，达 100% **停下来问老板**（不是静默继续，也不是静默掐断——见 §7.3 F3 的三态设计）
- 开定时前强制先跑一次，不允许跳过

**为什么这能挡住竞争**：老板的恐惧不是贵，是「不知道自己付了什么、花完了怎么办」。竞品把这件事留给财务，我们把它做进主干。**这是 Manus 差评里出现频率最高的抱怨（烧钱、无限循环烧掉 88,000 额度、一个月升两次套餐），也是我们最容易做到、竞品最难跟上的差异化——因为它需要产品价值观上承认「成本失控是不可接受的」。**

#### 差异化 2：岗位说明书，不是画布

**竞品的做法**：Dify/Coze 给空白画布 + 节点，让你自己搭。Coze 要喂三遍示例才对齐意图。

**我们的做法**：预置岗位模板，每张卡片写清「它干什么、你要准备什么、交什么给你」。5 个岗位起步，而不是让老板从零设计。

**为什么这能挡住竞争**：这是**产品形态层面的差异，不是功能数量差异**。通用 Agent 的 TCR 上不去（约 65%）的根本原因就是「意图约束无法固化」——老板说不清自己要什么，Agent 就猜。我们把意图写死在岗位模板里，等于**用产品的窄，换 AI 的准**。行业数据是垂直 Agent 可达 98% TCR，而通用 Agent 只有 65%——**这个 33 个百分点的差距，是我们这个产品存在的全部理由。**

#### 差异化 3：失败被当成交付物的一部分

**竞品的做法**：AgentGPT 撞 25 循环天花板留下半成品；Manus 死循环烧完额度无产出；硅基智能替代率 66% 意味着 34% 要人接但没人告诉老板哪 34%。

**我们的做法**：三件套
- 步骤流水用业务语言展示（不出现 token / loop / agent）
- 拿不准就停下来问（预算超限、单号重复、置信度低于阈值、金额超阈值）
- 每日汇报里明确列出「我停下来过」——这是汇报的固定板块，不是异常日志

**为什么这能挡住竞争**：直接对应我们给自己定的 TCR ≥ 85% 目标，以及人工介入率（HITL）< 2% 的行业生死线。**竞品把失败当 bug 藏着，用户发现后信任崩塌（Manus：「置信度宣布完成却拿不出证据」）；我们把失败当交付内容，用户反而更信。** 这是个反直觉但可验证的产品判断，必须在 MVP 就用埋点验证。

### 6.2 一句话差异化（对销售/官网用）

> 别人给你一个 AI 工具，你自己研究怎么用。
> 我们给你一个 AI 员工，上班第一天就能干活，花超了钱它自己会停下来问你。

### 7.2 RICE 最高的 3 个功能

| 排名 | 功能 | Score | 为什么是它 |
|---|---|---|---|
| **1** | **F2 模型接入（纯 BYOK）** | **15.00** | Effort 仅 2 人月却撑起 Reach 10 × Impact 3。没有它，产品第一天就死——用户卡在「怎么接模型」就走不了，且这是老板判断「你们靠不靠谱」的第一个技术关。且它是已决约束（纯 BYOK + 线下收款）的产品落地 |
| **2** | **F3 定时触发 + 预算闸门** | **10.80** | 「按时上班」是「雇 AI 员工」与「用 AI 工具」的唯一形态差别，也是差异化 1 的技术落点。预算闸门是这个功能里最不可省的部分——它同时是留存功能（每天早上有条信息）和风控功能（钱烧不到失控） |
| **3** | **F8 企业微信机器人推送** | **11.20** | Score 略高于 F3 名次但**排在 MVP 之后**：这不是因为价值低，而是因为**它不能脱离 F4（每日汇报）单独存在**。客户在企微里收到的一定是汇报内容，汇报做不好，推送只会把糟糕内容更快送到老板面前 |

> 说明：RICE 分数最高的不等于先做。**MVP 的排序逻辑是「依赖链顺序」**：F2（能跑）→ F6（能跑完）→ F1（知道跑什么）→ F5（知道按什么跑）→ F3（按时跑）→ F4（知道跑成什么样）。F8 依赖 F4，故 MVP 先做 F4 再做 F8。F6 的 RICE 低是因为 Effort 高（8 人月）和 Confidence 低（50%，长任务引擎是本产品最大技术风险），**但它是 P0 且必须在 MVP 落地**——没有 F6，本产品退化成 Manus，会重复它的全部差评。

### 7.3 功能详细说明（P0 五项）

#### F2 模型接入（纯 BYOK，不提供平台代付）

| 项 | 内容 |
|---|---|
| **用户故事** | 作为老板，我希望能用自己的模型密钥——**我付给模型厂商的钱我看得见，而且平台不赚这一块。** |
| **具体要求** | ① **纯 BYOK**：支持 OpenAI / Anthropic / DeepSeek / 智谱 GLM 四家，密钥加密存储（AES-256 + 每租户独立密钥），**不记录调用内容**；② **不提供平台代付，不经手任何模型费用**（2026-10-15 决策）；③ **密钥可随时更换**，切换不影响历史任务记录；④ 模型能力差异必须在 UI 上明示（不支持视觉/长上下文的模型要做任务前置校验，而不是跑到一半失败）；⑤ **预算闸门的语义是「帮客户盯自己的 API 账单」**，不是平台额度控制（见 §4.2 步骤⑤） |
| **验收标准** | Given 用户填入有效 DeepSeek 密钥，When 发起一次试跑，Then 任务使用该密钥完成且结果页显示「本次消耗 ¥0.00（你自带密钥）」+ 费用为 0 的原因说明；Given 用户未填密钥，When 发起任务，Then 系统**阻断任务**并提示「请先填入你的 API 密钥」+ 跳转密钥设置页，**不产生任何调用**；Given 密钥无效或余额不足（模型厂商侧），When 发起任务，Then 系统**在执行前**明确区分「密钥无效」与「密钥余额不足」两种原因，不笼统报「余额不足，请充值或填入自有密钥」（充值是错的建议——客户要充值的是模型厂商账户，不是我们） |
| **模型能力前置校验（架构 ADR-013 补充）** | 五个能力维度： /  /  /  / 。校验采用**双层**：数据库 `model_capabilities` 表（权威，**放数据库不放代码常量**，新模型上市运营加一行即可不发版）+ 厂商 API 探测（补充，缓存 24h）。**fail-closed**：探测失败/超时一律判为不支持——这直接对应「不允许跑到一半失败」。**按节点粒度校验，不做岗位级整体校验**（单任务可能只需 tool_use 不需 vision，岗位级过严会阻塞合法任务） |
| **降级必须校验能力** | 厂商故障切换备用模型前，**若备用模型能力不足则中止而非静默降级**。「宁可不降级」更安全——静默降级到能力不足的模型，会在跑到一半时才失败，那时用户已经付了前面几步的钱 |
| **失败/边界** | 密钥无效 / 密钥余额不足（模型厂商侧）/ 密钥权限不足 / 模型不支持所选能力（视觉、工具调用）/ **能力探测超时或失败（判为不支持，fail-closed）** / 模型厂商限流 / 模型服务不可用（需降级方案提示，见 NFR 可用性） |

#### F1 岗位模板库

| 项 | 内容 |
|---|---|
| **用户故事** | 作为老板，我希望像挑人一样挑 AI 员工——看一眼就知道它干什么、要准备什么。 |
| **具体要求** | ① MVP 上线 5 个岗位：电商订单录入、竞品监控日报、客户跟进催办、周报汇总、发票信息核对；② 每岗位强制五要素（图标 / 岗位名 / 一句话职责 / 上岗前置条件 / 交付物）；③ 每个岗位是「配置模板」（一段结构化岗位说明书：职责描述、输入来源、执行步骤、交付物格式、异常处理规则、预算建议），用户可改任意字段但默认值开箱可用；④ 岗位页需显示「有多少家公司在用这个岗位」（上线 3 个月后开始显示，早期显示会造假） |

| **岗位字段的难度基线（技术背书）** | 按「步骤数 / 外部副作用 / 熔断风险」三维：竞品监控日报（3-8 步/低/低）、周报汇总（3-6/低/低）、发票核对（8-15/中/中）、客户催办（5-12/中/中）、电商订单录入（20-40/高副作用/高风险）。**前 4 个 F6-lite 足够，只有第 5 个需要 F6-full** |
| **验收标准** | Given 新用户进入岗位库页，When 页面加载完成，Then 可见 5 张岗位卡片，每张都完整显示五要素，**无任何一张缺少「前置条件」或「交付物」**；Given 用户点击「电商订单录入」，When 进入配置页，Then 预填默认值，用户可在不修改任何内容的情况下直接点「跑一次试试看」并成功执行；Given 某个岗位模板，When 检查其配置，Then **`required_caps`、`optional_caps`、`expected_idle_steps`、`expected_total_steps` 四个字段均非空**，否则该岗位不允许上架 |
| **失败/边界** | 岗位配置文件损坏 / 岗位模板版本更新后老租户配置兼容 / 用户把配置改成无效组合 / 岗位下架时的租户迁移 / **`required_caps` 声明与实际模型能力不匹配时的 fail-closed 拒绝** |

#### F6 长任务引擎（分步持久化 + 断点续跑 + 熔断）— 本产品最大技术风险

> **本节已按架构 ADR-011 修正。原降级方案「AI 生成执行方案 + 人工逐步确认」已废弃**，理由见下方修正说明。

| 项 | 内容 |
|---|---|
| **用户故事** | 作为老板，我派一件活给它，然后关掉电脑去睡觉，明天早上看到完整结果，而不是半成品。 |
| **分期方案** | **F6-lite（MVP，1.5-2.5 人月）**：断点续跑 + 中止 + 步骤预估 + **简版熔断 = S1a（含归一化参数签名的工具序列检测）+ S2（产出物增量）双信号**<br>**F6-full（Phase 2，3-4 人月）**：四信号融合 + 软阈值人工确认 + 岗位级阈值调参<br>总量 5-6.5 人月（Breakpoint 续跑与事件流已在基础设施预算内，不重复计入）。**注意：F6-lite 不是纯砍一半，而是「S1a + S2 的精简组合」** |
| **具体要求** | ① 任务拆解为可持久化的步骤，每步完成即落盘，**支持从断点续跑**，**LLM 调用不重复计费**（AgentGPT 的核心教训：半成品必须能干净续跑）② **三层同时使用**（不是三选一）：L2 执行层 LangGraph Checkpointer 管恢复精度 + L3 业务层 `task_steps` 表管用户可见与费用归集（业务语汇粒度）+ L1 幂等键管重放正确性。**必须分两层的原因**：快照里只有 `parse` 这种图节点名，用户看不懂，而汇报验收标准要求「今天做完了 1-24 步，卡在第 25 步」且禁用技术术语；反过来只有业务状态机，恢复时不知道图执行到哪个中间态，只能整步重跑而非精确续跑 ③ 执行前给出**步骤数预估**，用户可见 ④ **无静默上限**：不设 AgentGPT 式固定循环天花板，改为无进展检测熔断，熔断后**保留全部已完成步骤并向人报告** ⑤ **熔断判定必须在下次 LLM 调用之前**，否则熔断那次 token 已花掉，违反「不产生熔断后额外费用」验收标准 ⑥ **检测窗口状态必须随checkpoint 落盘**，否则崩溃重启后归零，死循环要重复触发 N 次才熔断，每轮都是真金白银 ⑦ 每步写入事件流，供 F4 汇报消费 ⑧ 支持中止（用户主动中止，已完成步骤保留，不扣已完成部分的费用） |
| **熔断信号分层** | **S1a 工具序列哈希命中（含归一化参数摘要）**（立即熔断）/ S2 产出物增量为 0（强）/ S3 无外部副作用（中）/ S4 状态指纹（辅助，易骗过）。**MVP 实现 S1a + S2 双信号** |
| **【重要修正】S1 定义已修正（架构 ADR-016）** | 架构师推演后发现：若工具签名**只含工具名**，则「下载 50 个页面」的序列 `fetch_url→parse_html→fetch_url→parse_html…` 在窗口 K=5 内第 5 步与第 1 步完全相同 → 哈希命中 → **误判为死循环**。这会导致「下载 N 个页面」「逐行处理 N 条记录」「批量调同一接口」这类**极其常见的合法工作全部被误杀**。<br>**修正**：签名必须含归一化参数摘要，且 `url`/`page`/`index`/`offset`/`id` 这类循环索引参数**保留原值**（区分「循环推进」与「原地打转」正靠它们），内容参数用哈希。<br>**修正后的能力定级变化**：S1 从「确定性零误判」**降级为「误报极低」**。因此 **F6-lite 必须同时包含 S2 作为第二道防线，不能只靠 S1**——原方案存在验收标准无兜底的风险 |
| **软阈值用人工确认而非直接熔断** | 这是 HITL 的正确用途，也正好喂养 F4 的「我停下来过」板块 |
| **误杀测试（阻断级）** | 「下载 50 个竞品页面」这类每步产出物不同但无外部副作用的任务，全程**不能触发熔断**。**熔断系统误报率高比没有熔断更糟——用户会失去信任并直接关掉功能。** 此项进阻断级测试 |
| **验收标准** | Given 一个 40 步的任务，When 执行到第 25 步时进程崩溃，When 用户次日重新打开任务，Then **任务从第 26 步继续，1-25 步的成果和费用都保留**；Given 一个进入死循环的任务（重复工具序列哈希命中），When 触发检测，Then 系统在**下次 LLM 调用之前**停止、保留已完成步骤、推送「我卡在第 N 步，已停下」，且**不产生熔断后的额外 token 费用**；Given 用户查看一个执行中的任务，When 打开详情，Then **能看到预估总步数、当前步数、预估费用与实际费用的实时对比**；Given「下载 50 个竞品页面」任务全程无外部副作用，When 执行完毕，Then **未触发任何熔断**（误杀测试） |
| **失败/边界** | 单步超时 / 模型返回不可解析输出 / 工具（外部 API）超时或返回脏数据 / 任务总耗时超上限 / 部分步骤成功部分失败（必须**部分成功也产出汇报**）/ 用户在执行中修改岗位配置（须拒绝并说明）/ 检测窗口状态丢失（须随 checkpoint 落盘） |

> **降级方案废弃说明（架构师指出，成立）**
>
> 原降级方案「AI 生成执行方案 + 人工逐步确认」技术代价虽小（复用 `interrupt`，1-2 人周），但**效果是 HITL 率从 ≤2% 变成 100%，直接触发 §8.4 自己的 Go/No-Go 判据**。同时「雇 AI 员工」变成「AI 帮你想、你自己做」，567% 的 ROI 论证与 ¥899 对标实在智能的定价论证同时失效。
>
> **这不是技术降级，是换产品。** 已改为分期：F6-lite 做 MVP，F6-full 放 Phase 2。**断点续跑绝不能砍**——那是对撞 Manus 差评的核心能力。
>
> **岗位难度递进对F6 有利（技术背书）**：前 4 个岗位（步骤少、外部副作用低）F6-lite 足够；只有第 5 个「电商订单录入」（20-40 步、高外部副作用、高熔断风险）需要 F6-full。这给了天然节奏——**MVP 用 F6-lite 上线拿真实熔断数据，Phase 2 做电商岗位时补 F6-full。岗位排序不需要改。**

| **具体要求** | ① 支持 Excel / CSV / Word / PDF / 图片（图片走 OCR + 结构化抽取）；② **摄取过程必须对用户可见**——显示「已解析 48 行 / 识别 12 个字段 / 发现 2 处格式不一致」，而不是转圈后显示「完成」；③ 字段级识别结果需用户确认（Dify 的社区文章批评其摄取不可见，导致「测试前无法确认」）；④ 检索需支持结构化数据（Excel 按字段精确过滤），不只是语义检索 |

#### F3 定时触发 + 预算闸门

| 项 | 内容 |
|---|---|
| **用户故事** | 作为老板，我希望它每天按时自己干活，而且不管花多少钱都不会失控。 |
| **具体要求** | ① 定时类型：每日 / 工作日 / 每周 / Cron（预设为主，不开放任意表达式给非技术用户）；② 强制前置：未成功试跑过不允许开启定时；③ 每个 AI 员工独立月度预算，**默认由系统按历史任务费用自动建议**；④ 预算达80% 推送预警，达 100% 进入「待确认继续」状态（见下方三态设计）；⑤ 任务实例排队策略与并发上限（P2 调整） |
| **【P0 设计修正，2026-10-15】预算超限的三态设计** | 架构师指出：代付时代超预算返回 402 阻断是对的（**平台在花钱，有权止损**）；但纯 BYOK 下**客户花自己的钱，我们无权替他决定不能花**。这个判断成立。<br>**但不能简单改成「警告」**——因为纯 BYOK 下老板没有「充值」这个动作可点，原设计的「加到 ¥400 继续」在纯 BYOK 下是无效操作。<br>因此改为**三态**：<br>**① 未设预算（默认）** → **不阻断**。仅在预估将超月度阈值时给一次提醒：`本月你的员工已花 ¥180，预计还需 ¥60。是否设一个上限？` + [ 设上限 ] / [ 不设 ]<br>**② 已设预算且未用尽** → 正常执行，达80% 预警<br>**③ 已设预算且用尽** → **任务不执行，但必须给老板一个可执行的下一步**，文案改为：`本月这个员工的预算 ¥200 用完了，它没有继续跑。` + **[提高上限] [ 下月再说] [ 只跑这一次]** ——**第三个选项是纯 BYOK 特有的**：老板可能只想让这个任务跑完一次，而不是提高长期上限 |
| **「只跑这一次」的语义（新增，架构 ADR-019 配套）** | 该选项**必须是一次性的**，跑完即恢复为「已用尽」状态。**不允许「本次放行」变成无限放行**——那等于取消预算上限，闸门形同虚设。<br>「本次放行」需记录 `budget_override_count`，**若同一员工一个月内被放行 3 次以上，在汇报中提示：`这个员工本月触发过3 次预算放行，它的月度预算可能设得太低了`** ——**把异常暴露给老板而不是静默放行**。<br>**【总监补充】override 计数必须进审计日志**：它是**「客户明知超限仍要执行」的显式记录**，将来出现费用争议时，这是客户自己决策的证据。 |
| **验收标准** | Given 一个从未成功跑过的 AI 员工，When 用户尝试开启定时，Then 系统**阻断操作**并引导至试跑；Given 某 AI 员工本月预算 200 元已用 200 元，When 下一个定时任务到达，Then 任务**不执行**，系统推送「本月这个员工的预算 ¥200 用完了，它没有继续跑。」并给出 **[提高上限] / [下月再说] / [只跑这一次]** 三个选项（**纯 BYOK 语义，无「充值」选项**）；Given 用户选择「只跑这一次」，When 该次任务完成，Then 恢复为「已用尽」状态，**且 `budget_override_count` 累加**；Given 同一员工当月 `budget_override_count` ≥ 3，When 生成汇报，Then 显示「这个员工本月触发过 3 次预算放行，它的月度预算可能设得太低了」；Given 预算已用 160 元（80%），When 下一次任务执行，Then 执行**正常完成**但同时推送一条预警，提示本月剩余额度与预计可支撑次数 |
| **失败/边界** | 定时任务重复触发（防重）/ 上次任务未跑完下次已到（并发策略）/ 时区与夏令时 / 节假日是否跳过 / 预算耗尽但用户长期不处理（需 P1 提醒升级） |

#### F4 每日汇报

| 项 | 内容 |
|---|---|
| **用户故事** | 作为老板，我希望每天早上花一分钟就知道这个员工干了什么、要不要我管、替我省了多少钱。 |
| **具体要求** | 四个固定板块（顺序不可调）：**做完了 / 要你管 / 我停下来过 / 花的钱** + 第五块「算给你看」（人力折算）；② 汇报用**人**的语汇——禁用「调用/会话/任务/token/Agent」，用「处理/跑完/次数」；③ 「我停下来过」是固定板块而非异常日志；④ 支持按 AI 员工、按日/周/月聚合；⑤ 可导出 |
| **验收标准** | Given 一个已配置 3 个 AI 员工的租户，When 每日 09:30，Then 每个 AI 员工各收到一条汇报，四板块齐全（无异常的板块显示「今天没有要我管的」而非隐藏）；Given 某员工当日未执行（队列未跑完），When 查看汇报，Then 显示「今天没跑成，卡在第 3 步」并给出重试入口，**不得静默跳过该员工** |
| **失败/边界** | 推送渠道全部失败（需站内兜底）/ 汇报生成失败（不得阻塞第二天的任务调度）/ 单员工当日执行超 100 次（需合并为汇总，否则刷屏导致关闭通知）/ 用户已读未处理超 7 天（需升级提醒） |

## 8. MVP 范围

### 8.1 MVP 定义

**一句话 MVP**：一个中小企业老板注册后 10 分钟内，能雇一个 AI 员工（电商订单录入），喂给它一份 Excel，它第二天早上自动跑完并给他发一条汇报，汇报里有钱花了多少和哪两条要他确认。

### 8.2 MVP 范围（P0）

| # | 功能 | 是否 MVP | 说明 |
|---|---|---|---|
| F2 | 模型接入（纯 BYOK） | **是** | 不可省，否则产品跑不起来 |
| F6 | 长任务引擎（断点续跑 + 无进展熔断） | **是** | 不可省，否则会重演 Manus 的半成品差评 |
| F1 | 岗位模板库（5 个岗位） | **是** | 不可省，否则老板面对空白画布会流失 |
| F5 | 知识源上传与检索 | **是** | 不可省，否则无法基于客户私有数据工作 |
| F3 | 定时触发 + 预算闸门 | **是** | 不可省，否则只是「一次性工具」不是「员工」 |
| F4 | 每日汇报 | **是** | 不可省，否则老板不知道它干得怎么样，无法留存 |
| F7 | 待确认队列 | **降级实现** | MVP 只做「列出 + 一键确认/改」，不做工作流式审批 |
| F8 | 企微推送 | **是（简版）** | 只推汇报文本，不做交互卡片 |

**MVP 交付的 5 个岗位**（按「验证 TCR 的难度递进」排序，先做容易成功的）：

> **网页访问能力分层（用户复看后裁定：恢复第三方公开网页抓取，2026-10-15）**
>
> **裁定推翻过程与教训**：此前「MVP 只做客户自有域名」是偏保守判断。**其方法论错误是：让技术可行性反推了产品该做什么。** 技术上「只做自有域名」更安全，但商业上是错的——**竞品监控是 SMB 老板付费的核心价值感知，砍掉它等于自废武功。**
> **技术该说清代价，不该替商业做决定。**
>
> **推翻理由**：抓公开网页在中文语境下是常规商业行为（比价、竞品监控、舆情监测均属此类）。**真正的风险点不是「抓了」，而是「伪装」和「绕过」——而 G1-G4 四条护栏恰好封死了这两条。**
>
> **最终分层设计（不再是妥协，是正式产品能力）**：
>
> | 层级 | 场景 | 能力 | 实现 | 合规姿态 |
> |---|---|---|---|---|
> | **L1 公开网页** | 竞品官网、新闻页、行业资讯 | **自动抓取** | 服务端 HTTP 抓取 + HTML 解析（10-50ms，无状态） | **我们是直接请求方，责任在平台侧**（见 §16.2） |
> | **L2 无头浏览器** | JS 重渲染的 SPA 站点 | **不做** | — | — |
> | **L3 登录态系统** | 客户后台、竞品付费墙内、需要账号密码的站点 | **不做自动登录**。客户自行导出上传，员工做分析 | 客户导出文件 → 知识源 | **客户授权，风险可转移** |
>
> **关键：「需登录场景」的正式解法就是客户导出上传**，这不是降级方案，是这个场景下唯一正确的做法。**我们不做自动登录，因此不承担客户账号密码的保管责任与安全风险。**
>
> **关键认知**：竞品监控**不需要 L2**。企业官网、新闻、博客的主体内容绝大多数是服务端渲染的 HTML，L1 抓取就够；L2 只在目标是 JS 重渲染 SPA 时才需要。
>
> **L1 四条护栏（缺一不可上线，架构 ADR-014）**：
> - **G1 robots.txt 合规**：Disallow 命中即跳过，**不允许绕过**
> - **G2 频率限制**：单域名 ≥2s、单租户 ≤20 请求/分钟、全局 ≤200/分钟。**服务端强制，不靠 Agent 自觉**（LLM 会因重试高频请求）
> - **G3 UA 声明**：`OPCAgentAI/1.0 (+URL; contact=...)`，**不伪装成 Chrome**（伪装本身在很多站点 ToS 里违规）
> - **G4 失败显式化（最重要）**：抓取失败 / 被 robots 拒绝 / 内容为空，**必须进「我停下来过」板块，禁止返回空日报冒充成功**
>
> **G4 是差异化卖点 3 的直接应用**：竞品监控最危险的失败模式不是「抓不到」，而是「**抓不到但报告说今天没有异常**」——老板会据此做商业决策。**返回空日报等于撒谎。**
>
> **判据影响**：部分竞品监控会失败（目标站改版、加防护、要登录），**这是 G4 显式报告的内容不是 bug，但它会拉低竞品监控的 TCR 天花板**。故 §8.4 判据按岗位分组，外部依赖类 ≥70%。

| 岗位 | 难度 | 验证什么 |
|---|---|---|
| 1. **竞品监控日报**（**已恢复为岗位#1**，见下方网页访问分层设计） | 低 | L1 服务端抓取 + 摘要，**TCR 阈值按外部依赖类判 ≥70%** |
| 2. 周报汇总 | 低 | 表格汇总，最容易做到 95%+ TCR，作为「我们能做好」的信心基线 |
| 3. 发票信息核对 | 中 | 文档理解 + 三方比对，验证 OCR 与字段抽取 |
| 4. 客户跟进催办 | 中 | 需要业务判断，验证「主动升级给人」的机制 |
| 5. 电商订单录入 | 高 | **客户导出上传订单文件 → 员工核对录入**（非自动写 ERP）。20-40 步、高熔断风险，**需 F6-full**——放在最后做，因为它是决定项目成败的那个 |

> **MVP 排序的关键判断**：先做「文档 + 表格」类任务（准确率高、失败可恢复），最后做「外部系统操作」类任务（准确率低、失败代价高）。这样 MVP 前 4 个岗位上线时能拿到真实的 TCR 数据来支撑融资/销售，而第 5 个岗位的失败不会拖垮产品口碑。

### 8.4 MVP 成功判据（Go/No-Go）

MVP 结束后必须满足以下全部条件才进入规模化投放阶段：

> **本节已按架构 ADR-015 修正。** 原 7 条判据存在 3 处口径歧义 + 1 处无采集路径，已全部闭环（见下方修正说明）。

| 判据 | 阈值 | 来源 |
|---|---|---|
| 任务完成率 TCR（**完成且全程未经人工介入**） | **分组判定，见下表** | 行业投资人生死线，低于 75% 已是严重红旗 |
| 人工介入率 HITL | **≤ 2%** | 行业投资人生死线，5% 意味着变成「伪装成软件的外包」 |
| Agentic ROI | **≥ 300%** | （节省人力 - 订阅费）÷ 订阅费 ≥ 3 倍 |
| 新用户到「第一个 AI 员工成功跑完一次」转化率 | **≥ 40%** | 低于此说明岗位卡片墙或配置流程有问题 |
| 注册到首次成功跑完的中位时长 | **≤ 15 分钟** | 超过 15 分钟说明配置步骤太重 |
| 7 日留存（雇了 AI 员工的用户） | **≥ 40%** | 参考 SaaS 行业 30 日留存 40-60% 基线，7 日 40% 为合理下限 |
| 退款/投诉中「成本不可预期」占比 | **0** | 核心差异化，任何一例都是重大失败 |

#### TCR 按岗位分组判定（架构 ADR-014/015 修正）

竞品监控依赖第三方站点，**失败原因常在目标站（改版、加防护、要登录），不由我们控制**。对这类岗位用 85% 会导致「No-Go 但无法改进」。因此判据按岗位组独立判定：

| 岗位组 | 岗位 | TCR 阈值 | 理由 |
|---|---|---|---|
| 内部文档/表格类 | **周报汇总、发票信息核对、客户跟进催办** | **≥ 85%** | 依赖客户自有数据，结果可控 |
| **外部依赖类** | **竞品监控日报** | **≥ 70%** | **目标站改版/加防护/要登录是客观现实，不是实现缺陷。** 对此类岗位用 85% 会导致「No-Go 但无法改进」 |
| 外部系统写入类 | 电商订单录入 | **≥ 85%** | 写入类必须高标准，失败会造成业务脏数据 |

**聚合规则：每组独立判定，任一组不达标即整体 No-Go，不做加权平均。** 加权平均会导致「用一个岗位的成功掩盖另一个的失败」。

#### 三处口径歧义已修正

**① TCR 与 HITL 重复计算（原判据失效）**
原文「任务完成率（无需人工介入完成）」有歧义。若「软阈值拉人确认后完成」也算进 TCR 分子，它会同时被算进 TCR 和 HITL，**两条判据失去独立性，HITL≤2% 就失去约束力**。

明确后的归属：

| 事件 | 进 TCR 分子 | 计 HITL | 计失败 |
|---|---|---|---|
| 自主完成 | 是 | 否 | 否 |
| **软阈值拉人后完成** | **否** | **是** | 否 |
| 熔断（保留已完成步骤） | 否 | 否 | **是** |
| 失败/未执行/超时 | 否 | 否 | 是 |

**恒等式：`TCR + HITL + 失败率 = 100%`**

**② 熔断必须计失败（最易搞错的口径）**
直觉上「保留了前 3 步成果」像成功，但若把熔断算成功，**熔断率会伪装成成功率**。所以熔断一律计失败——这让熔断率成为诚实的暴露指标，而不是被藏起来的数字。

**③ ROI 的「节省人力」改为可配置参数**
原写法「节省人力」是 7 条判据中**唯一无客观数据源**的一项。改为可配置参数：

```
节省人力成本 = baseline_minutes_per_run × total_runs × human_hourly_rate_cny
Agentic ROI  = (节省人力成本 - 订阅费) ÷ 订阅费
```

两者都是数据不是代码常量，且**租户可配**（客户比我们更清楚自己员工时薪）。意义在于：**ROI 变成客户自己算的账，不是我们单方面的承诺**，同时降低法律风险（我们不再替客户断言「省了多少钱」）。

#### 判据 7 的采集路径缺口（唯一需改产品流程的一条）

**「成本不可预期投诉占比 = 0」当前没有任何采集路径**——客服不打标则永远是 0，会**假通过**。这是 7 条里唯一必须改产品流程才能满足的判据：

- 退款/投诉原因改为**结构化枚举**，须包含「成本不可预期」选项
- **该字段对客服不可编辑**（防止事后美化）
- 落地位置：F8 企微推送同级的客服 SOP，Phase 2 需同步给客服团队

#### 观测窗口

TCR / HITL 的观测窗口**≥ 2 周，不看首日**——外部依赖类岗位的失败率随时间波动，首日数据不具代表性。

## 9. Out of-Scope（MVP 明确不做，防范围蔓延）

> 本章是防蔓延清单。任何新增需求必须先回答「为什么不能进 MVP」。

### 9.1 形态类（明确不做）

| 不做 | 理由 |
|---|---|
| 桌面客户端 / Tauri 壳 | 已决 SaaS 形态。桌面端在 Phase 1 不做（OPEN-DECISIONS 已登记为待架构师确认项，未关闭前不排期） |
| 私有化部署 / 本地数据完全不出域 | 已决云端 SaaS 优先，私有化作为 v2 增量 |
| 移动端原生 App | Web 响应式够用。老板在手机上看汇报的场景用企微推送解决，不需要 App |
| 插件市场 / 技能市场 | v2。MVP 阶段岗位模板由我们定义，不开放第三方 |

### 9.2 能力类（明确不做）

| 不做 | 理由 |
|---|---|
| 多 Agent 协作 / Crew 编排 | 我们刻意走「窄而准」路线（差异化 2）。多 Agent 是通用 Agent 路线，我们不碰 |
| 可视化流程画布 | 一旦做成画布，产品就退化成 Dify/Coze，且老板不会用 |
| 用户自己写 prompt / 写代码 | 老板的核心约束。允许写 prompt 会让「不用伺候」的价值主张崩塌 |
| 通用浏览器代理（操作任意网站） | 这是 Manus 的做法，差评集中在无法预测成本与验证码死循环。**我们不做任意网页操作，只做明确定义的业务系统动作** |
| 语音/电话/数字人 | 硅基智能的主战场，依赖硬件与线路成本，不适合我们的自助 SaaS 形态 |
| 代码生成 / 网页搭建 | Manus 的 web-app 卖点。评测明确指出交付物「像 2005 年做的」，且不可维护 |
| 图片/视频生成 | 与「雇员工干活」无关，范围蔓延第一大来源 |

### 9.3 商业类（明确不做）

| 不做 | 理由 |
|---|---|
| 按席位收费 | 席位对 AI 员工无意义（AI 自己干活没人登录），按席位收费会惩罚核心价值主张 |
| 年度长合约 / 预付年费 | 中小企业业务波动大，强推长约会杀死早期转化。行业避坑指南明确指出「强制长合约」是主要雷区 |
| 私有化实施 / 定制开发服务 | 项目制会让我们变成硅基智能（客户集中度 64.4%、3.5 年亏 3.19 亿）。**我们刻意不做项目制** |
| 训练自有大模型 | 无必要。BYOK + 多模型路由已是行业标准，成本结构更健康 |
| 广告 / 数据变现 | 与数据主权承诺冲突，会摧毁信任 |

### 9.4 需求类（记录但明确不做）

| 不做 | 理由 |
|---|---|
| 「AI 帮我写一条视频脚本」 | 这是通用 AI 工具该做的事，不是「雇员工」。混进来会让产品定位模糊 |
| 「AI 帮我做个人日程管理」 | C 端场景，不是 B 端雇员工 |
| 「让我自己搭一个新岗位」 | F15，v3 再议。MVP 只做 5 个预置 |

## 10. 定价方案建议

### 10.1 定价决策的三条原则

1. **计费单位 = 岗位编制**，不是席位，不是 token。理由：AI 员工自己干活，没人登录；老板的采购语言是「我雇了几个人」。
2. **必须内含硬预算上限**。这是我们敢收订阅费的前提，也是与竞品最大的分野。
3. **锚定人力成本，不锚定算力成本**。定价必须明显低于被替代岗位的人力成本，且在页面上把这个对比摆出来。

### 10.2 三档定价方案

#### 档位 1：试用版 —— 「先雇一个看看」

| 项 | 内容 |
|---|---|
| **价格** | **¥0 / 月**（免费 14 天，或长期免费版每月 500 次调用额度，二选一由架构师评估成本后定） |
| 岗位编制 | 1 个 AI 员工（仅限试用岗位列表中的 2 个：竞品监控日报、周报汇总） |
| 执行次数 | 500 次任务执行 / 月 |
| 模型接入 | **纯 BYOK（客户自带密钥）** |
| 知识源 | 3 个文件 / 200MB |

| 汇报 | 每日汇报，无人力折算 |

| **设计意图** | **免费版必须能真的干完一件事**，不能阉割成「能注册不能干活」。行业避坑指南明确警告「低价引流、核心能力阉割」是最需要避开的陷阱。试用岗位只选 2 个低难度岗位，因为免费用户不承担失败成本，我们不能让他第一次就撞上高难度的 ERP 录入 |

| 定时 | 全部类型（每日/工作日/每周/Cron） |
| 预算闸门 | 支持，默认上限 ¥500/月，可自调 |
| **预算校验落点（架构 ADR-012 补充）** | 落点是**任务调度器（Hatchet worker 任务入口）**，不是网关、不是图内部。理由：网关不知道预估成本（那是 Planner 在图内部算的），图内部只能作第三道防线防跑超。四道校验各管一段：网关查余额>0（快速 402，不写库）→ 调度器查 `balance - reserved >= estimated`（**权威，写预占**）→ 图节点循环累计/预估>80% 预警 → 累计≥预估×1.5熔断 |
| **防超卖机制** | **预占-确认-释放两阶段账本 + PostgreSQL `SELECT...FOR UPDATE` 行锁**。超卖本质是 read-then-write 竞态，**唯一解法是把「校验+预占」放进一个数据库事务**。三条硬规则：① **权威账务必须在 PostgreSQL，不能用 Redis 计数器**（AOF 每秒刷盘，宕机丢一秒账务，这是钱的账不能容忍）② **settle 按实际扣不按预占扣**，差额自动退回，不多扣客户 ③ 预占带 `expires_at` 超时自动释放，防进程崩溃后额度被「幽灵任务」永久冻结。**明确不引入 Redis 分布式锁做预占**——DB 行锁是唯一权威，Redis 锁在网络分区/主从切换时可能失效 |
| **账本append-only** | `credit_ledger` 必须 REVOKE UPDATE/DELETE，与审计日志同等级别。**账务流水可篡改 = 账务系统不可信** |
| 汇报 | 每日 + 周报聚合 + 人力折算 + 导出 |
| 企微推送 | 支持（3 个群） |
| 员工查看 | 支持 3 个只读成员（让管理员能看，不占编制） |
| **定价论证** | ① **对标锚点**：实在智能 1 个数字员工 SaaS 约 1-2 万/年（即 ¥833-1,667/月/人）。我们 3 个编制 ¥899/月 = **人均 ¥300/月，比实在智能低 55%-64%**，用价格差直接抢客户 ② **ROI 论证**：3 个 AI 员工替换 1 个兼职岗位（月成本约 ¥6,000），则 ROI =（6000×3 - 899×3）÷（899×3）= **567%**，远超行业生死线 300% ③ **人力锚点**：¥899/月 ÷ ¥6,000 = 人类成本的 **15%**，落在「1/5~1/10」的稍保守区间内，留出客户的安全感 ④ **防竞争**：低于扣子企业版 980 元/月（且我们 3 个编制 vs 它 5 席起）、远低于 CrewAI 的 $6,000/年 |

### 10.3 销售话术禁用清单（砍功能的连带义务，硬规则）

> **产品边界变更必须同步销售口径。** 销售若用旧承诺签单，账由交付来还。
> **本清单与 §11.3「禁止说我们不采集 IP」并列，同属P0 级约束。**

用户已拍板 MVP 全砍方案 A，多个能力在 MVP 不存在。销售**不得**对客户承诺以下能力：

| 禁止承诺 | 实际状态 | 允许的替代表述 |
|---|---|---|
| 「支持多员工协同 / 多 Agent 协作」 | 已砍 | 「你现在可以雇多个 AI 员工，各自负责不同岗位」（**多个独立员工 ≠ 协作**，这句表述不越界） |
| 「员工可以自动操作任意网站」 | 已砍 | 「员工可以处理你上传的数据，并在你授权的系统内执行明确动作」 |
| ~~「自动盯竞品 / 自动监控竞争对手」~~ | **已恢复为允许表述**（2026-10-15，公开网页抓取恢复） | **允许**：「在你的员工设定里配置要盯的站点，它每天按时去查，有变化主动告诉你」（G1-G4 护栏已就位，风险可控） |
| **「自动登录竞品后台 / 需要账号密码的站点」** | 不做 | 「**需要登录的站点你导出上传，员工帮你做对比分析**」——这是需登录场景的**正式解法**，不是降级 |
| **「自动操作任意网站」** | 不做（仅做明确定义的公开页抓取） | 「它会按时去看你指定的公开页面并总结变化」——**不承诺任意网站可操作** |
| 「支持无头浏览器 / 绕过网站限制」 | 已砍 | 不提 |
| 「支持语音客服 / 电话机器人 / 数字人」 | 已砍 | 不提 |
| 「员工能生成图片和视频」 | 已砍 | 不提 |
| 「员工能写代码 / 能搭网站」 | 已砍 | 不提 |
| 「有可视化编排画布，可自己拖拉搭建」 | 已砍 | 「你从岗位模板开始，配置你公司的规矩」 |

**判断准则（给销售的简易自检）**：
> **这句话描述的是 MVP 真实存在的能力吗？** 如果它出现在 §9 Out-of-Scope 里，就不能说。

**为什么这条比「砍掉什么」更重要**：砍功能是减法，成本可见；说错话是信任透支，成本不可见且不可逆。**销售口径不一致造成的预期落差，最终由交付和退款承担。**

### 10.3 定价页必须写的内容（防客户疑虑）

定价页不是价格表，是**疑虑清除工具**。必须包含：

1. **直接对比表**：
   - 我们 ¥899/月 3 个 AI 员工 vs 扣子企业版 ¥980/月 5 席 vs 实在智能 ¥833-1,667/月 1 个数字员工 vs CrewAI $6,000/年 vs 自己招人 ¥6,000/月
   - 一句话结论：`招一个人 ¥6,000/月，我们 ¥899/月管三个岗位，且不用请假不用离职。`
2. **成本不可超的承诺（大字）**：`每个 AI 员工有独立月度预算上限。花了上限它就停下来问你，绝不自动继续扣钱。`
3. **ROI 自助计算器**：输入「你公司现在几个人 / 最想替代哪个岗位」，实时算省多少钱。**必须让客户自己算出我们帮他省钱，而不是我们告诉他我们帮他省钱。**
4. **TCR 承诺与人工兜底**：公开我们过去 90 天的真实任务完成率（目标 ≥85%），并写明未完成部分的处理方式。行业数据显示「隐藏人力」是杀死 ROI 的头号原因——**公开数字比承诺 100% 更可信**。
5. **明确不做的钱**：不强制年约、不售存储、不售硬件、不做驻场实施。列出这四条，避免与「低价引流、隐性消费、强制长合约、需技术团队运维」四大行业陷阱产生联想。

### 11.3 数据埋点方案（MVP 必做）

**不埋点 = 上线后无法验证产品假设。** 本产品的核心假设有三个（成本透明会不会带来信任？岗位模板能不能把 TCR 提到 85%？预留能不能留住人？），每一个都必须有数据支撑。

| 事件类别 | 必埋事件 | 说明 |
|---|---|---|
| **获客** | `signup_complete`, `company_size_selected`, `job_template_viewed`, `job_template_selected` | 老板从哪来、看了几个岗位才选、最终选了哪个岗位 |
| **激活** | `agent_created`（首次）, `first_run_submitted`, `first_run_completed`, `first_report_viewed` | **激活定义：首个 AI 员工首次成功跑完 + 老板查看了汇报**。这三个事件缺一不算激活 |
| **留存** | `session_start`, `owner_report_viewed`（老板看汇报）, `admin_usage_viewed`（管理员看用量）, `daily_report_clicked`, `agent_switched`（在多个 AI 员工间切换） | DAU/MAU、汇报打开率（**这是我们最重要的留存指标**）。**两个报告视图必须分开埋点**，否则无法衡量老板是否真的在用汇报页 |
| **核心假设验证** | `task_completed`, `task_escalated_to_human`, `escalation_resolved`（人工确认完成，与前者配对统计）, `task_failed`, `task_resumed_from_checkpoint`, `task_circuit_broken`（熔断）, `budget_warning_triggered`, `budget_exhausted`, `cost_viewed` | 直接产出 TCR、HITL、熔断率、预算触发率四个 MVP 判据指标，**并支撑「本月停下来问过你 N 次」信任闭环指标（真实数据，禁止硬编码）** |
| **转化** | `pricing_page_viewed`, `upgrade_click`, `subscription_started`, `agent_second_created`（雇第二个）, `credit_purchased` | 付费漏斗 + 「雇第二个」这个最强的续费/扩张信号 |
| **异常** | `error_occurred`, `model_fallback_triggered`, `key_invalid_detected` | 前端错误 + API 错误 + 降级触发 |

**埋点实现要求**：
- 前端用轻量自建 `trackEvent()` 封装（**不引入第三方 SDK，避免数据主权承诺被打脸**）
- 事件命名规范：`{对象}_{动作}`，全小写（示例：`agent_created`、`task_escalated_to_human`、`budget_exhausted`）
- 属性规范：每个事件附 `user_id`（租户内 ID，非个人身份信息）、`tenant_id`、`timestamp`、`agent_id`、`device`、`version`、`job_template_id`
- **隐私红线（2026-10-15 简化，删除平台代付后不再需要分层）**：
  - **不采集 IP 地址**（全场景，无例外）
  - **不采集 User-Agent**
  - **不存储原始输入内容**
  - **不上报文件名与文件内容**
  - 埋点实现必须与「不记录模型调用内容」的技术方案一致，**否则我们对客户的承诺就是假的**。
  - **本次简化说明**：此前因代付风控需要设备指纹，隐私条款被迫做分层表述（产品分析不采 / 风控层采集）。**删除平台代付后，风控需求消失，「不采集 IP」恢复为一条无例外的绝对承诺。** 给销售的统一表述也回归最简版本。
- **埋点实现补充约束（架构补充）**：① `trackEvent` 必须在**后端过滤后**才入库——前端不采集不够，后端只接受「事件名 + 属性白名单」，未知属性一律丢弃 ② 事件表走 RLS，保留 180 天 ③ 禁记 IP / UA / 原始输入 / 文件名
- **成本准确度不埋点（架构建议，已采纳）**：§8.4 Go/No-Go 要评估成本预估准确度，但**无需新增埋点事件**——直接从 `usage_records` 表算「预估 vs 实际」，数据已在库里，埋点是冗余的
- 关键漏斗需支持按 `job_template_id` 下钻——因为我们按难度递进上线 5 个岗位，必须能对比不同岗位的 TCR 来决定哪些岗位继续做、哪些砍掉

> **术语禁令的适用范围（设计部提出，已澄清）**：
> **禁止技术词汇的界面** = 试跑结果页、老板汇报页（`/`）、待确认队列、岗位卡片墙——**即老板会看到的全部界面**。
> **不受禁令约束的界面** = 管理员用量页（`/settings/usage`）、任务中心技术抽屉、设置页。这些界面的使用者是管理员与技术角色，**需要技术词汇才能工作**。
> **判据一句话**：**老板看不到的地方用老板的词，老板看到的地方不许出现技术词。**
>
> **一、试跑结果页禁止出现「Token」字样**。理由不是文案问题，是**认知分类问题**：老板一旦看到 Token 就会把产品重新归类为「开发工具」，而我们卖的是「员工」。**归类一旦形成，他对价格的容忍度会骤降**——他会拿工具的价格基准来比，而不是拿「一个市场专员」来比。
> **成本不作为独立区块，而作为一句嵌入式业务结论**：主数字是「单次成本 + 推算月度成本」，因为**老板的决策单位是「月」不是「次」**。金额用正文字体不用等宽（等宽数字=账单感），明细收进二级入口。
>
> **一之二、数字对齐纪律的分层（设计部提出，PM 采纳）**：
> **同一个数字在两种语境下需要两种处理方式**，不可一刀切：
> - **成本结论句**（「本月约 36 元」）→ 用正文字体（font-body）。**理由：避免账单感**
> - **成本构成列表**（18.40 / 12.10 / 5.50）→ 用等宽字体 + tabular-nums + **右对齐**。**理由：老板需要纵向比对大小，非等宽无法比对**
>
> **本条必须落UIUX.md**：此前这条分层只存在于设计部判断中，若 Phase 2 实现者只看到「金额不用等宽」就一刀切，成本构成列表会失去可比对性。**「精密仪器」的第四个杠杆是数字的对齐纪律，前三个是1px 边框、等宽字体承载标识类信息、强调色每屏 ≤2 处。**
>
> **二、待确认队列三条界面硬约束**：
> ① **禁止使用  /  作为容器色，禁止告警图标**，改用 （举手）。这是本产品**唯一会被「非故障」触发的红色/黄色场景**——一旦建立「红色=有问题」的映射，老板看到红色就紧张，而这条队列不是问题，是协作。**用红色会让一个正向设计变成信任负债。**
> ② **每条待确认项必须含「依据」行**（引用具体文件与位置）。这是把「它不确定」转成「它查过且发现了矛盾」的唯一手段——**没有依据行，问问题就等于甩锅**。老板判断「这员工行不行」的标准不是它问了什么，是它**问得对不对**。
> ③ **禁止把「跳过」做成与「按我这样处理」同等视觉重量**——那会暗示跳过是正常路径，鼓励无脑略过，把信任机制变成噪音源。

> **折算基准的三条 UI 落法（设计部提出，PM 全部采纳）**：
> ① 折算时长用 font-body 不用等宽（它是结论不是计量，同数字对齐分层）
> ② **必须显示基准值与可配置入口**：「相当于省下 31 小时人工 · 按你的设定：每批发票约需 12 分钟人工 → [ 调整 ]」。**理由：不显示基准的折算等于编造**
> ③ **未配置基线时**：「配置你的人工基准后可看到折算时长」+ [ 去配置 ]，**禁止用典型值估算**
>
> **【汇报页「算给你看」折算人力口径（PM 补，此前只在对话中定过，未落文档）】**
>
> 汇报页板块④「相当于：市场专员今天省下约 2 小时 40 分钟」的折算口径必须明确，否则**实现方会自己编一个公式**：
>
> ```
> 折算人力（小时）= (人工基线分钟数 × 本期运行次数) ÷ 60
> 其中「人工基线分钟数」= baseline_minutes_per_run，是租户可配参数，不是代码常量
> ```
>
> **为什么必须是租户可配**：老板比我们更清楚自己员工处理一批发票要多久。**我们替客户断言「省了多少时间」有法律风险，因为那是他自己的数。** 这与我把 ROI 改为 `baseline_minutes_per_run × human_hourly_rate_cny` 租户可配是同一个理由。
>
> **三条硬约束 [P0]**：
> ① **必须从真实执行记录聚合**，禁止用「典型值」估算
> ② **必须显示基准值与配置入口**（同周报落法②），**不显示基准的折算等于编造**
> ③ **未配置基线时不显示折算**，改为「配置你的人工基准后可看到折算时长」+ [ 去配置 ]
> ④ **`baseline_configured=false` 时前端必须显示配置引导，禁止显示 0**（架构 ADR-019 补充）——**因为 0 会被老板读成「这个员工一点时间都没省」，那与事实相反且损害更大**。这是「链路上一环造谣整条链都不可信」在展示层的具体形态
>
> **为什么这三条是 P0**：折算人力处于老板采购决策的依据链末端（成本 → 折算人力 → ROI）。**链路上一环造谣，整条链都不可信。** 理由与信任闭环那句禁止硬编码同源。
>
> **三、信任闭环指标（差异化卖点 3 的量化载体）**
>
> **日维度主句**：首页汇报区展示「本月你的员工停下来问过你 27 次，每次你都做了决定。它们没有一次是猜的。」
>
> **【P0 修正，设计部发现】周维度不得沿用同一句式**：
> 若本周问 8 次而老板只处理了 5 次，**「每次你都做了决定」字面上就是假的**。信任指标一旦被发现不实，杀伤力远大于不做。
>
> | 条件 | 主句 |
> |---|---|
> | **全部已处理** | 用完整句式：「本周停下来问过 8 次，每次你都做了决定。它们没有一次是猜的。」 |
> | **有未处理项** | **必须改写**为「本周停下来问过 8 次，其中 3 次还在等你。」——**不保留「每次你都做了决定」** |
>
> **配套约束**：
> ① 未处理项**禁止用 `--success` 绿色**，未解决的事不该是成功的绿
> ② **统计区间 = 本周新增 + 期末仍未处理**，不是仅本周新增
> ③ **周维度比日维度更严格**：日维度样本小、不易被逐条核对；周维度样本大，**老板更可能去数**
>
> **积压板块同理 [P0]**：若老板每天处理 1 件、每周新增 8 件，**日报每天显示「1 件」看起来可控，周报显示「5 件积压，最早已等 3 天」才是真实信号**。**日清模式会系统性掩盖慢性问题。** 积压必须显示最早一件的等待天数（等待时长是升级信号），禁止折叠。
> 这把「停下来问」从「系统不够智能」重新框定为「系统很可靠」，是本产品最重要的**语义重构**。
> **数据真实性硬要求**：该数字**必须来自真实事件流统计**（task_escalated_to_human 与 escalation_resolved 配对计数），**禁止硬编码、禁止取整凑数、禁止在无数据时编造**。当月为 0 次时显示「本月你的员工没打断过你，说明它拿得准」——**不用空洞的庆祝文案**。
>
> **【停下原因三分类（正式定义，此前仅存在于总监消息与 UIUX，2026-10-15 补入 PRD）】**
>
> 汇报页板块③「我停下来过」与待确认队列的**统一分类口径**。日报与周报必须一致。
>
> | 分类 | 含义 | 典型文案 | 归入事件 |
> |---|---|---|---|
> | **我需要你定** | AI 遇到**需要业务判断**的分歧 | 「两条记录对不上，你按哪个算？」 | `needs_human_input` |
> | **我卡住了** | 执行受阻（含**熔断**、缺权限、数据源异常、robots 拒绝） | 「我在检索这一步卡住了，因为需要你授权店铺后台」 | `circuit_break` |
> | **预算用完了** | 预算闸门触发（仅当用户设过预算） | 「本月这个员工的预算 ¥200 用完了，它没有继续跑。」 | `budget_exhausted` |
>
> **两条关键约束**：
>
> **① 熔断归入「我卡住了」，不单独成一类。**
> 理由：熔断是系统问题，但呈现给老板时它就是「这件事我没做完」——归入「我卡住了」符合老板的认知框架。**且文案只讲业务事实不讲系统行为**，严禁出现「由于无进展检测阈值调整为…」「S1 信号命中」这类系统术语（老板不需要知道熔断是怎么判定的）。
>
> **② 三类在 UI 上必须分开显示，熔断走任务行内联，不占待确认队列名额。**
> 理由：熔断是「这个任务失败了」，待确认是「这个任务在等你回答」，**两者的用户动作不同**（前者可能重试，后者必须回答）。架构侧已明确 `needs_human_input` 与 `circuit_break` 是两类事件，**禁止合并**。
>
> **周报口径补充（P0，设计部提出，总监裁定）**：
> **周维度样本量不足时不判定**——若某周只问 3 次其中 2 次熔断，按规则整周标红，但**3 次事件的 2 次不构成趋势**。
> **N < 5 时只显示中性状态 + 「样本不足，本周不做判断」，禁止红/黄/绿。**
>
> **该规则的边界（设计部补充，防过度应用）**：此约束**仅适用于信任闭环板块**。**积压天数不受此约束**——积压是绝对量不是比率，**1 件等5 天也是问题**，不能因为「样本不足」而不显示。

> **四、老板汇报页与管理员用量页是两个独立页面，不是一个页面的两个视角**：
>
> | 维度 | 老板汇报页 | 管理员用量页 |
> |---|---|---|
> | 路由 | （工作台首页，密度 4） | （密度 7） |
> | 数字字体 | 正文字体 | 等宽 tabular-nums |
> | 术语 | 处理 / 跑完 / 次数 / 省了多少 | Token / 调用次数 / 单价 / 成本构成 |
> | 主数字 | 今日完成数、本月省下的工时 | 总 Token、总成本、单 Token 均价 |
>
> 切分理由：① **两套术语体系在结构上互斥**，同一页无法同时满足 ② 权限边界不同（老板看自己团队总账，管理员看全公司构成）③ 导航深度不同（汇报一级每天看 3 秒抓结论，用量二级偶尔钻取）④ **合并必然导致 Token 主导，且这是必然结果而非偶然**——Token 明细信息密度更高，会自然占据视觉主导位。
>
> **下钻路径硬约束（总监裁定，产品与架构共同约束）**：
>
> ```
> 老板路径：试跑页「约 36 元/月」
>   └─> 汇报页内的员工维度成本构成（哪个员工花了多少 · 本月趋势）
>          └─>【终点】不再向 token 级下钻
>
> 管理员路径：/settings/usage （独立入口，不从老板汇报页下钻）
>   └─> token 级明细
> ```
>
> **三条落地要求**：
> ① 试跑页成本区块的「查看明细」指向**报告页内的员工维度成本构成**，不是 token 级
> ② 员工维度成本构成**同样使用业务口径**（金额 + 占比 + 趋势），**不得出现 prompt / response / token 任何字段**
> ③ **员工维度是老板路径的下钻终点**。token 级只存在于 `/settings/usage`，两个入口**不应互通**——一互通术语体系就被污染
>
> **为什么这条是硬约束而不仅是设计建议**：如果「查看明细」把老板送去 token 级页面，我们就在自己产品里开了一条**绕过自己 §12 硬约束的后门**。而这比不做成本下钻更糟——因为它是**看起来很专业的绕过**，且会重置定价锚点（详见 §12「认知分类」约束）。
> **实现约束（已同步架构师）**：后端提供**一份**用量接口，字段同时含业务口径与技术口径。**owner 视图接口层直接不传 token 字段**——不做「显示/隐藏」开关，否则 token 仍泄漏进 DOM 与网络响应。这与 §11.3「不记录模型调用内容」的 P0 承诺形成闭环。
> **埋点拆分**：report_viewed 拆为 owner_report_viewed 与 admin_usage_viewed，否则无法衡量老板是否真的在用汇报页。

| 13 | 越权响应码（架构约束补充） | A 租户尝试访问属于 B 租户的资源 | 服务层返回响应 | **返回 404 而非 403**。403 会泄露「该 ID 存在但无权限」，攻击者可用响应码差异批量枚举其他租户的资源 ID 与规模。同时需防时序侧信道：响应时间不得因资源是否存在而显著差异 |
| 14 | 可观测性数据边界 | 任意任务执行 | 检查该任务的 trace 与日志 | **允许记录**：模型名、token 数、延迟、费用、工具名、参数摘要、chunk ID 与相似度<br>**禁止记录**：prompt 全文、工具返回全文、文档内容、检索到的 chunk 原文。OTel 的 `gen_ai.prompt` / `gen_ai.completion` 语义约定属性**不得用于承载内容**，只用 `gen_ai.usage.*` 与 `gen_ai.request.model` |
| 14b | **owner 视图接口层剔除 token字段**（架构 ADR-015 + 设计部要求，AC-14 的接口层延伸） | 老板访问用量类接口 | 检查响应体| **owner 视角的用量接口在接口层就不序列化 token 字段**——不是置空、不是 null、**是不返回**。用 OpenAPI 不同 schema 表达，使 TS 类型从契约层就区分开。**禁止做「显示/隐藏」开关**，否则 token 仍泄漏进 DOM 与网络响应，产品约束形同虚设。<br>admin 视角接口完整返回技术口径字段。<br>**原则一致性**：我们承诺的不只是「不记录」，而是**连返回给老板的接口里都不出现**——这与 §11.3「不记录模型调用内容」是同一条原则的延伸 |
| 18 | operator 越权看总额 | operator 登录后请求本账套成本总额接口 | 返回响应 | **返回 404 而非 403**（跨权限边界统一 404，理由同AC-13）；operator **只能拿到被授权岗位的成本金额**，且响应中**不包含 token / model / duration 任何字段** |
| 19 | operator 越权改预算 | operator 尝试修改AI 员工的预算上限 | 返回响应 | **返回 404**；且**数据库层无任何写入**（不能只靠前端禁用按钮，后端必须拒绝） |
| 20 | operator 岗位数据隔离 | operator A 与 operator B 分别被授权不同岗位 | A 请求 B 的岗位任务详情 | **返回 404**；repository 层强制按岗位过滤，**不依赖前端传参** |

| 17 | **五条阻断级误杀测试**（架构 ADR-016/017） | 逐条执行下表任务 | 检查是否触发熔断 | **五条全部为 MVP 阻断级验收标准，F6-lite 与 F6-full 均须通过**。<br>**【为什么在 MVP 就必须跑——正确理由，勿用旧版错误理由】**：S1 收窄后**仍有非零误判率**（误杀条件收窄到「工具名+参数完全一致重复 5 次」，但这不是数学证明为零）；**且 S2 是 F6-lite 新增信号，阈值需实测调参**。<br>**【已作废的错误理由】**：「S1 零误判所以测了个不会失败的东西」——此理由已被架构 ADR-016 证伪，**若按此理解会让实现者认为 S1 天然无误杀风险，从而不认真实现参数签名**。<br>**① 下载 50 个竞品页面（url 递增）→ 全程不熔断**<br>**② 逐行处理 100 条 Excel 记录（index 递增）→ 全程不熔断**<br>**③ 批量调用同一接口 30 次（id 递增）→ 全程不熔断**<br>**④ 原地重试同一失败 URL → 第 5 次熔断**<br>**⑤ 参数固定的死循环 → 第 5 次熔断**<br>**优先级：前三条「不许误杀」不低于后两条「必须能杀」**——熔断误报率高比没有熔断更糟，用户会失去信任并直接关掉功能。<br>**用例 ③ 必须能证明修正前后的行为差异**：用仅含 tool_name 的签名跑同一任务应当误杀，若不如此则该测试无区分力，测了也白测。<br>**【配套端到端断言（架构 ADR-017）】**：调用 owner 视角用量接口，递归搜索响应 JSON，断言无任何 key 含 `token` / `model` / `duration`。**比人工检查 schema 可靠——有人在 owner schema 偷偷加回 token 字段时脚本会红** |
| 15 | API Key 密钥分离 | 某租户密钥已加密落库 | 攻击者拿到密文但无应用层漏洞 | 仍无法解密——每租户独立解密密钥，爆炸半径限制在单租户。接口层只显示末 4 位，永不回显全文 |
| 16 | 彻底删除完整性 | 客户申请租户级彻底删除 | 删除完成 | 知识库向量表（pgvector）与任务 checkpoint 表**必须一并纳入删除范围**（易漏项），删除过程可审计 |

## 12.1 角色权限矩阵（路由表映射依据，2026-10-15 新增）

> **背景**：路由表只有前缀没有角色映射，实现者无法判断哪个路由归哪个角色。本章是产品侧的权限定义，架构师据此落 API。
> **与 AC-14b 的关系**：owner 视角不序列化 token 这条硬约束，**只有在角色映射明确后才可执行**。

### 三角色定义

| 角色 | 范围 | 定位 |
|---|---|---|
| **owner**（账套所有者） | 本账套全部 | **付款决策人**，对应 PRD §3.1 的主要用户「企业决策者」 |
| **admin**（管理员） | 本账套 | **否决权人**，对应 §3.1 次要用户 A「管理员」（运营/行政负责人） |
| **operator**（操作员） | 被授权的岗位 | **使用者**，对应 §3.1 次要用户 B「普通员工」 |

### 权限矩阵

| 能力 | owner | admin | operator |
|---|---|---|---|
| 跑任务 / 看自己负责的岗位汇报 | 是 | 是 | **是（仅授权岗位）** |
| **看成本：本人岗位维度** | 是 | 是 | **是（仅自己岗位）** |
| **看成本：本账套总额** | 是 | 是 | **否** |
| **看成本：技术口径（含 token）** | **否** | 是（`/settings/usage`） | **否** |
| 配置 AI 员工（岗位、频率、知识源） | 是 | 是 | 否 |
| **改预算上限** | 是 | 是 | **否** |
| 成员管理 | 是 | 是 | 否 |
| 模型密钥配置 | 是 | 是 | 否 |
| **删除账套** | **是（需二次确认）** | **否** | **否** |
| 导出数据 / 彻底删除 | 是 | 否 | 否 |

### 三个关键裁定的理由

**① operator 能看成本，但只能看自己岗位的，不能看总额 —— 采纳总监判断。**
理由：operator 无从判断要不要停下一个任务，**完全不给成本会导致他无法履职**（这是我的补充理由）。但**必须挡住总额**——总额是老板与管理员的决策依据，给operator 看总额会引发横向攀比，且他无权调配预算。

**② 改预算权限 = owner + admin，operator 不能改 —— 采纳总监判断，并补一条理由。**
理由：operator 若能改预算，等于**给了花钱权限但没给责任承担**（预算超支由owner 承担）。**权限与责任必须匹配。**

**③ 删除账套 = 仅 owner 且需二次确认 —— 采纳总监判断，补强理由。**
理由：删除账套是**不可逆操作**（数据、任务记录、知识源全部清除）。owner 是付款人也是资产所有者，**只有资产所有者能处置资产**。二次确认不可省——PRD §13 已规定删除操作二次确认。

### 两条实现约束

**① owner 接口不得序列化 token（AC-14b 的角色映射依据）**
| 接口 | 角色 | 技术口径字段 |
|---|---|---|
| `/api/v1/usage/summary` | owner | **不返回** token / model / duration |
| `/api/v1/settings/usage` | admin | 完整返回 |
| **operator 的岗位成本接口** | operator | **不返回** token（他只需知道金额，不需要技术明细） |

**operator 视图与 owner 视图同理**——operator 也不需要技术口径。**原则：技术口径只对 admin 一人开放。**

**② operator 的数据范围必须按岗位隔离，且需过 RLS**
不只是「能不能看」，而是**能看的数据本身要按岗位过滤**。架构侧需在 repository 层强制 operator 只查被授权岗位的任务，**不能只靠前端过滤**。

### 客户账号识别码（架构 ADR-003 已实现，零改动）

**产品要求**：`tenant_code`（格式 `AC-` + 8 位 Base32）是**客户登录身份 + 线下收款识别码**，一码两用。

| 要求 | 内容 |
|---|---|
| 展示位置 | 账号设置页**顶部大字**展示 + 复制按钮 |
| 说明文案 | `登录或线下付款时请提供此编号` |
| 与公司关系 | **一个识别码对应一个公司**（用户明确裁定，非财务系统账套号） |

> **已删除的论证（2026-10-15）**：原文写过「为什么不用统一社会信用代码：一家企业可能开多个账套」——**该论证建立在「账套号 = 财务系统账套号」的假设上，用户已明确裁定「一个账套号对应一个公司」，故删除。** 保留此注记是为了说明：**当一个术语被用户重新定义后，所有基于旧定义的论证都要重新检查**——否则文档里会留下看似合理、实际已被否定的推理链。

## 13. 边界条件清单

| 类别 | 边界场景 | 处理要求 |
|---|---|---|
| **空状态** | 未创建任何 AI 员工 / 任务失败无结果 / 知识库为空 / 汇报无内容 | 全部必须有引导下一步的具体文案（禁止「暂无数据」），空状态必须给出可点击的行动 |
| **错误状态** | 模型厂商故障 / 密钥失效 / 平台余额不足 / 任务超时 / 部分步骤失败 | 错误分类展示（模型/网络/权限/预算）+ 具体原因 + 降级方案；**禁止只显示错误码** |
| **成本预估的精度边界** | **预估是「量级估算」不是「精确报价」**（架构 ADR-019 实测结论） | 三条硬限制必须让用户知道：① **峰谷定价**（DeepSeek 峰时段 UTC 01-04 / 06-10 工作日单价翻倍）② **缓存命中差异**（缓存命中输入 ¥0.02 vs 未命中 ¥1，**差 50 倍**）③ **长上下文阶梯**（部分模型超阈值后涨价）。<br>**文案约束**：可以说「本月预计还需 ¥60」，**禁止说「这个任务确切要花 ¥3.42」**。<br>若客户要求精确到分 → 提供「导出明细 CSV」让客户自己对账，**我们只承诺区间不承诺精确值** |
| **加载状态** | 知识库索引中 / 长任务执行中 / 汇报生成中 | 区分排队与执行；给预计时间；提供中止；**知识库索引中允许提前使用并告知索引未完成** |
| **边界值** | 单文件 > 2GB / 任务步骤 > 200 / 单次输出 > 5 万字 / 知识源 > 500 个 / 岗位编制 > 50 | 均需明确上限提示；超限时阻断并给替代方案（拆分任务/分批上传），**不得静默截断** |
| **并发** | 同一 AI 员工定时任务重叠 / 多个用户同时编辑同一岗位配置 / 用户在任务执行中改配置 | 重叠按队列排队并提示；配置编辑用乐观锁 + 冲突提示；**执行中改配置必须被拒绝并说明原因** |
| **离线/弱网** | 移动端弱网提交任务 / 企微推送失败 / 大文件上传中断 | 任务提交走重试 + 幂等；推送失败走站内兜底 + 后续重推；上传断点续传 |
| **权限拒绝** | 普通员工访问他人任务 / 只读成员尝试编辑 / 离职成员残留权限 | 明确拒绝 + 审计记录；**权限变更立即生效，不等会话过期** |
| **数据删除** | 客户要求彻底删除 | 支持租户级彻底删除（知识源、任务记录、汇报、密钥全部清除）；删除过程可审计 |
| **合规** | 客户数据要求不出域 | MVP 不支持私有化，但必须支持「关闭数据用于训练」+ 提供数据处理说明文档，供客户法务审阅 |

## 14. 风险与依赖

| 风险 | 影响 | 缓解 |
|---|---|---|
| **长任务引擎技术不达标（F6）** | **致命**。这是本产品最大不确定性，Confidence 仅 50%。做不好会重演 Manus 的半成品差评 | ① MVP 前 4 个岗位先选低难度场景（表格/文档）积累 TCR 数据；② 熔断 + 断点续跑作为**兜底正确性保障**，而非优化项——即使 AI 判断能力不足，至少不丢成果、不烧钱；③ 若 F6 在 MVP 阶段确实无法达标，**降级方案是「AI 生成执行方案 + 人工逐步确认」**（牺牲自动化率换可靠性），此时产品应诚实改名为「AI 员工助手」而非宣称全自动 |
| **5 个岗位里第 5 个（ERP 录入）做不到高 TCR** | 销售话术「雇 AI 员工干活」失信 | 提前调研目标客户的 ERP 品牌集中度；优先支持 1-2 个主流 ERP；**不支持时在岗位页明确写「目前支持 XX/XX，不支持其他」**，不做虚假承诺 |
| **通用 Agent 的 TCR 天花板（约 65%）** | 商业模式不成立 | 这是我们用「窄场景」而非「通用能力」的根本原因（差异化 2）。若单岗位也无法突破 85%，需回到岗位设计上找原因，而非扩功能 |
| **模型厂商涨价（智谱 2026 年 2 月 API 涨 67-100%）** | BYOK 用户成本上升，归因到我们 | 定价页明确「模型费付给模型厂商，价格随厂商调整」；支持多模型切换，让用户可转向更便宜的模型 |
| ~~平台代付的资金压力与坏账~~ **已作废**（2026-10-15 删除平台代付） | — | **删除平台代付后该风险消失**：平台不经手模型费用，无赠送额度池、无透支、无坏账。**平台资金风险为零。** 若将来重新引入代付，此条须恢复 |
| **熔断误杀率过高** | **高**：用户会失去信任并直接关掉功能，**比没有熔断更糟** | ① 阈值由岗位模板 `expected_idle_steps` 声明，不全局写死 ② 「下载 100 个页面」类任务全程不得触发熔断，列为**阻断级测试** ③ 软阈值用人工确认而非直接熔断 |
| **「不采集 IP」承诺与风控需求冲突** | 法律风险：销售拿绝对承诺回答客户法务，而风控模块确实在采 | 已修正为分层表述：产品分析不采IP，风控模块限定采集设备指纹（仅反滥用/ 保留 90 天 / 隐私政策单列 / 可关闭）。**宁可承认有限采集，也不做无法兑现的绝对承诺** |
| **模型能力静默降级** | 跑到一半才失败，用户已付前面几步的钱 | 降级前校验备用模型能力，不足则**中止而非降级**。能力探测 fail-closed |
| **客户从试用到付费转化低** | 商业模式不成立 | 试用版必须能真的干完一件事；ROI 自助计算器；第二个 AI 员工是扩张信号——需在首份汇报后就引导 |
| **员工抵触导致管理员否决采购** | 销售被「这玩意没人会维护」否掉 | 管理员视角的功能（统一入口、零运维、成本清晰）必须在 MVP 就到位；员工侧需求（F12）虽延后但要尽快 |

### 16.2 网页访问的合规姿态（L1 第三方抓取已恢复，恢复本节）

**关键判断：代客户抓取第三方网站，与客户抓取自己授权的域名，是完全不同的法律姿态。**

| 场景 | 法律姿态 | 风险归属 |
|---|---|---|
| L1 服务端抓取第三方公开网页 | **我们是直接请求方** | **责任在平台侧**。不能用「客户授权我访问他的竞品」来抗辩——授权链在我们与第三方之间断裂了，客户并未授权我们访问第三方 |
| L3 客户自有系统 / 登录态操作 | 客户授权 | 风险可转移给客户 |

**这个风险无法用技术消除，只能靠 G1-G4 四条护栏 + 服务条款明示来管理。**

**四条护栏（技术侧已在架构 ADR-014）**：G1 robots.txt 合规不允许绕过 / G2 频率限制服务端强制 / G3 UA 声明不伪装浏览器 / G4 失败显式化禁止返回空日报冒充成功。

**须在服务条款中明示的核心声明（架构师要求 PM 补写，他明确声明不越界决定）**：

> **本服务会代表您访问第三方公开网页。** 您的 AI 员工在执行「竞品监控」类任务时，会由我们的服务器直接向第三方网站发起请求。我们对访问第三方网站的行为承担平台侧责任。

**为什么必须明示**：L1 抓取第三方时，**授权链在我们与第三方之间断裂了**——客户并未授权我们访问第三方，因此不能用「客户授权我访问他的竞品」抗辩。**这个风险无法用技术消除，只能靠明示 + 四条护栏管理。**

**其他待法务起草的条款（PM 提供事实，措辞由法务定）**，需明确：
- 客户使用「竞品监控」类岗位时，需自行确认目标网站的 robots.txt 政策与使用条款
- 我方遵守 robots.txt、限制频率、不伪装浏览器身份
- 目标站改版、加防护、要求登录导致的抓取失败，会在汇报中显式告知（不静默返回空结果）
