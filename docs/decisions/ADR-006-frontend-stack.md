# ADR-006: 前端采用 Next.js 16 Web 应用 + lucide-react 锁定图标库，不引入 Tauri

## Status
Accepted (2026-10-14)

## Background

两个决策交织在一起，需要一起回答：

**决策 A：形态**。EvoFlow 是 Tauri 桌面应用。但用户已确认要做**云端 SaaS 多租户**——服务器端必须有后端，桌面壳不再是架构的载体。那还要不要 Tauri？

**决策 B：图标**（P0 绝对规则）。项目总监明令：**Spec 中必须锁定一套 SVG 图标库，全项目统一不混用，禁止任何 emoji 图标方案，技术栈选型必须包含锁定图标库的依赖**。这条规则要在这里落地成具体库名+ 版本号。

产品的实际使用场景也影响这个决策：目标客户是**中小企业老板**。他们的工作方式是：早上打开电脑浏览器看一眼 Agent 昨晚干了什么，点几个审批，晚上在手机上看一眼。**"打开浏览器就能用"对这个人群是刚需**，装机/desktop 客户端是巨大的转化漏斗流失点。

## Decision

**前端形态**：Next.js `16.4.0`（App Router，纯 Web，不做桌面壳）
**UI**：React `19.3.0` + Tailwind CSS `4.3.3`
**图标库（锁定）**：`lucide-react@1.57.0` —— **全项目唯一图标来源，禁止引入任何第二套图标库，禁止任何 emoji 充当功能图标**

**锁定细节**：

| 项 | 值 |
|---|---|
| 包名 | `lucide-react` |
| 版本 | `1.57.0`（精确锁定，不用 `^`） |
| 许可 | ISC（免署名，商用无忧） |
| 图标数量 | 1500+ |
| 网格 | 24x24，stroke-width 2 |
| 引入方式 | 逐个具名import（依赖 tree-shaking） |

## Alternatives Considered

### 形态决策

#### 方案 A：Next.js 16纯 Web（选中）

**评分：4.5 / 5**

| 维度 | 权重 | 评分 | 依据 |
|------|------|------|------|
| 与 SaaS 形态契合 | 高 | 5 | 无需安装、无需更新、多租户天然。目标客户是老板，"打开浏览器"是刚需 |
| 开发成本 | 高 | 5 | 一套代码，无 Electron/Tauri 的打包签名/自动更新/崩溃监控三块额外成本 |
| 移动端可达 | 高 | 5 | 响应式 + PWA。老板在手机上审批是高频场景 |
| 性能 | 中 | 4 | Next.js 16.4 生产包更小（Turbopack 缩短 CSS Module 类名与导出名） |
| 本地能力（文件/剪贴板/本地模型） | 中 | 2 | 受浏览器限制，需配合沙箱服务补偿 |
| 流式支持 | 高 | 5 | Route Handler 天然支持流式响应 |

#### 方案 B：Tauri 2 桌面壳 + Web 后端

**评分：2.5 / 5**

| 维度 | 权重 | 评分 | 依据 |
|------|------|------|------|
| 转化漏斗 | 高 | 1 | **目标客户要装客户端才能用**，这是 SMB 市场最大的流失点 |
| 多租户一致性 | 高 | 2 | 桌面端天然是单机概念，多租户逻辑全在服务端，桌面壳只承担渲染，边际价值极低 |
| 开发成本 | 高 | 1 | 额外三块成本：安装包与签名（Windows 代码签名证书 / macOS notarization 谁出钱）、自动更新、崩溃监控 |
| 本地能力 | 中 | 4 | 唯一优势项：本地文件系统、剪贴板、系统托盘常驻 |
| Rust 学习成本 | 中 | 2 | 系统调用要重写为 Rust command，IPC 模型从"全权限"改为 capability 声明 |

**保留价值**：Tauri 在"Agent 需要在本地安全地动手 + 跑/接本地模型 + 轻量常驻"三件事同时出现时是最优解（安装包 ~8MB vs Electron ~150MB，系统托盘/全局热键/开机自启）。我们**Phase 2 若做本地模型/本地文件深度访问**，Tauri 是正确选择。

但 MVP 阶段三件事一件都不成立：我们的模型全在云端、文件操作走沙箱、不需要常驻。**为不需要的能力付三块额外成本，是典型的过度设计。**

#### 方案 C：React 19 + Vite 8（纯 SPA）

**评分：3.5 / 5**

若整个应用都在登录墙后、不需要 SEO，纯 SPA 更简单直接。降级项：团队在 Next.js 的 Server Components /缓存模型上学习成本更高，且 Cache Components 默认开启会引入新的心智负担。

保留意见：如果 Phase 1 决定不做 SSR/SEO（企业 SaaS 后台确实不太需要），这个方案更轻。**但 Next.js 16 的 Instant Navigations 已大幅降低"SPA 感"**，且同一仓库将来要承载营销落地页，所以仍选Next.js。

### 图标库决策

#### 方案 A：lucide-react（选中）

**评分：4.5 / 5**

| 维度 | 权重 | 评分 | 依据 |
|------|------|------|------|
| 图标覆盖度 | 高 | 4 | 1500+，覆盖 B 端后台全场景。缺口存在但可接受 |
| 设计一致性 | 高 | 5 | 24x24 网格 + 统一 stroke-width 2，视觉不打架 |
| Tree-shaking | 高 | 5 | 逐个具名 import，只有实际用到的进包 |
| 生态契合 | 高 | 5 | **shadcn/ui 默认就用 Lucide**，Vercel / Resend / 主流 AI 工具 SaaS 都在用——工程师无需学习成本 |
| 许可 | 高 | 5 | ISC，商用免署名 |
| 包体积 | 中 | 4 | 约 30KB（全量），tree-shaking 后按需 |
| 独特性 | 低 | 2 | 太大势，icon 偏通用（详见下方风险） |

#### 方案 B：Heroicons

**评分：3.5 / 5**

Tailwind 官方出品，292 个图标，质量极高。但**数量太少**——26 个功能模块（对话/Plan/Goal/思维导图/Lead Agent/子Agent/Agent Teams/智能体员工/组织树/资产中心/记忆/知识库/技能/工具集/MCP/沙箱/应用中心/自动化/任务中心/SSO/费用统计/可观测性/安全中心/IM 集成/浏览器控制/Git 集成）必然遇到缺口，缺口就要引第二套库，直接违反"统一不混用"规则。否决。

#### 方案 C：Tabler Icons

**评分：3.5 / 5**

5900+ 图标，覆盖度最好（"数据密集后台"是它的主场，正好匹配我们的场景），MIT 免署名，可自定义 stroke。**它其实比 Lucide 更适合功能模块极多的后台。**

否决理由仅为生态：Lucide 已是 shadcn/ui 默认，新人零学习成本。两者质量差距不足以覆盖生态差距。但这是一个需要在 Phase 2 重新评估的决策——**如果 Lucide 的覆盖度在实现中确实成为瓶颈（缺口 > 20 个），则改用 Tabler，而不是"再引一套"。**

#### 方案 D：Phosphor Icons

**评分：3 / 5**

9000+ 图标（6 字重），6 字重是独特优势——可以用字重表达信息层级。tree-shaking 支持。缺口：Base 版本仅约 1500，实际用起来复杂度高于 Lucide；设计风格偏几何，与 B 端工具的稳重感略有偏差。

#### 方案 E：Radix Icons

**评分：2 / 5**

仅约 300 个，15px 网格。覆盖度完全不够。

#### 方案 F：react-icons / Iconify

**评分：1.5 / 5**

- react-icons：40,000+ 图标但是 20+ 套库聚合，**风格混杂**，直接违反"统一不混用"。且授权需逐套核对（Font Awesome Pro 锁在付费订阅、Noun Project 按次计费）
- Iconify：35 万+ 图标的超集，"一个框架装下所有"。但它解决的痛点是"要用 5 种风格"——我们恰恰要**只用一种**。且逐套许可各异，是商用合规隐患

#### 方案 G：Heroicons + Lucide 双库

**评分：0.5 / 5（违反 P0 规则，直接否决）**

P0 绝对规则明令"全项目统一不混用"。双库必然导致 stroke 宽度、网格、视觉密度不一致。这是规则明令禁止的方案，不做评估。

## Consequences

### 正面

- **转化漏斗最短**：目标客户打开浏览器就能用，无需下载、无需更新、无需信任本地安装包。对中小企业老板这个人群，这是决定性的
- **移动端天然可达**：响应式布局 + 可选PWA，老板在手机上审批天然支持
- **一套代码栈**：无 Electron/Tauri 的打包签名/自动更新/崩溃监控三块额外成本。安装包签名证书谁持有、macOS notarization 谁花钱、崩溃监控何时接入——这些问题在桌面端从第一天就要回答，在 Web 端不存在
- **图标零学习成本**：Lucide 是 shadcn/ui 默认，新工程师不需要学习
- **图标合规无忧**：ISC 许可，商用免署名

### 负面

**必须写进 Spec 的图标硬约束：**

1. **`package.json` 中图标依赖只有 `lucide-react` 一项**。任何新增第二套图标库的 PR 一律拒绝
2. **禁止 emoji 作为功能图标**。这是 P0 规则。审查方式：`grep -P "[\x{1F300}-\x{1FAFF}\x{2600}-\x{27BF}]"` 扫源码与文档，命中即拒
3. **禁止内联手写 SVG 图标**。统一从 `lucide-react` 具名 import。只有品牌 logo（如需）例外，且必须放在 `components/brand/` 单独目录并注明来源
4. **导入方式**：必须具名（`import { Bot } from 'lucide-react'`），禁止命名空间导入（`import * as Icons`）——后者会破坏 tree-shaking
5. **Emoji 仅允许出现在纯文本语境**（如用户生成的正文内容），不作为 UI 元素

**其他负面**：

- **浏览器本地能力受限**：本地文件系统、剪贴板深度访问、系统通知受限。补偿方案：文件操作全部走服务端沙箱（ADR-004），系统通知走 Web Notification API
- **Lucide 只有 outline 风格**：无 filled/duotone 变体。若 UI 设计需要通过"填充 vs 描边"表达选中态，需要另寻方案（如用 opacity/背景色区分）——**不要为此引第二套库**
- **覆盖率缺口风险**：1500+ 图标对 26 个功能模块够用但不是宽裕。若实现中出现 > 20 个图标找不到，**正确做法是改用 Tabler 整体切换，不是新增依赖**

## Verification

**存在性核验**：

```bash
npm install --save-exact lucide-react@1.57.0 next@16.4.0 react@19.3.0
# 断言 lock 文件中版本精确为 1.57.0，无 ^ 前缀
grep '"lucide-react"' package.json   # 必须存在
```

**端到端验证步骤**：

1. **唯一性断言（阻断级）**：`package.json` 中搜索所有图标类包名（lucide|heroicons|tabler|phosphor|radix-icons|react-icons|iconify|font-），断言**只有 lucide-react**
2. **Emoji 扫描（阻断级）**：
   ```bash
   grep -rP "[\x{1F300}-\x{1FAFF}\x{1F000}-\x{1F2FF}\x{2600}-\x{27BF}\x{FE0F}]" src/ docs/
   ```
   断言无命中（用户内容渲染的 fixture 除外）
3. **导入方式断言**：`grep -rn "import \* as .* from 'lucide-react'" src/` 断言无命中
4. **tree-shaking 断言**：`npm run build` 后检查产物，Lucide 相关体积 < 60KB（按需引入后的合理区间），而非全量 30KB+ 图标全进包
5. **渲染一致性断言**：抽取 10 个核心功能图标（Agent/Goal/知识库/沙箱/审批等）截图，断言 stroke 宽度一致、无视觉突兀
6. **构建断言**：`npx tsc --noEmit` 零错误，`npm run build` 零错误（锁版本后必须能复现构建）

第 1、2 条为阻断级：任一失败即违反 P0 绝对规则，禁止继续 Phase 2。
