# ADR-014: 网页访问能力分三级，MVP 只做 L1 HTTP 抓取且不承诺通用浏览器自动化

## Status

**Accepted (2026-10-14) → 曾按 C1 收窄（2026-10-15）→ C1 已被用户复看推翻，L1 全面恢复（2026-10-15）**

> **裁决演进（保留完整轨迹）**：
>
> 1. **初版（10-14）**：主张 L1 抓第三方公开网页，竞品监控留在 MVP 第 1 位。
> 2. **C1 收窄（10-15上午）**：总监裁定「仅客户自有域名」，本 ADR 据此收窄。理由是**授权链断裂**——代客户抓第三方时，客户并未授权我们访问第三方。
> 3. **C1 被推翻（10-15 下午）**：**用户复看后推翻 C1，恢复 L1 第三方公开网页抓取。**
>
> **推翻理由**：抓公开网页在中文语境下是**常规商业行为**（比价、竞品监控、舆情监测均属此类）。
> 真正的风险点不是「抓了」，而是**「伪装」与「绕过」**——而 G1/G3 两条护栏恰好封死了这两条。
> 且**竞品监控是 SMB 老板付费的核心价值感知**，砍掉它商业上是自废武功。
>
> **连带后果**：竞品监控日报**恢复为 MVP 岗位 #1**，替换「自有渠道经营日报」。
>
> **教训（已升级为团队规则）**：C1 收窄与推翻发生在同一天。架构侧执行了 C1 后**未复核最新裁定**就锁定了三份文档，
> 造成「ADR 说收窄、PRD 说恢复、法务说恢复」的矛盾状态。**裁决变更必须回查已落盘的所有下游文档**，
> 不能只改一处（详见团队规则「结论变更通知义务」）。
>
> **下方 Decision 段已按最终裁定（恢复 L1）重写。** 分级能力设计与 G1-G4 护栏本身自始成立。

## Background

本ADR 修正 Phase 1 架构文档中的一处**自相矛盾**，并回答 PM 提出的阻塞问题。

### 矛盾所在

| 位置 | 表述 | 冲突 |
|------|------|------|
| ARCHITECTURE §12.3 | 建议 MVP「只做客户自己授权的域名，不做通用网页自动化」 | — |
| ARCHITECTURE §14.1 | 「前 4 个岗位（**竞品监控**/周报汇总/催办/发票核对）F6-lite 足够」 | 竞品监控按定义要访问**竞品官网**，不是客户自有域名 |
| ARCHITECTURE §4.5 | 出网策略 default-deny，白名单只有 LLM API + 包管理器镜像源 | **竞品域名不在白名单，竞品监控在网络层就会失败** |
| OPEN-DECISIONS | 「浏览器控制模块范围」未决，倾向 MVP 只做客户自有域名 | PM 的 5 岗位里有一个依赖它 |

**根因**：我此前把「网页访问」当成一个能力讨论，实际上它是**三个成本与合规风险差一个数量级**的能力。混为一谈会导致要么过度设计（为竞品监控引入浏览器集群），要么让 PM 的岗位上线顺序建立在错误假设上。

## Decision

**把网页访问能力显式分为三级，各自的成本、合规姿态、并发上限都不同。MVP 只做 L1；L1 抓第三方公开网页（用户复看裁定，已恢复）。**

| 级别 | 能力 | 单次成本 | 内存开销 | 目标合规姿态 | MVP |
|------|------|---------|--------|------------|-----|
| **L1** | 服务端 HTTP 抓取 + HTML 解析 | 10-50ms | ~0（无状态） | **代客户抓公开页；我们是直接请求方，责任在平台侧** | **是** |
| **L2** | 无头浏览器渲染（Playwright） | 0.3-2s | 300-500MB/实例 | 同 L1，但可渲染 JS | 否 |
| **L3** | 登录态/客户自有系统操作 | 0.5-3s | 300-500MB/实例 | 客户显式授权，风险可转移 | 否 |

**关键认知：竞品监控日报不需要 L2。** 现代企业官网/新闻/博客的主体内容绝大多数是服务端渲染的 HTML，
L1 抓取即可。L2 只在目标是 JS 重渲染 SPA 时才需要——**且这类目标应被显式标记为「抓取失败」而非静默返回空内容**（见 G4）。

### 最终落地要点（用户复看裁定）

| 项 | 结论 |
|----|------|
| L1 适用范围 | **第三方公开网页**（竞品官网、新闻页、行业资讯）+ 客户自有域名 |
| 竞品监控日报 | **MVP 岗位 #1**（核心价值感知） |
| L2 无头浏览器 | 不做（成本高 + Chromium 在 gVisor 下 syscall 覆盖大概率失败） |
| L3 登录态 | **不做自动登录**，客户导出上传 |
| G1-G4 护栏 | **全部保留；G1/G3 的定位是「约束平台行为」而非「取悦客户」** |

**合规姿态的诚实表述**：代客户抓第三方时**授权链在平台与第三方之间断裂**——客户并未授权我们访问第三方，
因此**不能用「客户授权我访问他的竞品」抗辩**。责任在平台侧，须写进服务条款（已落 PRIVACY-NOTICE-FOR-LEGAL.md）。

**但风险可控**，因为真正的风险点不是「抓了」而是「伪装」与「绕过」：

- **G1** 遵守 robots.txt —— 不绕过站点声明的抓取规则
- **G3** UA 声明不伪装浏览器 —— **伪装本身在很多站点 ToS 里就是违规**

这两条封死了主要风险面，所以 L1 恢复是合理的。

### L3「不做自动登录」的三重理由（不只是安全决策）

若做自动登录，我们必须存储客户后台凭证，那意味着：

1. **承担客户凭证泄露责任**
2. **凭证进沙箱即违反 ADR-004「凭据不进环境变量」**（`ps` / `/proc/*/environ` 可读）
3. **客户改密码会导致我们的任务批量失败**

「客户导出上传」把三个问题一次性绕开。**这是能力边界的选择，不是能力缺失。**
**G1 在自有域名场景的特殊价值**：客户自己的站点 robots.txt 若禁止抓取，应当遵守——**这向客户证明我们不会擅自访问他的系统**，是信任的一部分。

**MVP 的 L1 必须配套四条护栏**（缺一条即不可上线）：

| 护栏 | 内容 | 防什么 |
|------|------|--------|
| G1 robots.txt 合规 | 抓取前检查目标站 robots.txt，`Disallow` 规则命中即跳过并记录 | robots 协议违规（法律风险） |
| G2 频率限制 | 单域名 ≥2s 间隔；单租户 ≤20 请求/分钟；全局 ≤200/分钟 | 压垮目标站（可能被对方封禁我们 IP） |
| G3 UA 声明 | User-Agent 明确标识本服务（如 `OPCAgentAI/1.0 (+https://...; contact=...)`） | 身份隐瞒；被目标站识别后可追溯 |
| G4 失败显式化 | 抓取失败/被 robots 拒绝/内容为空 **必须记入「我停下来过」板块**，禁止返回空日报冒充成功 | **静默失败是竞品差评的头号来源** |

**G4 是本ADR 最重要的一条**。竞品监控日报最危险的失败模式不是「抓不到」，而是「抓不到但报告说今天没有异常」。老板会据此做决策。架构上必须让抓取失败成为一等公民状态，而不是被吞掉的异常。

> C1 收窄后此点更关键：抓取对象是客户自有系统，客户对「今天没抓到」的容忍度更低，静默失败会直接引发「我自己系统是不是坏了」的工单。

### 关于 L1 的合规姿态（必须诚实）

**代客户抓取第三方网站与「客户抓取自己授权的域名」是完全不同的法律姿态。**

- L3（客户自有域名）：客户授权，我们是被代理人，风险可转移
- L1（竞品官网）：**我们是直接请求方**，责任在我们这一侧，不能用「客户授权我访问他的竞品」来抗辩

**结论：L1 必须满足 G1-G4 四条护栏，且必须在 PRD 与服务条款中明示「本服务会代表您访问第三方公开网页」。** 这一点PM 需要写进 PRD 的合规章节，我不能替产品做这个决定。

## Alternatives Considered

### 方案 A：L1 做，MVP 采用（选中）

**评分：3.5 / 5**

| 维度 | 评分 | 依据 |
|------|------|------|
| 覆盖竞品监控需求 | 4 | 企业官网/新闻/博客主体是 SSR HTML，L1 够用。JS 重渲染站点会失败（G4 显式报告） |
| 成本 | 5 | 无状态，无常驻内存，比 L2 低一到两个数量级 |
| 合规风险 | 2 | **我们有责任**。靠 G1-G4 护栏把风险降到行业惯例水平，但不能归零 |
| 并发能力 | 5 | 无实例开销，可支撑高并发 |
| 对 PM 岗位顺序的影响 | 4 | **不改顺序** |

**唯一实质风险是合规**，且这个风险无法通过技术消除，只能通过护栏 + 服务条款 + G4 显式失败来管理。这是可接受的商业风险（竞品监控是明确的市场需求），但**必须让 PM 和法务知情**。

### 方案 B：L1 不做，竞品监控降级为「客户自有系统 + 授权 API」

**评分：2 / 5**

| 维度 | 评分 | 依据 |
|------|------|------|
| 合规风险 | 5 | 零风险，责任完全转移 |
| 覆盖需求 | 1 | **「竞品监控」改成「监控自己的系统」就不是竞品监控了**，PRD 里的岗位语义被破坏 |
| 对岗位顺序影响 | 1 | 竞品监控退出，周报汇总升为第 1 |

否决理由：**这等于把「竞品监控日报」这个岗位重新定义成别的东西。** PM 的岗位库设计里竞品监控是最能体现「AI 员工主动干活」（每天自己去看竞品变化并汇报）的岗位，是差异化最直观的一个。为了规避合规风险而把它改成「监控自己的系统」，等于砍掉差异化最强的岗位。

### 方案 C：直接做 L2（无头浏览器），一步到位

**评分：1.5 / 5**

| 维度 | 评分 | 依据 |
|------|------|------|
| 覆盖能力 | 5 | JS 站点也能抓 |
| 成本 | 1 | 每实例 300-500MB，10 并发就是 3-5GB，需独立节点集群 |
| 并发上限 | 1 | 严重受限。免费版用户刷监控任务就能打满 |
| 合规风险 | 2 | 同样有责任，但**用了浏览器技术抓取更容易被目标站识别为自动化并封禁**，实际合规姿态反而更差 |
| 沙箱兼容风险 | 2 | gVisor syscall 覆盖仅约 60%（ADR-004 §12.2），Playwright/Chromium 在 runsc 下**大概率失败**，需先跑 POC 才能评估 |

否决理由：**用最高成本方案解决 20% 的问题。** 且 L2 在 gVisor 下的可行性未验证（Chromium 需要大量 syscall），把它放进 MVP 是把一个未验证的技术风险放进最关键的阶段。

### 方案 D：L1 + 客户自带 API Key 访问（客户自己去第三方服务抓）

**评分：2.5 / 5**

让客户配置自己的第三方数据 API（如某数据服务）。

| 维度 | 评分 | 依据 |
|------|------|------|
| 合规风险 | 5 | 责任完全在客户侧 |
| 可用性 | 1 | **中小企业老板不会去买数据 API 并配置 Key**。这与「无 IT 运维能力」的用户画像（PRD §2.3）直接冲突 |
| 体验 | 1 | 与「开箱可用」的岗位设计冲突 |

否决理由：技术上干净但产品上是灾难。PRD 的核心用户画像明确写了「中小企业无 IT 运维能力」，让老板自己配第三方数据 API 是把这个痛点原样还给用户。

## Consequences

### 正面

- **竞品监控日报可留在 MVP 第一位**，PM 的岗位上线顺序表不用改
- **成本可控**：L1 无状态，无常驻开销，比 L2 低一到两个数量级
- **不引入未验证技术风险**：避开了 gVisor + Chromium 的兼容性问���
- **G4 显式失败反而强化了差异化**：抓不到就说「今天没抓到 A、B、C 的页面，已停下」，而不是给一份空日报。这与「失败是交付物的一部分」的定位一致

### 负面

**必须写进 Spec 的七条约束**：

1. **L1 抓取工具必须在出网白名单机制内**，且白名单是**租户可配置**（每个租户配置自己要监控的域名），但需平台侧审核（防止租户用它当通用爬虫）
2. **G1 robots.txt 检查是强制的**，命中 `Disallow` 必须跳过并记录，**不允许绕过**
3. **G2 频率限制必须在服务端强制**，不能靠 Agent 自觉。LLM 可能因为重试而高频请求，必须有服务端限流兜底
4. **G3 User-Agent 必须可识别**，不得伪装成普通浏览器（伪装本身在很多站点的 ToS 里是违规的）
5. **G4 抓取失败必须是一等状态**，进入 `task_steps` 的 `failed` 状态并携带 `error_code`，进「我停下来过」板块。**禁止返回空结果冒充成功**
6. **目标为 JS 重渲染站点时应明确失败**，不让L1 抓取返回空 HTML 被误判为「无变化」。建议 `error_code = TARGET_REQUIRES_JS_RENDER`，并在失败原因中提示「该站点需要浏览器渲染，本服务当前不支持」
7. **服务条款与 PRD 必须明示「本服务会代表用户访问第三方公开网页」**。这是合规姿态的必然要求，不能靠技术手段掩盖

**其他负面**：

- **部分竞品监控会失败**。目标站点改版、加防护、要求登录时抓不到。这是 G4 显式报告的内容，不是 bug。但**这会降低 TCR**，PM 需要知道：竞品监控的 TCR 天花板低于其他岗位（因为外部依赖不受我们控制）。建议 Go/No-Go 判据对不同岗位分别设定，而不是一刀切
- **租户白名单的平台审核**是额外的运营负担。需要一个后台让运营审核租户提交的域名列表

## Related ADRs

- ADR-004（沙箱隔离）—— 出网白名单与 default-deny 策略在此定义
- ADR-011（长任务引擎）—— G4 的失败状态进入 `task_steps` 并驱动「我停下来过」
- ADR-012（预算）—— 抓取失败的步骤不产生模型费用，但已发生的抓取请求有网络成本

## Verification

**存在性核验**：

```bash
# 沙箱网络策略中需有租户可配置的 L1 抓取白名单通道
grep -rn "egress_allowlist" app/services/sandbox/
```

**端到端验证步骤**：

1. **基本抓取**：租户配置 3 个竞品域名，抓取成功，断言：日报含 3 个站点的内容摘要
2. **robots.txt 合规（阻断级）**：
   - 配置一个 robots.txt 中 `Disallow: /` 的站点
   - 断言：**跳过该站**，抓取记录含 `skipped_robots_disallowed`
   - 断言：**不产生任何对该站的请求**
3. **频率限制**：
   - 单域名连续请求 10 次
   - 断言：间隔 ≥2s；租户级 ≤20 请求/分钟
   - 断言：**即使 LLM 主动重试，服务端仍强制限流**
4. **UA 可识别**：断言：发出的请求 UA 含 `OPCAgentAI/` 且含联系方式，**不伪装成 Chrome/Firefox**
5. **失败显式化（阻断级）**：
   - 目标站点返回 500 / 超时 / robots 拒绝
   - 断言：`task_steps` 记 `failed` + `error_code`
   - 断言：汇报「我停下来过」板块**列出该站及失败原因**
   - 断言：**不出现「今天竞品无变化」这类伪造成功的表述**
6. **JS 站点正确失败**：
   - 配置一个 JS 重渲染站点
   - 断言：`error_code = TARGET_REQUIRES_JS_RENDER`，**不是静默返回空内容**
7. **出网白名单生效**：
   - 租户提交一个未在白名单的域名
   - 断言：请求被沙箱网络层拒绝
   - 断言：需平台侧审核通过后才能抓取
8. **越权不可达**：租户 A 配置的域名列表，租户 B 不可见（断言：查询返回 404，符合 §3.5）

第 2、5、6 条为阻断级。第 5 条尤其重要——**静默失败是竞品监控这个岗位最容易犯、也是最伤用户信任的错误**。
