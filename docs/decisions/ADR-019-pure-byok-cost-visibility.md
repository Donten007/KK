# ADR-019: 纯 BYOK 下的成本预估与账套号（删代付后的架构修订）

## Status
Accepted (2026-10-15)

## Background

产品方向发生重大变更（用户决策）：**删除平台代付，改为纯 BYOK + 线下收款**。

用户原话：「不要考虑充值问题，只要能在 SaaS 系统里做出客户公司账套号区分，可以线下收款开户」。

**这作废了 ADR-012 的适用对象，但没作废它的全部内容。** 本 ADR 逐项裁定，并回答 PM 的头号问题。

| ADR-012 原内容 | 裁定 |
|---------------|------|
| 预占-确认-释放两阶段账本 + PG 行锁 | **作废**（平台不经手资金，无账本可预占） |
| `credit_ledger` append-only + REVOKE | **作废**（平台无计费流水） |
| 赠送额度池上界 ¥5,000/月 | **作废** |
| 代付租户熔断阈值更严 | **作废** |
| **权威账务必须在 PG 不用Redis 计数器** | **保留，但对象变了**（见下） |
| **成本事件流 + 幂等归集** | **完全保留，且更重要**（成本统计视图的基础） |

## Decision

### 一、核心问题：纯 BYOK 下成本预估的技术基础是否成立？

**结论：成立，但精度有限，且必须改变「预估」的定位。**

#### 厂商单价能否程序化获取？—— 不能直接获取，但有可靠间接来源

| 途径 | 可用性 | 结论 |
|------|-------|------|
| 厂商官方价格 API | **不存在** | 各家均无price API，价格只在文档网页 |
| 抓取厂商文档页 | 可行但脆弱 | 页面结构变动即失效，且**价格随时可变**（DeepSeek 明确保留调价权） |
| **LiteLLM `model_prices_and_context_window.json`** | **可用** | 行业事实标准，3850+ 模型，社区每日同步 |
| `llmprice-kit`（Python 轻量库） | 可用 | 零依赖包，数据源同为 LiteLLM，MIT 许可 |

**裁定：采用 LiteLLM 价格表作为单价权威来源，每日同步 + 本地缓存兜底。**

**但必须接受三个精度限制**（写进 Spec，不允许前端假装精确）：

| 限制 | 影响 | 缓解 |
|------|------|------|
| **峰谷定价** | DeepSeek 有峰谷价（峰时段单价翻倍），LiteLLM 表不含峰谷规则 | 预估标注「按非峰时段估算」 |
| **缓存命中差异** | DeepSeek 缓存命中输入 ¥0.02 vs 未命中 ¥1，**差 50 倍** | 预估按「部分命中」加权，标注区间而非单值 |
| **长上下文阶梯** | Gemini/Grok/GPT-5 类超阈值后涨价 | 预估标注「不含长上下文阶梯加价」 |

**结论：预估是「量级估算」不是「精确报价」。** 预算闸门用它是合理的（判断是否超预算），但**绝不能用于「这个任务确切要花 ¥3.42」这种表述**。

#### `usage_records` 数据源是否还存在？—— 存在，且是纯 BYOK 的核心资产

**关键认知：成本统计的数据源从来不是平台的账本，而是厂商返回的 usage。**

每次 LLM 调用，厂商响应都带 `usage: {input_tokens, output_tokens, cache_hit_tokens?}`。**这与谁付钱无关。**

```
成本 = Σ(input_tokens × 单价_in + output_tokens × 单价_out)
```

**因此 `usage_events` / `usage_records` 两张表在纯 BYOK 下完全保留**，它们的用途从「平台计费流水」变为「客户成本可见性」。

**这恰好是纯 BYOK 下的新卖点**：平台不经手钱，但**平台比客户更清楚他的钱花在哪**（因为客户只有厂商的月度账单，我们是按任务/按员工的明细）。

#### 预算闸门是否还成立？—— 成立，但性质改变

| 维度 | 代付时代 |纯 BYOK |
|------|----------|---------|
| 闸门目的 | **平台止损**（防止平台亏钱） | **帮客户盯自己的钱** |
| 超预算后果 | 平台拒绝执行 | **警告 + 建议降级**，不硬拦（客户有权花自己的钱） |
| 超预算必要性 | 必须（平台要止损） | **仍然必要**（见下方新场景） |

**纯 BYOK 下的新风险场景（PM 提出，判断成立）**：客户配了高频定时任务 + 不设预算的 AI 员工，几天下来 DeepSeek 账单烧掉几百块。**这正是预算闸门的新价值。**

**裁定：闸门保留，但超预算行为从「阻断」改为「警告 + 明确后果告知」。**

理由：客户花的是自己的钱，我们无权替他决定不能花。但**我们必须让他知道**——「本月已用 ¥180/¥200，接下来 3 个定时任务预计再花 ¥60，你确定吗？」

#### 简化的账务架构

| 组件 | 处置 |
|------|------|
| `credit_accounts` | **删除**（无平台余额） |
| `credit_reservations` | **删除**（无预占对象） |
| `credit_ledger` | **删除**（无平台流水） |
| `usage_events` | **保留**（append-only，幂等键 `request_id`） |
| `usage_records` | **保留**（小时聚合） |
| `model_pricing` | **新增**（LiteLLM 价格表落地，版本化） |
| `agent_budgets` | **保留**（月度预算上限，性质改为「提醒阈值」） |

**ADR-012 的三条设计原则重新表述**：

| 原原则 | 纯 BYOK 下的形态 |
|-------|----------------|
| 权威数据在 PG 不用 Redis 计数器 | 成本归集权威在 `usage_records`，Redis 只做缓存 |
| 幂等防重复 | **完全保留**——`usage_events` 重投必须幂等，否则客户看到虚高的账单 |
| 预占防超卖 | **不适用**（平台无超卖） |

**幂等这条特别强调**：代付时代重复记账坑的是平台的钱，纯 BYOK 时代重复记账坑的是**客户对平台的信任**——他看到自己账单虚高 3 倍会立刻失去信任。**所以幂等约束在纯 BYOK 下更重要，不是更不重要。**

### 二、账套号：**已实现，无需新增**

用户要求「在 SaaS 系统里做出客户公司账套号区分，配合线下收款开户」。

**结论：架构 v1 已实现，无需改动。**

| 标识 | 格式 | 用途 | 状态 |
|------|------|------|------|
| `tenant_id` | UUID v4 | 内部主键，数据库关联 | 已实现（ADR-003） |
| **`tenant_code`** | `AC-` + 8 位 Base32 | **对外账套号，线下收款开户凭据** | **已实现** |

**`tenant_code` 的现有设计恰好匹配这个需求**：

- **可口述、可截图**——老板线下付款时能报出「账套号 AC-8F3K2M9W」
- **不可枚举**——8 位 Base32 = 40 bit，暴力枚举不可行
- **不含业务信息**——不泄露公司名/规模，避免内部编号被外部推断
- **与 `tenant_id` 双向唯一**——登录后可反查

**回答 PM 的三个疑问**：

| 疑问 | 答复 |
|------|------|
| 纯数字还是信用代码？ | **`AC-` + 8 位 Base32**（已定）。**不用统一社会信用代码**——那是企业注册号不是账套号，一家企业可能开多个账套，且信用代码是敏感工商信息 |
| 是否与租户 ID 分离？ | **已分离**。`tenant_code` 对外，`tenant_id` 对内 |
| 是否支持一个客户多个账套？ | **天然支持**。一租户一 `tenant_id`，集团客户可开多租户。若需「同一集团下多账套聚合」，是 Phase 2 的 `parent_tenant_id` 需求，MVP 不做 |

**唯一的建议**：把 `tenant_code` 在 UI 上做得**更显眼**（当前在设置页）。既然它现在是线下收款的唯一凭据，应该在账套设置页顶部以「你的账套号」大字展示，并提供复制按钮 + 「线下付款时请提供此编号」说明。

### 三、删除代付的连带简化：隐私承诺恢复为绝对

**这是对架构有利的变更。**

| 项 | 代付时代 | 纯 BYOK |
|----|---------|--------|
| 设备指纹采集 | **需要**（防薅羊毛） | **不需要** |
| 「不采集 IP」 | 分层表述（产品不采/风控采） | **恢复为一条无例外的绝对承诺** |

**架构侧的三条约束现在完全自洽，无任何例外分支**：

1. §9.6 可观测性数据边界（不记录模型调用内容）
2. AC-14b 接口层不返回 token（owner 视图）
3. owner/admin 双 endpoint 分离

PM 已删除分层表述，**这消除了我此前提出的「销售拿『我们不采集 IP』回答质询有法律风险」问题**。

## Consequences

### 正面

- **成本归集的底层数据源不受影响**——`usage` 由厂商返回，与谁付钱无关
- **ADR-012 从「计费系统」降级为「成本统计」，工作量减少约 40%**（3张表删除，2 张保留，1 张新增）
- **隐私承诺恢复为绝对**，三条约束无例外分支，销售话术简单
- **账套号零改动**
- **预算闸门从平台止损转为客户自守**，法律风险大幅下降（不替客户决定能不能花钱）

### 负面

**六条必须落进 Spec 的约束**：

1. **`model_pricing` 表新增**，数据源 LiteLLM `model_prices_and_context_window.json`，**每日同步 + 本地快照兜底**（拉取失败时用上次快照，不得中断服务）
2. **预估必须标注为量级估算**，前端禁止表述为「确切费用」。峰谷价 / 缓存命中差异 / 长上下文阶梯三个已知偏差必须在 UI 注明
3. **超预算行为改为警告而非阻断**（纯 BYOK 下客户有权花自己的钱），但必须展示「继续会花多少」的提示
4. **`usage_events` 幂等约束在纯 BYOK 下升级为最高优先级**——重复记账直接摧毁客户信任
5. **四个计价维度保留**（租户/用户/Agent/模型），这是纯 BYOK 下的核心卖点——客户只能拿到厂商的月度总额，只有我们能给按岗位下钻
6. **`tenant_code` 需在 UI 提升显眼度**（账套设置页顶部大字 + 复制按钮 + 线下付款说明）

**其他负面**：

- **预估精度无法做高**。若客户对「本月花了多少」要求精确到分，我们只能给区间。**这是能力边界，必须诚实告知**，不能靠话术掩盖。缓解：提供「导出明细 CSV」让客户自己对账
- **LiteLLM 价格表是社区维护**，不是厂商权威。价格调整时有延迟（通常 T+1）。必须明示「单价以厂商账单为准」
- **删除 3 张表后，ADR-012 需要标记为「部分作废」而非删除**——保留作废记录，避免将来有人重新论证代付时重复讨论

## Verification

**存在性核验**：

```bash
pip install llmprice-kit
python -c "from llmprice import LLMPrice; print(LLMPrice().get('deepseek-v4-pro').input_cost_per_1m)"
```

**端到端验证步骤**：

1. **ADR-012 表已删除**：
   - 断言：迁移后 `credit_accounts` / `credit_reservations` / `credit_ledger` **不存在**
   - 断言：`usage_events` / `usage_records` / `agent_budgets` / `model_pricing` **存在**
2. **成本归集仍然工作（纯 BYOK）**：
   - 用客户自有 Key 发起 10 次调用
   - 断言：`usage_events` 有 10 条，含厂商返回的 `input_tokens`/`output_tokens`
   - 断言：`usage_records` 聚合正确，**无平台参与**
3. **幂等（阻断级，纯 BYOK 下更关键）**：
   - 重投3 次事件
   - 断言：聚合数仍为 10（**不虚高**）
   - 理由：客户看到自己账单虚高 3 倍会立刻失去信任
4. **单价来源可用**：
   - 断言：`model_pricing` 表非空，覆盖 4 家厂商
   - 断言：LiteLLM 拉取失败时**回退到本地快照**，不中断服务
5. **预估标注为量级**：
   - 断言：预估响应中含「估算」字样与偏差说明
   - 断言：**不含「确切」「精确」类表述**
6. **超预算为警告非阻断**：
   - 预算超 100%，发起任务
   - 断言：任务**正常执行**，同时返回 warning 与「继续预计花费 ¥X」
   - 断言：不返回 402
7. **账套号可用**：
   - 断言：`tenant_code` 格式为 `AC-` + 8 位 Base32
   - 断言：与 `tenant_id` 双向唯一
   - 断言：账套设置页顶部可见且有复制按钮
8. **四维度计价可用**：
   - 断言：`/reports/cost-breakdown`（owner 口径）能按Agent 维度聚合
   - 断言：管理员能按模型维度看 token 明细
   - **理由：客户只有厂商月度总额，按岗位下钻是我们的核心价值**

第 3、6 条为阻断级。第 6 条是本轮变更最容易搞错的地方——**纯 BYOK 下不能沿用代付时代的「超预算硬拦」**，那是替客户做决定。
