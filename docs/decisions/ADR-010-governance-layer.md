# ADR-010: 治理层（SSO/多账号/费用统计/可观测性/安全中心）从零自建

## Status
Accepted (2026-10-14)

## Background

用户已确认这是**与 EvoFlow 最本质的架构差异之一，也是差异化机会**。

项目总监的判断：EvoFlow 的多账号/SSO/费用统计在开源版其实是**残缺的**——因为它是桌面应用，"多账号"只是本地配置切换，"SSO"是第三方 API Key 接入，"费用统计"是本地 token 计数。做云端 SaaS 时，这整块需要我们自己从零建。

**这是风险，也是机会**：

- 风险：26 个功能模块里，这5 个治理模块（多账号 SSO、费用统计、可观测性、安全中心、任务中心）我们没有任何可参考的实现，全新设计
- 机会：这恰好是**中小企业老板最买单的东西**。老板买 SaaS 最关心三件事：（1）钱花在哪了（2）员工能不能用（SSO +权限）（3）安不安全（数据不泄露）。EvoFlow 在这三点上都是空白

**关键判断**：治理层不是"附属功能"，它是**这个产品能否卖给企业**的前提。功能再多，安全和账目不清，企业客户不会买。

## Decision

**治理层从零自建，分5 个模块，与主业务解耦但共享基础设施。**

| 模块 | 自建内容 | 优先级 |
|------|---------|-------|
| **多账号 SSO** | 邮箱密码 + Google OAuth + 企业 SSO（SAML/OIDC 可插拔） | P0 |
| **费用统计** | 按租户/用户/Agent/模型 四维度归集 + 实时看板 + 配额熔断 | P0 |
| **可观测性** | OpenTelemetry trace + 结构化日志 + 成本可追溯 | P0 |
| **安全中心** | 审计日志 + 密钥托管 + 权限矩阵 + 出网策略 | P0 |
| **任务中心** | 全租户任务视图 + 失败重试 + 死信处理 | P1 |

**锁定技术**：

| 组件 | 版本 | 用途 |
|------|------|------|
| JWT | `PyJWT` 2.x | Access/Refresh token |
| 密码哈希 | `argon2-cffi` | 优于 bcrypt（抗 GPU 破解） |
| OTel SDK | `opentelemetry-sdk` + `opentelemetry-instrumentation-fastapi` | trace/span |
| Prometheus | 服务端指标 | metrics 拉取 |
| Grafana | 看板 | 可视化 |
| Sentry | 错误追踪 | 前端 + 后端异常 |

## Alternatives Considered

### 多账号 SSO

#### 方案 A1：自建邮箱密码 + 可插拔 OAuth/OIDC（选中）

**评分：4/ 5**

| 维度 | 权重 | 评分 | 依据 |
|------|------|------|------|
| MVP 速度 | 高 | 5 | 邮箱密码 1-2天；Google OAuth 接现成库 1 天 |
| 企业 SSO 扩展 | 中 | 4 | 用 OIDC 通用协议，Keycloak/Authentik/企业 IdP 都能接，**不需要为每家 IdP写代码** |
| 学习成本 | 高 | 3 | 团队要理解 OIDC 流程（授权码+ PKCE） |
| 成本 | 高 | 5 |自建无License 费 |

**为什么不用托管 Auth**（Auth0 / Clerk / Supabase Auth）：

| 方案 | 评分 | 否决理由 |
|------|------|---------|
| Auth0 | 2.5 | 免费层有MAU 限制，超出涨价快；SAML 连接器和企业功能要付费；MAU 上涨后成本不可控 |
| Clerk | 2.5 | 同样 MAU 计费，SAML 在付费层|
| Supabase Auth | 3 | 免费额度内可行，但引入 Supabase 就意味着部分数据在 Supabase，与"数据不出境/自主可控"冲突 |

**决定性理由**：SSO 连接器（企业客户真正需要的功能）**在所有托管方案里都是付费项**，而企业 SSO 是我们面向中小企业老板 selling point 之一。MVP 阶段用 OIDC 标准协议 + 预留 SAML 适配位，把"接哪个 IdP"变成部署配置而不是代码开发。

#### 方案 A2：Keycloak（自托管 IAM）

**评分：3.5 / 5**

开源（Apache 2.0）、功能完整（SAML/OIDC/LDAP/MFA 全支持）、企业客户认可度高。**这是 Phase 2 的正确答案**。MVP 不选因为：它是独立的 JVM 服务（+2GB 内存），运维成本高于收益；且MVP 阶段不需要 SAML/LDAP/MFA。

### 费用统计

#### 方案 B1：自建事件流归集 + PostgreSQL 聚合（选中）

**评分：4.5 / 5**

架构：
```
LLM 调用 / 沙箱执行 / API 请求
        ↓ 写入
usage_events（Redis Streams，实时）
        ↓ 消费者
usage_records（PostgreSQL，按小时聚合）
        ↓ 看板查询
费用看板 + 配额熔断
```

四个归集维度（对应四种老板关心的问题）：

| 维度 | 回答的问题 | 示例问题 |
|------|-----------|---------|
| 按租户 | 我这个月花了多少 | "10 月账单为什么比 9 月高 3 倍" |
| 按用户 | 谁在用 | "员工 A 用了 80% 的额度" |
| 按 Agent | 哪个数字员工最烧钱 | "市场专员小王的成本最高，值不值" |
| 按模型 | 贵在哪 | "为什么这次任务花了 5 元" |

| 维度 | 权重 | 评分 | 依据 |
|------|------|------|------|
| 归集准确 | 高 | 5 | 事件驱动，不丢|
| 查询性能 | 高 | 4 | 小时聚合表 + 物化视图，百租户百万元级无压力 |
| 实时性 | 中 | 4 | 准实时（秒级），不是强实时 |
| 成本 | 高 | 5 | 零License |

#### 方案 B2：Langfuse / Helicone

**评分：3 / 5**

Langfuse 是优秀的 LLM 可观测性工具，trace 界面开箱即用。**但在"按 Agent / 按租户 / 按用户 做计费归集"这个核心需求上，它是为"调试"设计的，不是为"计费"设计的**——需要额外开发映射层。且SaaS 商业产品把计费数据放在第三方，需评估数据出境与成本。

**采用混合策略**：Langfuse 可在 Phase 2 作为开发调试工具引入，但**计费归集必须自建**（数据是商业核心资产，且要与配额熔断强耦合）。

#### 方案 B3：直接查 LLM 厂商账单

**评分：1.5 / 5**

致命缺陷：**BYOK 模式下客户用自己的 Key，账单在客户那里，我们拿不到数据**。而 BYOK 是已确认的决策之一。所以费用统计必须自建——这与选型无关，是决策 #4 的必然推论。

### 可观测性

#### 方案 C1：OpenTelemetry + Prometheus + Grafana + Sentry（选中）

**评分：5 / 5**

| 维度 | 权重 | 评分 | 依据 |
|------|------|------|------|
| 标准化 | 高 | 5 | OTel 是行业标准，不锁定厂商 |
| 成本 | 高 | 5 | 全部开源自托管 |
| 生态 | 高 | 5 | 所有主流库都支持自动埋点 |
| 前端错误 | 中 | 4 | Sentry 补位（OTel 的前端 RUM 支持弱） |
| 学习成本 | 中 | 3 | trace/span/metric 概念需熟悉 |

**必须埋点的关键 span**（这直接对应"可观测性"功能模块）：

- `llm.call`：模型、token 数、延迟、成本、是否重试
- `sandbox.exec`：沙箱 ID、运行时长、退出码、是否超时
- `tool.execute`：工具名、参数摘要、结果摘要、耗时
- `agent.run`：Agent ID、goal ID、总成本、总时长
- `subagent.delegate`：父→子 Agent、并发数

#### 方案 C2：仅 Sentry

**评分：3 / 5**

错误追踪优秀，但缺 trace 关联、缺 Prometheus 指标、缺成本归集。作为补充而非替代。

#### 方案 C3：商业 APM（Datadog / New Relic）

**评分：2 / 5**

成本随用量线性增长，且**Agent 场景的 trace 量极大**（一个 goal 可能产生几百个 span）→ 账单不可预测。否决。

### 安全中心

#### 方案 D1：自建审计日志 + 密钥托管 + 权限矩阵（选中）

**评分：4/ 5**

五个子模块：

| 子模块 | 实现 | 关键约束 |
|--------|------|---------|
| 审计日志 | `audit_logs` 表 + OTel 事件 | **只追加，不可修改删除**；保留 ≥ 1 年 |
| 密钥托管 | `credentials` 表 + KMS 加密 | **每租户独立解密密钥**（密钥分离）；凭据永不进沙箱环境变量 |
| 权限矩阵 | RBAC（4 租户角色 + 5 全局角色）+ 资源级 ACL | 权限感知 function calling：LLM **根本不知道**被限制的工具存在 |
| 出网策略 | 租户级 egress 白名单 | 默认拒绝 |
| 数据导出/删除 | 租户全量导出 + 一键删除 | 客户流失时的合规要求 |

**"权限感知 Function Calling"是关键设计**：RBAC 过滤必须在**发送给 LLM 之前**完成，让 LLM 看不到无权使用的工具——而不是"知道有这个工具但不能用"。后者会诱导模型反复尝试调用被拒的工具，既浪费 token 又有越权风险。

#### 方案 D2：第三方 Secrets Manager（Vault）

**评分：3/ 5**

Vault 功能最全（动态密钥、轮换、审计），但运维成本高（需要专门运维 + 高可用）。MVP 阶段用 PostgreSQL + KMS 加密足够（AWS/GCP 的托管 KMS 本身就可靠）。**Vault 作为 Phase 2 升级路径**。

### 任务中心

#### 方案 E1：复用 goal/run 表 + 独立管理界面（选中）

**评分：4.5/ 5**

不新建数据模型——`goals` / `agent_runs` / `approvals` / 死信表已足够。任务中心是一个**聚合查询视图**：按租户/状态/时间筛选，展示运行中、等待审批、失败、已完成的全部任务，提供重试/终止操作。零额外数据模型，零额外同步逻辑。

## Consequences

### 正面

- **这是差异化优势，不是负担**：EvoFlow 在这 5 个模块全空白，我们从零建的这套恰好是企业客户最关心的
- **零 License 成本**：全部开源自托管，随租户数增长不增加软件成本
- **BYOK 决策的必然要求**：费用统计必须自建（决策 #4 已锁定 BYOK 优先）
- **无厂商锁定**：OTel 是标准，换后端不影响业务代码

### 负面

**必须内嵌 Spec 的五条约束：**

1. **【最高风险】权限过滤必须在发送给 LLM 之前完成**，让 LLM 看不到无权工具。这与"工具白名单"的实现位置直接相关——必须在构建 tool schema 列表的环节过滤，不能在 function calling 执行环节才拒绝

2. **审计日志必须只追加**。用数据库触发器或专门的 append-only 权限（`REVOKE UPDATE, DELETE ON audit_logs`），**不能依赖应用层自律**。审计日志可被篡改等于没有审计日志

3. **凭据永不进沙箱环境变量**。环境变量会被 `ps`、`/proc/*/environ`、崩溃 dump 泄露。必须经 stdin 或一次性 token 文件注入，任务结束立即销毁。且**每租户独立解密密钥**：即使应用层有 bug 泄露了密文，解密也需要该租户独有的密钥，爆炸半径限制在单租户

4. **费用归集不能丢事件**。Redis Streams 消费者用消费者组 + 显式 ACK，未ACK 的事件在重启后重投。且每条 `usage_event` 必须带 `request_id` 幂等键，`usage_records` 聚合时 `ON CONFLICT DO NOTHING`——否则重投会导致重复计费

5. **配额熔断必须在 API 层和任务层双层执行**。API 层拦瞬时超额（返回 429），任务层拦长任务超额（优雅降级或终止）。只在 API 层拦的话，跑到一半的 goal 会把预算烧穿

### 中性：MVP 明确不做

- 不做 MFA/2FA（Phase 2）
- 不做 SAML（只预留 OIDC 适配位，Phase 2 集成 Keycloak）
- 不做字段级加密（Phase 2，如客户要求）
- 不做跨区域数据驻留（Phase 2）
- 不做 SOC 2 / ISO 认证流程（拿到 10 个付费客户后再启动）

## Verification

**存在性核验**：

```bash
pip install "PyJWT[crypto]" argon2-cffi \
            opentelemetry-sdk opentelemetry-instrumentation-fastapi \
            opentelemetry-exporter-otlp
```

**端到端验证步骤**：

1. **SSO 基本流**：
   - 邮箱注册 → 验证邮件 → 登录，断言：JWT 签发，refresh token 可换新 access token
   - Google OAuth 登录，断言：回调正确创建/关联账号
2. **越权阻断（阻断级）**：
   - `member` 角色用户尝试访问 `/admin/*`，断言 403
   -租户 A 的 token 访问租户 B 的资源，断言 403 **且数据库查询返回 0 行**（RLS 兜底）
3. **权限感知 Function Calling（阻断级）**：
   - `viewer` 角色发起对话，断言：发送给 LLM 的 tool schema 中**不含**写入类工具
   - 断言：LLM 从未尝试调用被禁工具（不是"调用后被拒"）
4. **审计日志不可篡改（阻断级）**：
   - 执行若干敏感操作，断言：`audit_logs` 有对应记录，含操作人/租户/时间/资源/结果
   - 尝试 `UPDATE audit_logs SET ...` 和 `DELETE FROM audit_logs`，断言：**均失败**（权限拒绝）
5. **费用归集准确性**：
   - 发起 10 次 LLM 调用，断言：`usage_events` 有 10 条
   - 触发消费者重投 3 次，断言：`usage_records` 聚合数仍为 10（**不重复计费**）
   - 断言：四个维度（租户/用户/Agent/模型）分别聚合的总数一致
6. **配额熔断**：
   - 把租户配额设为 100 token，发起超额请求，断言 API 返回 429 +升级引导
   - 起一个预计超配额的长 goal，断言：任务层优雅降级/终止，**总花费不超配额 120%**
7. **凭据保护（阻断级，与 ADR-004 联动）**：
   - 断言：沙箱内 `env` / `/proc/1/environ` 无任何凭据
   - 断言：租户 A 的凭据密文用租户 B 的密钥解不开
8. **可观测性链路**：
   - 跑一个含子 Agent 的 goal，断言：trace 中能看到父→子 Agent 的 span 父子关系
   - 断言：LLM span 上挂着模型名、token 数、成本
9. **任务中心**：
   - 造出运行中/等待审批/失败/完成各状态的任务
   - 断言：任务中心页面能按租户/状态/时间筛选
   - 断言：能从界面触发重试

第 2、3、4、7 条为阻断级。
