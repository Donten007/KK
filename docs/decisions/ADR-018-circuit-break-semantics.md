# ADR-018: 熔断与员工判断的语义分离 + 图标删除门禁 + F8 取舍排序

## Status
Accepted (2026-10-14)

## Background

本 ADR 记录 Phase 1.5 第三轮的三项决议，其中两项是**修正我自己的建议**，一项是**接受 PM 的反驳**。

| 来源 | 输入 | 性质 |
|------|------|------|
| PM | 反驳我「先砍 F8」的建议，给出留存依赖论证 | **我采纳 PM** |
| 设计师 | 熔断与员工判断必须语义分离；图标删除也要门禁 | 采纳并扩展 |
| 设计师 | 询问 F6-lite 事件类型清单 | 本 ADR 提供 |

## Decision

### 一、接受 PM 的反驳：F8 排在岗位数量之前（修正我上一轮建议）

我上一轮建议「若必须压缩，先砍 F8（企微推送）或减少岗位数量」。**PM 反驳并给出了我没想到的论证，我采纳她的排序。**

**PM 的论证**：F8 是「老板每天早上在企微收到汇报」这个通道，而**老板汇报打开率是最重要的留存指标**（PRD §11.3 原话）。砍掉 F8 后老板必须主动打开网页才能看到员工干了什么，**直接影响判据 6「7 日留存 ≥40%」**。而砍岗位数量只减少验证覆盖面（5→3），不影响任何一条判据。

**我复核了 PRD，确认她是对的**，且理由比我原来的更强：

| 判据 | 是否依赖 F8 | 依据 |
|------|------------|------|
| 判据 6「7 日留存 ≥40%」 | **是** | PRD §11.3：留存事件为 `session_start` / `owner_report_viewed` / `daily_report_clicked`。**推送是这些事件的触发器**，没有推送老板不会打开网页 |
| 判激活定义 | **是** | PRD §11.3 激活定义含 `first_report_viewed` + `daily_report_clicked` |
| TCR / HITL / ROI | 否 | 与推送无关 |

**修正后的取舍排序**（依据是「砍掉会让哪条判据失效」，不是「哪项实现便宜」）：

```
1. 先砍岗位数量（5 → 3）        代价：覆盖面，不影响任何判据
2. 再砍 F8（企微推送）          代价：判据 6 与激活定义受影响
3. 最后才考虑 F6                代价：TCR 判据本身失效（无断点续跑 → 长任务失败率必然高）
```

**我上一轮把 F8 排在岗位数量之前是错的**，理由是我只看了「F8 是渠道不是能力」，忽略了渠道决定了判据 6 的事件能否发生。**这是工程视角与产品视角的差异，我按产品视角修正。**

**给总监的补充**：这个案例说明取舍排序**不能由架构单方决定**——我判断「实现成本与判据影响」时漏了「事件触发器」这一层，而 PM 从用户行为出发生看到了。取舍排序应与 PM 共同定。

### 二、熔断与员工判断必须语义分离（采纳设计师）

设计师指出一个我漏掉的后果：修好 S1 误杀后熔断频率会回落（好事），但**误杀版本下已经产生的历史数据会留在用户的待确认队列里**。

**更重要的设计判断**：熔断是**系统问题**，员工主动判断是**协作行为**，两者混在同一队列会让老板错误归因。

| 语义 | 图标 | 位置 | 文案示例 |
|------|------|------|---------|
| 员工主动判断不确定 | `Hand` | 汇报页③ + 员工卡片状态点 + **待确认队列** | 「我没敢填客户等级」 |
| 系统熔断 | `CircleDashed` + `CircleAlert` | **任务行内联（不占队列名额）** | 「这一趟卡住了，我停下来等你」 |

**架构落点：事件类型必须区分两类**

```
needs_human_input  → 进待确认队列（owner 可见，L1）
circuit_break      → 任务行内联（owner 可见，L1，但不入队）
```

**为什么熔断不占队列名额**：队列是给「需要老板做决定」用的。熔断时系统已经停止并保留了成果，**不需要老板做任何决定**，把它塞进队列会稀释队列的信号强度并造成疲劳。

**设计师提出的降频规则**：降频三级（合并同类项 / 降级汇总条）**只作用于「员工主动判断」类**；**熔断类不受降频影响，因为熔断必须每次都可见**（它是系统问题，隐藏它等于隐藏系统缺陷）。

**已实包验证**：`CircleDashed` / `CircleAlert` / `Hand` 三个图标在 `lucide-react@1.57.0` 中均存在（架构师已独立验证）。

### 三、熔断文案禁止暴露系统行为（采纳设计师的约束）

设计师提出一条我完全赞同且未想到的约束：

> **熔断阈值收紧时，UI 上不能有任何「我们收紧了限制」的暗示。** 理由：如果界面暴露「系统现在更保守了」，老板会理解为「之前那些产出可能是靠运气」——这会一次性摧毁「我停下来问过 N 次，它们没有一次是猜的」这句话的可信度。

**架构约束**：熔断事件的 UI 文案**只讲业务事实，不讲系统行为**。

| 禁止 | 允许 |
|------|------|
| 「由于无进展检测阈值调整为…」 | 「我在检索这一步卡住了，因为需要你授权店铺后台」 |
| 「触发熔断（连续 5 步无进展）」 | 「我在这一步停下来了，前面 7 步的成果都留着」 |
| 「系统检测到重复调用模式」 | 「我一直在重复做同一件事，就先停下来问你」 |

**技术侧配合**：`error_code` 保留在数据库与审计日志（供排查），但**不进入 owner 可见的文案**。这与 ADR-017 的 `visibility` 分级是同一个思路——技术细节进 admin 侧。

**这条与 §8.5 的信任指标直接冲突**：信任指标说「它们没有一次是猜的」，若界面暴露「我们收紧了限制」，这句话立刻自相矛盾。

### 四、图标删除也要门禁（采纳设计师的第 5 步）

设计师指出我的 `verify-icons.sh` 只管新增，不管删除——**删掉一个状态后，某处旧 import 会静默变成 undefined 而不报错**。

**我已验证这个说法成立**（Node 实测）：

```javascript
const m = { a: 1 };
const { a, nonexistent } = m;   // nonexistent === undefined，静默无报错
```

ESM 具名导入失败通常在构建时报错，但**在 re-export 或 map 引用场景会静默渲染空白**。

**门禁扩展为双向**：

| 方向 | 检查 |
|------|------|
| 新增 | 源码中所有 `from 'lucide-react'` 的导入名，必须存在于包的 `declare const` 导出 |
| **删除** | 包中已移除的导出名，**若仍被源码引用则阻断**（对照历史 lock 文件的导出快照） |

### 五、F6-lite 事件类型清单（回应设计师的请求）

设计师要求一份事件类型清单，逐条标注 L1/L2/L3 与图标。**这份清单同时是 ADR-017 `visibility` 字段的落地依据。**

| 事件类型 | 语义 | visibility | UI 级别 | 图标 | 说明 |
|---------|------|-----------|--------|------|------|
| `task_started` | 任务开始 | owner | L1 | `LoaderCircle` | — |
| `step_completed` | 单步完成 | owner | L1 | `CircleCheck` | 汇报页时间轴 |
| `task_completed` | 任务完成 | owner | L1 | `CircleCheck` | — |
| `task_failed` | 任务失败 | owner | L1 | `CircleX` | — |
| `needs_human_input` | 员工主动询问 | owner | L1 | `Hand` | **进待确认队列** |
| `circuit_break` | 系统熔断 | owner | L1 | `CircleDashed` + `CircleAlert` | **任务行内联，不入队** |
| `budget_warning` | 预算达 80% | owner | L1 | `CircleAlert` | 文案只讲业务事实 |
| `budget_exhausted` | 预算耗尽 | owner | L1 | `CircleAlert` | 同上 |
| `task_cancelled` | 用户主动中止 | owner | L1 | `CircleX` | — |
| `stopping` | 中止进行中 | owner | L1 | `CircleDashed` | ADR-017 §17.1 |
| `tool_called` | 工具调用 | owner | L2 | `Wrench` | 折叠节点 |
| `retrieval_hit` | 知识检索命中 | owner | L2 | `Search` | 折叠，显示「检索了 N 条 · Xs」 |
| `file_written` | 产出文件 | owner | L2 | `FileText` | 折叠 |
| `step_retry` | 单步重试 | owner | L2 | `RefreshCw` | 折叠 |
| `raw_prompt` | 原始 prompt | **admin** | L3 | — | **绝不进 owner** |
| `raw_completion` | 完整响应体 | **admin** | L3 | — | 同上 |
| `retry_attempt` | 重试记录 | **admin** | L3 | — | 同上 |
| `token_usage` | token 明细 | **admin** | L3 | — | 同上 |
| `checkpoint_written` | 检查点落盘 | **admin** | L3 | — | 运维用 |
| `sandbox_exec` | 沙箱执行 | **admin** | L3 | — | 运维用 |

**L1 禁止项**：不得含 `[INFO]` / `elapsed=` / token 数（对齐设计师「禁止系统日志语汇」）。

**总数 19 个事件类型，其中 owner 可见 10 个（L1）、admin-only 9 个（L3+运维）。** 未列入本表的新事件类型**默认落 admin**（ADR-017 §17.2 的默认值方向）。

## Consequences

### 正面

- **F8 取舍排序修正**：避免砍掉直接影响判据 6 的能力
- **熔断与员工判断语义分离**：避免老板把系统缺陷误归因为「员工能力不行」
- **熔断文案约束**：保护「我没有一次是猜的」这句话的可信度——这是差异化卖点 3 的载体
- **图标删除门禁**：防静默 undefined（已 Node 实测确认该风险真实）
- **事件清单**：ADR-017 的 `visibility` 字段有了具体落地依据

### 负面

**六条必须落进 Spec 的约束**：

1. **F8 取舍排序修正为：岗位数量 → F8 → F6**。架构文档与 SCOPE-CUT-DECISION.md 均需同步（PM 已同步该材料）
2. **`needs_human_input` 与 `circuit_break` 是两类不同事件**，前者进队列、后者任务行内联。禁止合并
3. **降频三级只作用于 `needs_human_input`**，`circuit_break` **不受降频影响**（每次必须可见）
4. **熔断/预算类文案禁止暴露系统行为**（不写「阈值调整」「检测到重复模式」，只写业务事实）。`error_code` 保留在库与审计日志，不进 owner 文案
5. **图标门禁双向**：既校验新增导入名有效，也校验已移除的导出名不再被引用
6. **新事件类型默认 `visibility='admin'`**，面向老板需显式改并经 review

**其他负面**：

- **事件清单需维护**。新增事件若忘记标 `visibility`，默认落 admin（安全但可能该给老板看的不给）。建议每次新增事件时 review 问一句「这个老板需不需要知道」
- **F8 若最终仍被砍**，判据 6 与激活定义的达成率会显著下降，届时应下调留存目标而非硬扛

## Verification

**存在性核验**：

```bash
npm pack lucide-react@1.57.0 && tar -xzf lucide-react-1.57.0.tgz
for n in Hand CircleDashed CircleAlert CircleCheck CircleX LoaderCircle Search FileText RefreshCw Wrench; do
  grep -q "declare const ${n}:" package/dist/lucide-react.d.ts && echo "OK $n" || echo "MISSING $n"
done
```

**端到端验证步骤**：

1. **F8 取舍排序已同步**：
   - 断言：架构文档与 SCOPE-CUT-DECISION.md 的排序均为「岗位数量 → F8 → F6」
2. **两类事件分离（阻断级）**：
   - 触发 `needs_human_input`，断言：进待确认队列，图标 `Hand`
   - 触发 `circuit_break`，断言：**不占用队列名额**，出现在任务行内联
   - 断言：owner 订阅 SSE 能收到这两类事件
3. **熔断不受降频（阻断级）**：
   - 同一租户单日触发 10 次熔断
   - 断言：**10 次全部可见**，未合并为汇总条
   - 对照：10 次 `needs_human_input`，断言：按降频规则合并
4. **熔断文案约束（阻断级）**：
   - 断言：owner 可见文案中**不含**「阈值」「检测」「熔断」等系统行为词
   - 断言：`error_code` 存在于数据库与 admin 审计日志
5. **图标删除门禁（阻断级）**：
   - 从源码移除某图标的 `declare const`（模拟包版本变化），保留源码引用
   - 断言：CI **阻断**
6. **事件 visibility 默认值（阻断级）**：
   - 新增一个未标 `visibility` 的事件
   - 断言：默认落 `'admin'`，owner 收不到
7. **事件清单完整性**：
   - 断言：ADR §5 表中 19 个事件类型全部有 `visibility` 与图标标注
   - 断言：L1 事件文案不含 token 数

第 2、3、4、5、6 条为阻断级。第 4 条需人工评审文案，但可做成关键词黑名单自动化检查。
