# ADR-009: 智能体员工"上班"调度采用组织树 + 定时触发 + 审批流三段式

## Status
Accepted (2026-10-14)

## Background

这是 EvoFlow 的"智能体员工"和"组织树协作"两个功能模块的实现基础，也是产品的差异化卖点：

**场景**：中小企业老板配置几个"数字员工"，每个有岗位、职责、汇报线、工作时间表。例如：

- "市场专员小王" —— 每天 9:00 巡检竞品动态，产出日报发给老板
- "财务小李" —— 每周五 17:00 生成本周账单汇总，需老板审批后才发出
- "客服小张" —— 实时响应工单，紧急问题需升级给"客服主管小陈"

对应的三个技术能力：

1. **定时触发** —— "上班"（cron 触发）和"下班"（停止接单）
2. **组织树汇报线** —— 小王向小陈汇报，小陈向老板汇报。任务在小陈层汇聚，小陈需要向老板汇总
3. **审批流** —— 小李生成账单后**不能直接发给客户**，需要老板点批准

**技术难度排序**：定时触发（简单，Hatchet cron 即可）< 审批流（中等，LangGraph interrupt 即可）< **组织树汇报线（最难，见下）**

**组织树为什么难**：这不是"树形结构存一下"就完了。真实的组织协作有这些要求：

- **多级汇总**：小王的产出要能自动汇总进小陈的日报，小陈的再汇总进老板的周报
- **循环依赖**：小陈的审批结果要能唤醒小李继续执行（图节点级的 interrupt/resume，不是简单的定时器）
- **权限继承**：小王不该看到老板的客户定价数据（小陈也不该看到全部）
- **员工离职（停用）**：停用小王时，他手上正在跑的任务怎么办
- **成本归属**：小王的 token 花费要算在小王头上，不算在老板头上（"费用统计"功能模块的基础）

## Decision

**采用"组织树（PostgreSQL 递归 CTE）+ Hatchet cron + LangGraph interrupt 三段式架构。**

**锁定**：

| 组件 | 实现 |
|------|------|
| 组织树存储 | `agents` 表自引用 `parent_id` + PostgreSQL 递归 CTE |
| 定时触发 | Hatchet cron（ADR-008） |
| 任务派生 | `agent_schedules` 表，父 Agent 的 run 由子 Agent 的 run 派生 |
| 审批流 | LangGraph `interrupt()` / `Command(resume=...)`（ADR-007） |
| 权限继承 | 沿parent_id 链逐级收敛，`min()` 汇总权限等级 |
| 成本归属 | 每个 Agent run 独立记 `agent_id`，费用按 run 归集 |

## Alternatives Considered

### 方案 A：定时触发

#### 方案 A1：Hatchet cron（选中）

**评分：5/ 5**

ADR-008 已选定 Hatchet 作为调度层，cron 是其原生能力。不引入新组件。

#### 方案 A2：Celery Beat

**评分：2.5 / 5**

成熟但需独立进程，且**只能跑一个实例**（多跑会重复调度，需分布式锁）。配置面大。对比 Hatchet 无优势。否决。

#### 方案 A3：APScheduler

**评分：2 / 5**

轻量，适合单进程。但多实例同样会重复调度，且无持久化任务状态（进程重启丢调度）。否决。

#### 方案 A4：PostgreSQL pg_cron

**评分：3 / 5**

| 维度 | 评分 | 依据 |
|------|------|------|
| 依赖 | 5 | 零新增，我们已有 PG |
| 精度 | 2 | **最小粒度 1 秒但实际受 PG 负载影响**，不保证准点 |
| 能力 | 2 | 只能执行 SQL，不能直接调Python 函数做复杂编排 |
| 可观测性 | 3 | job 表可查，但与我们的 run 表割裂 |

否决理由：**能力不足**。pg_cron 只能跑 SQL 表达式，"启动一个 Agent run 并把它挂到队列"这一步仍需自建胶水。且不保证准点——"每天 9:00 上班"如果漂移到 9:03，对老板是可感知的。

### 方案 B：组织树汇报线

#### 方案 B1：自引用 parent_id + 递归 CTE（选中）

**评分：4.5 / 5**

```sql
WITH RECURSIVE org_tree AS (
  SELECT id, parent_id, name, 1 AS depth
  FROM agents WHERE id = :root_agent_id
  UNION ALL
  SELECT a.id, a.parent_id, a.name, t.depth + 1
  FROM agents a JOIN org_tree t ON a.parent_id = t.id
  WHERE t.depth < :max_depth
)
SELECT * FROM org_tree ORDER BY depth, name;
```

| 维度 | 权重 | 评分 | 依据 |
|------|------|------|------|
| 实现成本 | 高 | 5 | 一个字段 + 一个 CTE |
| 层级深度 | 中 | 4 | 递归 CTE 无硬上限（但需设 `max_depth` 防循环引用打爆） |
| 查询性能 | 中 | 4 | 需`parent_id` 索引；层级浅（通常 < 5 层），性能无压力 |
| 权限继承 | 中 | 4 | 沿链收敛即可，但需注意**性能随深度线性增长** |
| 变更灵活性 | 低 | 5 | 改parent_id 即改汇报线，零迁移 |

#### 方案 B2：闭包表（Closure Table）

**评分：3 / 5**

查询任意节点的所有祖先/后代都是 O(1) 范围查询，适合层级很深或需要频繁跨层查询的场景。但需要**维护触发器**保证一致性，且层级变更要批量重写。我们层级浅（< 5 层）、变更不频繁，收益不足。否决。

#### 方案 B3：邻接表 + 应用层递归

**评分：2.5 / 5**

和 B1 本质相同，但递归放 Python 里。可读性略好，但：多次往返数据库（N+1）；递归深度受 asyncio 栈限制；无法在 SQL 层做权限收敛聚合。**比B1 差**，除非有强理由否则不选。

#### 方案 B4：外部 HR 系统集成

**评分：1 / 5**

MVP 阶段不接企业微信/钉钉/飞书的组织架构同步。企业客户通常已有 HR 系统，但我们不能假设他们愿意开放 API。组织树由用户在我们的产品内自建。否决。

### 方案 C：审批流

#### 方案 C1：LangGraph interrupt/resume（选中）

**评分：5 / 5**

ADR-007 已选定LangGraph。其 `interrupt()` 是为这个场景原生设计的，且**支持"人类修改后继续"**——不只是批准/拒绝，可以带着修改意见恢复执行。这是审批流的正确语义（如"小李的账单金额改成X 再发"）。

#### 方案 C2：状态机表 + 人工改状态

**评分：2.5 / 5**

自建 `approvals` 表，状态 `pending → approved/rejected`。问题：审批通过后**如何让原执行流程从暂停点精确继续**？需要自己维护"暂停在哪个节点"的映射——这就是重新实现 LangGraph 的 interrupt。否决。

#### 方案 C3：工作流引擎内置审批节点

**评分：3/ 5**

Temporal /Inngest 等有 human-in-the-loop 原语。但引入它们与 ADR-007/008 的决策冲突（职责重叠）。且它们的审批模型通常不支持"带修改恢复"。否决。

## Consequences

### 正面

- **三段职责清晰**：Hatchet 管"何时上班"，组织树管"向谁汇报"，LangGraph 管"如何暂停等审批"，三者不重叠
- **组织树零迁移**：改 parent_id 即改汇报线
- **审批语义正确**：支持"带修改恢复"，这是真实审批场景的核心需求
- **成本可归集**：每个 Agent run 独立记 `agent_id`，"费用统计"功能模块直接可用

### 负面

**必须内嵌 Spec 的六条约束：**

1. **【最高风险】审批等待必须有超时兜底**。老板可能永远不点批准。必须设计：审批超时（如 7 天）→ run 标记为 `expired` + 通知老板。**不允许永久`waiting_approval` 状态**

2. **必须防止组织树循环引用**。A的 parent 是 B，B 的 parent 是 A 会导致递归 CTE 死循环。硬约束：`parent_id` 设置时校验"目标祖先链中不含自己"；递归 CTE 额外设 `max_depth`（建议 10）

3. **员工停用时在途任务的处理必须明确**。三种策略：立即终止 / 跑完当前任务再停 / 转移给上级。MVP 采用**跑完当前任务再停 + 新任务不再派发**，语义最安全

4. **权限继承必须收敛而非放大**。子 Agent 权限 = min(自身权限, 所有祖先权限)。用数值等级（`viewer=1 < member=2 < admin=3 < owner=4`）取 `min()` 即可。**绝不能出现子Agent 权限大于父 Agent 的情况**

5. **循环依赖是真实风险**。小陈审批 → 唤醒小李 → 小李产出 → 需小陈再审批 → 若 ID 或判断写错就是死循环。硬约束：图编排层设全局最大迭代次数（建议 20），超出即标记 `abnormal` 并告警

6. **组织树查询必须有 `parent_id` 索引**，且递归 CTE 必须设 `max_depth`。无索引时树形查询随数据量线性劣化

### 中性：不做的事

MVP 阶段明确不做：

- 不与企业微信/钉钉/飞书的组织架构同步（用户自建）
- 不做跨租户的组织树（一个租户一棵独立的树）
- 不做多级汇总的自动合并（老板的周报需人工汇总，MVP 只做"按员工筛选查看产出"）
- 不做 Agent 之间的消息传递（只有"派发任务"和"汇报产出"两种关系，不做 IM 式通信）

## Verification

**存在性核验**：

```bash
psql -c "CREATE INDEX idx_agents_parent_id ON agents(parent_id);"
```

**端到端验证步骤**：

1. **组织树正确性**：建 3 层树（小王→小陈→老板），断言：递归 CTE 返回 3 个节点，depth 分别为 1/2/3
2. **循环引用阻断（阻断级）**：
   - 尝试设置 `小陈.parent_id = 老板`（正常）
   - 尝试设置 `老板.parent_id = 小王`（形成环）
   - 断言：**报错拒绝**，数据库中 parent_id 未被修改
3. **max_depth 兜底**：构造 15 层深树，断言：递归查询在 depth=10 处停止，**不返回全部 15 层，无死循环**
4. **权限收敛（阻断级）**：
   - 父 Agent 权限 = `member`(2)，子 Agent 权限 = `admin`(3)
   - 断言：子 Agent 的**有效权限 = member(2)**，不是 admin(3)
5. **cron 触发**：配置"每天 9:00"，断言：连续 3 天各触发一次，无漏无重；断言：9:00 触发时间偏差 < 60 秒
6. **审批流核心用例**：
   - 小李生成账单 → `interrupt()`
   - 断言：run 状态 = `waiting_approval`，且 `approvals` 表有一条 pending 记录
   - 执行 `Command(resume={"action": "approve", "amount": 9800})`（**修改金额**）
   - 断言：小李从**暂停点**继续执行，发出的账单金额是 9800（修改生效）
7. **审批超时兜底（阻断级）**：
   - 创建一条 pending 审批，模拟 7 天后
   - 断言：run 被标记为 `expired`，owner 收到通知
   - 断言：**无run 永久停留在 `waiting_approval`**
8. **循环依赖兜底**：构造互相审批的场景，断言：达到最大迭代次数（20）后标记 `abnormal` + 告警
9. **停用员工**：小李在跑任务时被停用，断言：当前任务跑完，但新任务不再派发给小李
10. **成本归集**：断言：`usage_records` 表能按 `agent_id` 汇总出小王的 token 花费，且不计入老板

第 2、4、7 条为阻断级。
