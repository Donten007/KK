## 变更一：恢复竞品监控日报为岗位 #1（推翻 2026-10-14 裁决）

### 原裁决（作废）
> **只做客户自有域名，不抓第三方公开网页。**
> 代价：竞品监控岗位必须替换为「客户跟进催办」。

### 新裁决
> **恢复竞品监控日报为 MVP 岗位 #1。L1 抓第三方公开网页，四条护栏一条不减。**

### 推翻理由
1. **对客户价值**：中小企业老板付费的核心理由就是「看看同行在干什么」。砍掉这个，最直观的价值感知消失。
2. **法律风险被高估**：抓公开网页在中文法律语境下是常规商业行为（比价、竞品监控、舆情监测均属此类）。**真正的风险点不是「抓了」，而是「伪装」和「绕过」** —— 而四条护栏恰好封死了这两条。
3. 架构师 ADR-014 原方案（服务端 HTTP 抓取 + G1-G4 护栏）**恢复**，无需改版。

### 保留不变的四条护栏（G1-G4）
| 护栏 | 要求 |
|------|------|
| G1 robots.txt 合规 | Disallow 命中即跳过，**不允许绕过** |
| G2 频率限制 | 单域名 ≥2s、单租户 ≤20rpm、全局 ≤200rpm，**服务端强制**不靠 Agent 自觉 |
| G3 UA 声明 | `OPCAgentAI/1.0 (+URL; contact=...)`，**不伪装成浏览器** |
| G4 抓取失败显式化 | 抓取失败/被 robots 拒绝/内容为空，**必须显式告知，禁止返回空日报冒充成功** |

**G4 不许因范围扩大而放松** —— 竞品监控最危险的失败不是「抓不到」，而是「抓不到但报告说今天没有异常」，老板会据此决策。

### 连带修订
- 岗位顺序表 §8.2：「竞品监控日报」恢复 #1；「客户跟进催办」降为 #2
- §8.4 判据分组：恢复「外部依赖类（竞品监控）TCR ≥70%」分组，与「内部文档/表格类 ≥85%」**并列独立判定**，任一组不达标即整体 No-Go，不做加权平均
- 法务文本第七章恢复「L1 抓第三方」合规姿态（我们是直接请求方，责任在平台侧）
- 销售话术：「自动盯竞品」**恢复为允许表述**（G1-G4 护栏已在，法律敞口可控）

## 变更二：删除充值代付，改为纯 BYOK + 线下收款（新增决策）

### 用户原话
> 「不要考虑充值问题，只要能在saas 系统里做出客户公司账套号区分，可以线下收款开户」

### 变更内容
| 项目 | 原方案 | 新方案 |
|------|--------|--------|
| 模型接入 | BYOK + 平台代付双通道 | **纯 BYOK 为主 + 平台代理 Key（线下签约配置）** |
| 充值系统 | 有（赠送额度池 + 预占-确认-释放账本） | **无** |
| 赠送额度池 | ¥5,000/月上界 | **删除** |
| 设备指纹采集 | 需要（防薅羊毛） | **删除** |
| 风控防薅羊毛 | 需要 | **删除** |
| 收款方式 | 线上充值 | **线下签约 + 线下收款 + 后台配额度** |

### 这个变更关掉了两个法律敞口
1. **「不采集 IP」的承诺不再有裂缝** —— 设备指纹采集是为了防薅羊毛，没有充值就没有薅羊毛，矛盾源头消失。隐私承诺可理直气壮表述，**法务文本第四章（设备指纹四条边界）可整章删除**。
2. **不做资金托管** —— 收了钱就是收了钱，不存在「用户充的钱未消费完就退款」的纠纷。对要收预付款的商业产品，这是显著简化。

### 「平台代付成本上界」决策自动作废
该待决策项依赖赠送额度池，池子删除后问题不复存在。**无需再核定数值。**

### 技术影响
- `credentials` 表新增 `kind = 'platform_proxy_key'` 类型（与客户自带 Key 同一条代码路径，仅计费来源不同）
- `credit_ledger` 预占-确认-释放两阶段账本可简化为**仅记录不拦截**（额度由线下谈判决定，无需实时拦截）
- 删除：赠送额度池管理、风控模块、设备指纹采集与存储
- 保留：预算闸门（但语义变化，见下）

### 预算闸门语义变化（重要）
| | 原语义 | 新语义 |
|---|------|----------|
| 预算闸门 | 平台防止代付额度被烧光 | **客户防止自己的 API Key 账单超支** |
| 价值主张 | 平台止损 | **帮客户盯住他自己的模型账单** |
| 触发后行为 | 任务不执行 + 通知 | **任务不执行 + 通知 + 提供加额指引（引导联系客户经理）** |

**这个语义转变不削弱卖点，反而强化了。** Manus 差评最高频就是「成本不可预期」，BYOK 客户同样面临这个问题（他自己的 DeepSeek 账单也会烧）。闸门从「平台止损」变成「帮你盯自己的钱」，**用户价值感更强，且平台零资金风险**。

### 首次接入摩擦的处理（待定，需用户或架构师选）
客户第一次用要自己填 API Key，这是流失点。三方案：
- **A引导页 + Key 检测**：注册后先弹「连接你的模型」引导页，列供应商 + 3 步图文说明
- **B 自带小体验额度**：首次赠 20-50 次调用（需垫资，与「不做充值」冲突，慎选）
- **C 平台代理 Key（推荐）**：客户可线下签约后由平台配额度，无需自己弄 Key。**额度线下谈，不做线上充值系统。** 技术上仅需在 `credentials` 加一个 kind，逻辑与 BYOK 同路径

**倾向 C**：既解决 B 的问题（客户不用自己弄 Key），又不引入充值系统复杂度。

## 变更三：配色维持现状（确认，不是变更）

**维持青蓝 `#29B6D6`（深色）/ `#0C6F86`（浅色），色相 191°。不换。**

理由：已通过 WCAG 2.1 实测 + 四种色觉障碍模拟。PM 曾提「墨玉沉金」偏绿/偏金方向，会与 success 绿撞车 —— 而 success 绿承载「已完成」这一最核心状态的语义。**为品牌调性牺牲状态可辨识性是本末倒置。**

换配色成本在 CSS 变量，随时可换。**建议 Phase 2 视觉细化时再看。**

## 一条记录

本次变更源于用户复看自己的裁决后发现「只做自有域名」与产品意图不符。**这说明 MVP 范围的商业侧决策（客户为什么付费）不应由技术可行性反推** —— 技术约束应告知商业决策的影响，但不能让技术可行性单独决定产品做什么。

「只做自有域名」在技术上完全可行（甚至更安全），但它在商业上是自废武功。**技术负责说清代价，最终判断商业价值。**
