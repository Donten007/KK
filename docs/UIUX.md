## 0. P0 红线自检（本方案的合规声明）

| 红线 | 本方案如何满足 |
|---|---|
| 禁止 emoji 作功能图标 | 全文零 emoji。图标统一走 Lucide 描边 SVG，见 §6 |
| 禁止紫→粉渐变主视觉 | 主色为**青蓝 `#0C6F86` / `#29B6D6`**（hue 191°），与紫(270°)/粉(330°) 距离 > 79°，物理上不可能构成紫粉渐变。全文无任何品牌色渐变 |
| 禁止空洞占位文案 | §7 核心页面构想中所有文案均为**真实业务内容**（具体岗位名、具体数字、具体报错） |
| 禁止硬编码颜色 | §3 全部色值均为 Token，组件层禁止裸 hex（唯一例外 `#fff`/`#000`） |
| 禁止千篇一律Hero | 登录页展示**真实工作台预览**（真实智能体运行中状态），非「大标题+副标题+居中CTA」 |
| 禁止弹跳缓动 | 全局禁用 `cubic-bezier(0.68,-0.55,0.265,1.55)`，缓动仅 3 条，见 §5 |
| 禁止侧条纹边框 | 全文档无 `border-left/right > 1px` 彩色强调 |
| 禁止渐变文字 | 无 `background-clip:text` |

## 1. 设计语言定位

> **一句话：把「管理一支 AI 团队」做成一台精密仪器——每个数字都可追溯，每个员工都在你能看见的状态里。**

### 1.1 寄存器判断：**Product 寄存器**

按 `design-commands.md` §1 判定：路径形态为 `/app/*`（工作台、员工管理、任务中心），用户为企业决策者+一线使用者，交付物是工具界面而非营销页。

**判据结论**：Linear/Figma/Notion/Raycast 的熟手用户（我们的目标用户画像正是这类人——他们日常用飞书/钉钉/企业微信）坐下来应当**立即信任**这个界面，不需要在任何一个组件上停顿。

由此确定：
- 调色板策略 = **Restrained**（强调色仅用于主操作、当前选中、状态指示）
- 字体 = 一族为主（display 与 body 同族），固定 rem 阶梯
- 动效 = 150–250ms 状态传达，**无开场编排动画**（Product 寄存器明令反对 page load choreography）

### 1.2 三轴刻度（本次标定）

| 刻度 | 值 | 依据 |
|---|---|---|
| `DESIGN_VARIANCE` | **4** | 老板用户要的是"看得懂、放心"，不是设计奖。结构可预测 > 视觉惊喜。仅在工作台允许分数单位网格做轻度非对称（如 2fr 1fr），强制对称布局在核心业务页 |
| `MOTION_INTENSITY` | **3** | 「克制专业」。仅 3 类动效：状态切换、进度推进、面板进出。无装饰性动效、无滚动入场 |
| `VISUAL_DENSITY` | **6** | 中间偏密。任务中心/员工列表这类"监看"页面用紧凑表格（VISUAL_DENSITY 7 的行为：仅 1px 分隔线、无卡片盒子）；会话/知识库这类"阅读"页面放松到 5 |

## 2. 对标品牌分析（2+1）

### 2.1 主对标：**Linear** — 借"密度即签名"

**借什么**：
- **暗色原生（dark-native）而非暗色模式**——Linear 的深色不是"浅色主题加个滤镜"，是背景即产品。这对本项目至关重要：AI 员工的**值班状态、实时日志、长任务运行**在暗色底上更可信，像监控台而非办公文档。
- **4px 基准 + 4/6/12 圆角阶梯**——我们照抄。Radius 大=廉价，Radius 小=精密。
- **1px 边框 + inset 阴影制造深度，而非 drop shadow**（这是本方案 §4 质感规则的核心）
- **Inter 的 510 字重**（regular 与 medium 之间）——我们采用，因为它是"强调但不喊叫"的层级手段
- **微交互 scale(0.97)**：按下态 97% 缩放，80ms。我们的采纳值见 §5

**不借什么**：Linear 的紫（`#5E6AD2`）。本产品主色走青蓝（§3.3），理由见3.3。

### 2.2 副对标：**Stripe Dashboard** — 借"数字的排版纪律"

**借什么**：
- **表格里所有数字用 `font-variant-numeric: tabular-nums`**，右对齐。老板看用量/成本/工时，数字必须能竖着对齐扫读——这是 Stripe 让人信任的核心。
- **分层账单式信息架构**：用量计费页用"分组小计 → 总计"的层级，不是平铺一堆数字。
- **语义色克制**：Stripe 用蓝(品牌)/绿(成功)/红(危险)/中性(其余)，其余全部灰。我们同构。

### 2.3 参照：**Retool** — 借"表格就是主界面"的纪律

Retool 的 `DesignMD` 明确写了一条反模式：**"Do not apply box-shadow to any element; the system is flat"**。它靠 z-index + 颜色 + 排版 + 间距建立层级。

我们不完全照抄（我们要「有质感」，纯 flat 会显得寡淡），但采纳它的**表格纪律**：员工列表、任务列表、资产列表一律表格优先，`px-3 py-2` 单元格、`h-9` 工具栏行、`gap-2`。

### 2.4 为什么不是 Vercel / Notion

- **Vercel**：黑白极端克制 + 大量 radial-gradient 装饰 + spring 动效。这套语法在开发者品牌站成立，但用于"管理 AI 员工"会显得**太冷、太技术、太不透明**——老板需要的是"我的员工在干什么"的**确定感**，不是极客审美。
- **Notion AI**：氛围友好但**密度不足**。员工/任务管理是监看场景，老板要一屏看到 20 个员工的状态。Notion 的宽松排版会浪费一半屏幕。

### 2.5 借 Manus 的「执行可视化」（非对标品牌，但必须借其模式）

调研中最重要的单条发现（Manus UX teardown）：

> *"Autonomous agents fail when users feel blind. Manus exposes file edits and elapsed time to justify credit spend and build trust that work is happening off-screen."*

对本产品的直接含义：**「AI 员工正在做什么」必须是一个一等公民界面元素**，不能只在会话里显示一行"处理中"。具体到我们的产品 = 员工卡片上必须有：
- **实时状态点 + 当前动作动词**（如"正在检索：客户合同模板"）
- **本班次累计运行时长 + 已完成/总任务数**
- **可中断**（running 状态下有停止入口）

这不是"科技感装饰"，是**信任基础设施**——对应本产品的核心商业承诺（老板按结果付费）。

## 3. 配色系统（完整 Token 列表 + 实测对比度）

### 3.1 设计依据：为什么主色是青蓝而不是靛蓝

我用脚本实测了候选色的**色相距离**（避免主色与 success绿撞车）：

| 候选主色 | hex | 色相 | 与 success绿(150°)色相差 | 深底对比度 |
|---|---|---|---|---|
| teal | `#14B8A6` | 173° | **23°** (否决) | 7.83:1 |
| cyan | `#29B6D6` | **191°** | **41°** (通过) | 8.12:1 |
| indigo（Linear） | `#5E6AD2` | 239° | 89° (通过) | — |

**teal 被否决**：色相仅差 23°，在红绿色盲下主色与"任务成功"绿几乎无法区分——而"这个员工的任务完成了吗"正是本产品最核心的状态语义。用一个看不清的状态色去做状态驱动型产品是致命错误。

**青蓝 `#29B6D6` / `#0C6F86` 通过**：41° 色相间隔 + 亮度不同，是 CVD 安全的选择。

### 3.2 实测验证方法（可复现）

所有对比度用 WCAG 2.1 相对亮度公式实算（`L = 0.2126R+0.7152G+0.0722B`，`ratio=(L_light+0.05)/(L_dark+0.05)`），并额外跑了色盲模拟（deuteranopia/protanopia/tritanopia/achromatopsia）。**不是目测，是算出来的。**


> **浅色主题调色过程中发现并修正的问题**：初版选`#667479` 作 muted、`#0E7C96` 作 accent，在 `surface-2 #EFF3F3` 上分别只有 4.33:1 —— **不达AA**。已下调为 `#616E73`/`#0C6F86`，现最差情况 4.71:1 仍为 AA。这个坑记录在此提醒 Phase 2：**色值必须在最深的那层表面上也验一遍，不能只验白底。**

### 3.5 [P0] 状态色不可单独承载语义（P0 无障碍硬约束）

色盲模拟实测发现 —— **红绿色盲下 `--warn #E39A2E` 与 `--danger #F0555A` 模拟后对比度 1.00:1，即完全同色。** 全色盲下5 个语义色全部坍缩为灰。

**因此强制规则**：

> 任何状态**必须**同时具备三个通道：**颜色 + 图标 + 文字**。
> 禁止仅用色点/色条表达状态；禁止 `border-left:3px solid <语义色>` 表达状态。

实现映射：

| 状态 | 颜色 | 图标（Lucide） | 文案（必须有） |
|---|---|---|---|
| 运行中 | `--accent` | `Loader`（旋转） | 「运行中」 |
| 空闲/待命 | `--muted` | `Pause` | 「待命」 |
| 成功 | `--success` | `CircleCheck` | 「已完成」 |
| 警告 | `--warn` | `TriangleAlert` | 「需关注」 |
| 失败 | `--danger` | `CircleX` | 「失败」 |
| API 预算超限 | `--warn` | `CircleDollarSign` | 「API 预算用 82%」 |

### 3.6 语义色 vs 品牌色的隔离

`--success`(150°) / `--warn`(36°) / `--danger`(358°) / `--info`(232°) / `--accent`(191°) 相邻色相间隔分别为 114° / 38° / 126° / 41°，全部 ≥30°。CVD 安全性由 §3.5 的三通道规则兜底。

### 3.7 强调色配额

**每屏 `--accent` 可见使用 ≤2 处**，仅允许：主CTA 按钮、当前选中 Tab/行、以及最重要的那一个数据高亮。标题永不用强调色。

## 4. 质感规则（"高级感"到底从哪来）

> 这一节是本项目的核心。用户要"有质感"，但质感不是阴影和圆角。下面 8 条是**可执行的决策规则**，每条都给了「怎么做 / 为什么」。

### 规则 1 — 层级用「1px 边框 + 亮度递进」，不用投影

- **做法**：深色主题下层级靠 surface 亮度递进实现：`bg #0B0D0E` → `s1 #111618` → `s2 #171D20` → `s3 #1F2629`，每级仅差 1.07:1 亮度（**极微**，靠累积可辨，单级不可感——这是 Linear 的手法）。需要边界时加 1px `--border`。
- **为什么**：投影是有方向的，它暗示"光从上面来"，在多层级界面里会造成视觉噪音和"贴纸感"。亮度递进无方向，永远成立。**唯一例外**：真正的浮层（Popover/Modal/拖拽层）才用一层 `0 8px 24px rgba(0,0,0,0.4)` + `inset 0 1px 0 rgba(255,255,255,0.06)`。

### 规则 2 — 卡片的唯一合法形态

```css
/* 唯一允许的卡片 */
.card {
  background: var(--surface-2);
  border: 1px solid var(--border);
  border-radius: var(--radius-md);   /* 8px */
  /* 无 box-shadow */
}
/* 交互卡片才允许 hover 反馈 */
.card-interactive:hover { background: var(--surface-hover); border-color: var(--border-strong); }
/* 选中态用 accent 描边，不用左侧色条 */
.card[aria-selected="true"] { border-color: var(--accent); }
```

**禁止**：`border-left:3px solid <color>`（AI 设计特征）、24px+ 大圆角、卡片嵌卡片、投影卡片。

### 规则 3 — 数据密度：表格优先，卡片是例外

员工列表、任务列表、资产列表、用量明细这四类页面 → **表格**：
- 单元格 `padding: 8px 12px`，行高 40px
- 表头 `--fg-2` / 12px / `letter-spacing:0.06em` / 全大写
- 行分隔用 1px `--border`，**不用斑马纹**（斑马纹是廉价感的主要来源）
- hover：`background: var(--surface-hover)`
- 数字列：`font-variant-numeric: tabular-nums` + 右对齐

**判定规则**：一页里 ≥5 个同类结构化对象 → 用表格；<5 且需要图片/富描述 → 用卡片。混用禁止。

### 规则 4 — 字体层级用「三级字重 + 三级字号」，不是靠加粗

- **字重只有 3 档**：`400` 正文 / `510` 小标题与表格头 / `590` 页面主标题。禁止 700 及以上（那是营销页的东西）。
- **强调顺序**：先改字号 → 再改字重（510）→ 最后才用颜色。**禁止**用强调色写标题。
- **等宽字体承载所有标识类信息**：员工 ID、任务 ID、Token 消耗数、时间戳、成本金额 → `--font-mono`（JetBrains Mono）。这是"精密仪器"感的重要来源——数字对���齐、ID 有辨识度。

### 规则 5 — 留白比例：组内紧，组间松

- 同组元素间距 8px；标签与控件 6px；卡片内边距 16px；卡片之间 12px；**页面主区块之间 48px**。
- **硬规则**：留白节奏必须是「小—小—大」的对比序列。若所有间距相等，界面就没有层级可言。
- 内容最大宽度：会话区 `max-width: 720px`（约 65 中文字符），其余页面不限但用 12列栅格控制。

### 规则 6 — 深度只用两级，且必须有理由

| 级别 | 用在哪 | 表现 |
|---|---|---|
| L0 平 | 95% 的界面 | 无投影，1px 边框或无边框 |
| L1 浮 | Popover / Modal / Toast / 拖拽中元素 | `0 8px 24px rgba(0,0,0,.4)` |

只有两级。不存在 L2。禁用毛玻璃装饰（`backdrop-filter` 仅允许用于 Modal 遮罩 `backdrop-blur:2px` 且必须配 `rgba(0,0,0,0.6)`）。

### 规则 7 — 动效只做三件事

1. **状态确认**（150ms）：状态点变色、按钮按下 `scale(0.98)`、勾选框填充
2. **因果关系**（200ms）：面板展开/收起、抽屉进出
3. **持续进行**（1000ms循环）：运行中智能体的脉冲点、进度条推进

**禁止**：入场 stagger 编排、滚动淡入、装饰性 hover 缩放、任何弹跳/回弹缓动。

### 规则 8 — 「密」与「松」按页面职能分配

| 页面 | 密度 | 留白 | 理由 |
|---|---|---|---|
| 工作台/会话 | 松（5） | 大 | 老板在这里读内容 |
| 员工管理 | 中（6） | 中 | 浏览+ 偶尔配置 |
| 任务中心 | 密（7） | 小，1px 分隔线为主 | 监看场景，一屏要看到 20 个任务 |
| 知识库/资产 | 中（6） | 中 | 表格为主 |
| 用量计费 | 密（7） | 小 | 数字对齐扫读优先 |
| 登录注册 | 中（6） | 中 | 不干扰，不炫技 |

> 密度切换是**页面级**的，不是全局的。混用会让产品显得没有系统。

## 5. 基础规范：间距 / 圆角 / 字号 / 动效

### 5.1 间距（4px 网格，仅允许这些值）

```
--space-1:4px    --space-2:8px    --space-3:12px   --space-4:16px
--space-5:20px   --space-6:24px   --space-8:32px   --space-12:48px
```

## 6. 图标库选型

### 6.1 锁定：**Lucide**

| 维度 | Lucide | Tabler Icons | Phosphor | Heroicons |
|---|---|---|---|---|
| 许可 | **ISC**（与 MIT 等效，可商用免署名） | MIT | MIT | MIT |
| 图标数（独立概念） | 1,778 | **6,143** ⭐ | 1,527 | ~300 |
| 绘制模型 | 2px 描边 / 24 网格 | 2px 描边 / 24 网格 | **填充路径** / 256 网格 | 描边+实心双版 |
| 字重控制 | 单一（stroke-width 可调） | 描边+填充双版 | **6 字重** ⭐ | 2 版 |
| 中文语境生态 | React/Vue/Next 全覆盖，社区最大 | 有 wrapper | React/Vue/Flutter | Tailwind 官方 |

**选 Lucide 的理由**：
1. **描边风格与我们的 1px 边框语言一致**——填充型图标（Phosphor）在深色底上会显得"重"，破坏 Linear 式精密感。
2. **单字重 = 不会出现混用混乱**。Phosphor 的 6 字重听起来灵活，实际是每个图标都要做一次决策，小团队必然选乱——这是反模式。
3. **ISC 许可，商用零风险**，与 architect 的选型不冲突（见 §6.3）。
4. React/Vue 官方包 tree-shaking，按需引入。

### 6.2 尺寸规范（锁定，全项目一致）

| 用途 | 尺寸 | stroke-width |
|---|---|---|
| 行内（表格内、文本前缀） | **16px** | 1.5 |
| 按钮内、导航项 | **20px** | 1.5 |
| 独立图标、状态点、员工头像内 | **24px** | 1.5 |

**关键规则**：
- 所有图标 `stroke="currentColor"`，`fill="none"`——颜色由父级文字色继承，禁止给图标单独设颜色 token（除状态图标，且必须配文字，见 §3.5）
- **禁止 emoji 替代图标**（P0）。语义映射示例：智能体→`Bot`、员工岗位→`Briefcase`、值班→`CalendarClock`、知识库→`Library`、计费→`Receipt`、组织架构→`Network`、排班→`CalendarDays`、知识检索→`Search`
- Lucide 1.0 已移除品牌图标→ 如需模型 logo，用 Simple Icons（CC0）单独引入，**不与 UI 图标混排**

### 6.3 与 architect 的对齐结论（已达成一致）

**architect 已独立选型 `lucide-react@1.57.0`，与设计侧结论一致，本节按双方共识定稿。**

**唯一例外：Simple Icons（CC0）**，用于模型 logo 等品牌展示场景。三条约束**同时**满足才允许使用：
1. 只在模型选择器这类**品牌展示**场景
2. 限定独立目录 `components/brand/`
3. **不与 Lucide UI 图标在同一视图并排出现**

理由：规则的价值在于「没有例外」，一旦开口子就会扩散。上面第 3 条是防止两套风格同屏的关键。

#### 缺口处理：整体换库，而非双库并存

architect 提出的方案我接受并已采纳——**我原先建议的「Lucide 为主 + Tabler 补缺」被否决**，否决理由充分：

- 两套包意味着两套版本升级节奏、两套 tree-shaking 行为、两套 `node_modules`
- 新人加了 Tabler 的 import 无人拦截，半年后必然失控
- 两库同为 2px 描边 / 24 网格，**整体切换的视觉成本近乎为零**

**定稿规则**：预估图标缺口 > 20 个 → 整体换Tabler，**不接受双库并存**。

对 PRD 5 个岗位的覆盖判断（architect 已核实）：电商订单录入 /竞品监控日报 / 客户跟进催办 / 周报汇总 / 发票信息核对，均属通用业务语义（文件、表格、日历、搜索、图表、通知），**Lucide 全覆盖，不会缺**。

#### 7.5.1 协作式取消的「正在中止」中间态（架构侧需求，设计侧规范）

architect 的方案是**协作式取消**（asyncio task cancel + 状态落盘，已完成步骤保留且不扣费）。这带来一个 UI 必须解决的问题：

> **协作式取消不是瞬时的。** 用户点击「中止」到真正停下来有 1–3 秒延迟。这段时间若无反馈，用户会以为按钮坏了而**重复点击**——重复取消请求可能引发状态机竞态或重复落盘。

**核心设计决策：引入独立的 `stopping` 中间态，它是第五个状态，不是「运行中」的子状态。**

状态机（UI 侧）：
```
queued → running → stopping → cancelled
                    └────────→ completed   (在中止生效前恰好跑完)
```
关键：`stopping` 不能复用 `running` 的视觉。若沿用旋转图标，用户会以为任务还在跑而更用力点；若直接跳到 `cancelled`，用户会以为已中止而关掉页面，实际后台还在收尾。

**「正在中止」的视觉规范**：

| 元素 | 规范 | 理由 |
|---|---|---|
| 图标 | `CircleDashed` + **1.2s 循环旋转**（区别于 `running` 的 `LoaderCircle`） | 虚线语义 =「正在收尾，非推进」；`LoaderCircle` 保留给真正推进中的任务 |
| 状态文字 | **「正在中止…」**（带省略号） | 省略号暗示过程未完成，与瞬时态区分 |
| 中止按钮 | **立即变为 disabled + 文案「中止中」** | 关键：按钮必须**当场响应**，不给用户第二次点击的余地 |
| 进度条 | **立即停止推进动画，填充层切为 `--muted` 并静止** | 视觉上「不再前进」是中止完成的最强信号 |
| 已完成步骤 | **保持原样，不回滚、不置灰** | 对应架构侧「已完成步骤保留且不扣费」——用户必须看到之前的成果还在 |
| 禁止 | 不用 `--danger`、不用 `OctagonX`、不弹模态 | 中止是用户主动的正常操作，不是错误 |

**「正在中止」最长展示 5 秒**：超时则降级为 `cancelled` 并在抽屉内提示「已请求中止，后台正在收尾；已完成步骤已保存」。保证 UI 永不卡在中间态。

**幂等要求（给 architect）**：重复的取消请求必须返回同一状态而非报错，且 UI 的 disabled 按钮是最后一道防线。建议后端对同一 taskId 的 cancel 做幂等处理。

**空/边界情形**：
- 点击中止时任务**恰好完成** → 直接进 `completed`，不闪`stopping`
- 任务已在 `queued` 未启动 → 直接 `cancelled`，无中止延迟
- 已 `cancelled` 的任务再次点击中止 → 按钮本就不出现

#### 7.5.2 实时日志的三级分级（架构侧 7 种事件类型的 UI 归属）

architect 的架构有 7 种事件类型，但未定「哪些进 UI、哪些只进审计日志」。设计侧的分级原则：

> **分界线：这件事老板需不需要知道？** 需要 → 进 UI；不需要 → 只进审计日志（可查但不打扰）。

| 级别 | 内容 | UI 呈现 | 事件类型举例 |
|---|---|---|---|
| **L1 主叙事**（默认可见） | 任务级里程碑 | 会话流/抽屉时间轴上的**一行摘要** | `task_started` `step_completed` `task_completed` `task_failed` `needs_human_input` |
| **L2 细节**（点击展开） | 单步的输入输出、耗时、命中的文档名 | 折叠的时间轴节点，展开后显示 | `tool_called` `retrieval_hit` `file_written` |
| **L3 审计**（仅管理员可见） | 原始 prompt / 完整响应体 / 重试记录 / token 明细 | **老板界面绝不出现**；仅 `/settings/usage` 与后台可查 | `raw_prompt` `raw_completion` `retry_attempt` `token_usage` |

**这条分界线的商业理由**：L3 一旦出现在老板界面，产品立刻被重新归类为「开发工具」（与 §8.1 同源逻辑）。所以**不是「不显示」，而是老板界面的接口层不接收**（见 §8.4）。

UI 呈现规则：
- L1 每条一行，`14px/--fg-1`，左侧 2px `--border-strong` 竖线作时间轴（结构线非彩色）
- L2 默认折叠，标题行显示「检索了 12 条 · 1.4s」，展开后进详情区
- **禁止**在 L1 里显示 `[INFO]` / `elapsed=` / token 数——这是 §8.1 禁止的系统日志语汇
- L3 折叠区标注「仅管理员可见」

- 检索结果页：引用块用 `Quote` 图标 + 左侧 2px `--border-strong` 竖线（结构线，**非彩色**，符合红线）+ 来源文件名 + 相似度分数（等宽数字）
- 空状态要具体：「上传第一份产品手册后，员工回答客户问题时会引用原文，而不是凭记忆作答」

### 7.7 用量计费（密度 7）

借鉴 Stripe Dashboard 的数字排版纪律。

**布局**：
1. **顶部 4 个KPI**（不是 4 个孤立卡片，而是 1 个 `--surface-2` 容器内用 1px 竖线分4 格）：
   `本月总 Token` / `本月总成本` / `任务完成数` / `当前套餐`
   数字 24px/590/等宽，带 `+12.4%` 环比（**纯文字 + 语义色，不用 pill 徽章**）
2. **用量趋势图** — 面积图，单色 `--accent` 15%→0% 渐变（这是功能性的，不是装饰）。**禁用饼图**
3. **按员工用量表格** — 员工 / Token / 成本 / 占比条（水平条，非饼）/ 环比
4. **账单记录** — 日期 / 描述 / 金额 / 状态 / 发票下载

- **成本预估入口**：在智能体配置页显示「按当前用量，此员工预计月耗 ¥1,240」——**用真实预估数字**，非「节省 30%」类虚构指标
- 付费墙设计：达到配额 80% 时，页面顶部出现 `warn` 条 + 图标 + 文字「本月额度已用 82%，预计 3 天后用尽」+ 「升级套餐」按钮。**不弹模态打断**

## 8. 信任链界面（PM 反馈补充，Phase 1 追加）

> 本章回应 PM 在PRD 走查中指出的两个设计缺口。共同前提：**这两个页面是本产品的信任命门，它们的设计目标不是"信息完整"，而是"让老板敢把下一批活交给它"。**

### 8.1 试跑结果页（密度 4，试跑/汇报类页面中最松）

**与任务中心抽屉的本质区别**（这是本节最重要的一条）：

| | 任务中心抽屉 | 试跑结果页 |
|---|---|---|
| 回答的问题 | 「出了什么问题」 | 「这员工靠不靠谱」 |
| 面向 | 排查者 | 老板 |
| 密度 | 7 | **4** |
| 数字风格 | 等宽 + Token 明细 | **`font-body` + 无 Token 字样** |
| 语气 | 系统口吻 | **员工口吻** |

**核心决策：试跑结果页禁止出现「Token」这个词。** Token 是工程语言；老板看到 Token 会把产品重新归类为「开发工具」，而我们卖的是「员工」。这不是文案问题，是**认知分类问题**——一旦归类为开发工具，老板对价格的容忍度会骤降。

#### 区块一：干了什么（业务语言步骤流水）

**用"员工工作日志"的语法，而非"系统日志"的语法。** 具体做法是三处替换：

| 系统日志写法（禁止） | 员工日志写法（采用） |
|---|---|
| `14:32:05 [INFO] search_knowledge(query="2026Q3渠道") → 12 results (1.4s)` | `14:32  查了「2026Q3 华东渠道台账」，找到 12 条相关记录` |
| `tool_call: spreadsheet_write(file="日报.xlsx") success` | `把结果整理进了「竞品日报-0912.xlsx」` |
| `[done] elapsed=8m23s tokens=14,208` | `这一趟花了 8 分 23 秒` |

- 每行 = `时间(11px/muted, tabular) + 业务动作(14px/fg-1)`，行高 32px
- **行距宽松**（这是密度 4 的主要来源），行间**无分隔线**，仅靠行距分组
- 每段之间空16px，用 `--fg-2` 的小标题分段（如「收集信息」「整理与核对」「产出」）
- **不用等宽字体**——等宽字体是技术感的最大来源。业务日志用 `--font-body`

#### 区块二：干得怎么样（待确认记录）

见 §8.2，这是独立设计的组件，不内嵌在流水里。

#### 区块三：花了多少钱（显眼但不像账单）

PM 的顾虑我完全接受：「成本区块要显眼但不能像账单，否则老板第一屏看到成本明细，会觉得这东西是给工程师用的。」

**解法：成本不作为独立区块，而作为一句嵌入式的业务结论。**

```
─────────────────────────────────────
这一趟试跑的成本

生成这份日报，你的模型账单多了 1.2 元。
按这个节奏，一名市场专员一个月约 36 元。
                     [ 查看成本明细 → ]
─────────────────────────────────────
> **[纯 BYOK 语境变更]** 「花了 1.2 元」的主语必须是**客户自己的模型账单**，不是平台账单。
> **禁止**出现「你的平台额度」「充值」「余额」——产品已删除代付功能（2026-10-15 用户裁定）。
> 口径可对齐 PRD 销售话术：「我们不赚你模型费的钱，也不碰你的模型账户。**我们只帮你盯着别烧超。**」
```

设计要点（**每条都是"不像账单"的具体手法**）：

1. **不用表格**。账单 = 表格 + 右对齐数字 + 标签列。成本结论 = 一个句子。
2. **金额用 `--font-body` 20px/510，不用等宽**。等宽数字 = 账单感。金额要像句子里的词，不像表格里的单元格。
3. **主数字是「单次成本 + 推算的月度成本」**，不是 Token 数。老板的决策单位是「月」，不是「次」。
4. **明细收进二级入口**。「查看成本明细 →」**在汇报页内下钻到「成本构成」区块（员工维度），不跳管理员用量页**。老板默认不看到 Token。理由见下方 [P0] 下钻路径规则。
5. **金额不加粗放大**。最大只到 20px。不做「Hero 数字」，因为那是广告页做法；这是报表页做法。

#### 页面状态

| 状态 | 设计 |
|---|---|
| **Loading** | 不用骨架屏。用**员工口吻的实时流**：`正在查资料…` → `正在整理…` → `正在生成日报…`，配`LoaderCircle` 旋转。这是唯一允许"加载中"看起来像在干活的地方 |
| **成功** | 三个区块顺序呈现，步骤流可折叠（默认展开前 3 步） |
| **有失败项** | 失败步骤在流水里就地显示 `CircleX + 我在检索这一步卡住了，原因：需要你授权店铺后台` + 「补上授权后重跑」按钮。**不隐藏、不重试、不假装成功** |
| **全部失败** | 顶部 `CircleAlert + 这一趟没能跑完` + 明确原因 + 下一步动作。**空状态要给具体原因，不写「服务异常」** |
| **待确认积压** | 若待确认 ≥3 条，顶部提示条：`有 3 件事在等你确认，员工已经停下来了`（用`Hand` 图标，不用 `TriangleAlert`） |

#### [P0] 成本下钻路径规则（不可逆性防护 · 终裁版）

> **终裁（总监）：下钻终点是员工维度，到此为止。**
> **[重构记录]** 本节曾设计第 3 层「这些数字是怎么算出来的？」通往token 级，**该层已被裁掉，从未进入 Spec**。裁掉理由见下。

PM 提出一个真实风险：老板从「约 36 元/月」点进明细后若看到 `input_tokens 12,340`，会带着「这系统在计费」的印象回到汇报页。**这个顾虑成立，但解法不是禁止他看，而是让下钻终点落在业务维度上。**

**规则：老板的成本下钻终点 =「哪个员工花了多少」，到此为止。**

```
「约 36 元/月」
   ↓ 点「查看成本明细」—— 同页展开，不跳页
「成本构成」（汇报页内的区块，员工维度）
   市场专员  ¥18.40  ━━━━━━ 51%  ↑2.1%
   内容专员  ¥12.10  ━━━━  34%  ↓0.4%
   客服专员  ¥5.50  ━━    15%  —
   ─────────────────────────────────────
   本月合计 ¥36.00 · 环比上月 +8.2%
   近 8 周  ▁▂▂▃▃▄▃▅
```

**两层，到此为止**：

| 层 | 形态 | 作用 |
|---|---|---|
| 1 | 「约 36 元/月」一句话 | 老板的决策单位 |
| 2 | **同页展开**「成本构成」区块 | 员工维度 + 趋势。**不跳页 = 不进入技术语境**，回归是「收起」而非「返回」 |

**第3 层被否决的原因（我原方案的错误）**

我原设计保留了「这些数字是怎么算出来的？」作为通往 token 的入口，理由是「不剥夺能力」。**总监指出这是错的，我认可**：

> 如果「查看成本明细」把人送去 token 级页面，等于**在自己产品里开了一条绕过自己硬约束的后门——而且是看起来很专业的绕过，这比不做下钻更糟。**

**一个折叠入口不是中性的。** 我当时的论证是「能力不剥夺」，但真实问题是：**老板看到「36 元」时想知道的从来不是 token，而是「这钱花得值不值、该砍谁」。** 我设计的那条路径回答的不是他的问题，只是满足了他「想看明细」的假设。**给他一个他不需要的技术答案，比不给更糟。**

**所以此处不留 token 入口。** 若他本人技术背景、主动要求，走侧边栏 `/settings/usage` 自行进入——**主动寻路与被动推送是两件事**，前者是用户的选择，后者是产品替他做决定。

#### 员工维度成本构成的硬约束（总监指定）

**三条禁止（违反即退回）**：

| # | 禁止 | 理由 |
|---|---|---|
| 1 | 禁止出现 **token / prompt / response / 模型名 / 单价 / 调用次数** 任何一项 | 一旦出现，认知分类立刻重置为「计费工具」（同 §8.1 主约束） |
| 2 | 禁止**下钻到员工以下**（不点单个员工看其 prompt / 模型） | 单员工下钻 = 单点泄漏，且必然导向技术视角 |
| 3 | 禁止跳转到 `/settings/usage` | 下钻终点是本页，成本构成**就地展开** |

**密度口径：4，不进 7。** 员工维度成本构成属于汇报页的一部分，**沿用报告页密度**（行距宽松、无斑马纹、无等宽表格），不因为「是数据」就升级为密度 7 的管理表。**这是防止「成本区块悄悄变回账单」的关键**——密度一升、表格一排，账单感立刻回来。

**允许呈现的三个维度**（全部业务口径）：

| 维度 | 表达 | 图标 |
|---|---|---|
| 金额 | 「¥18.40」+ 折算人力（「约 4 小时人工」） | `HandCoins` |
| 占比 | 水平占比条（**非饼图**）+ 百分比 | — |
| 趋势 | 环比百分比 + 近 8 周迷你趋势线 | `TrendingUp` / `TrendingDown` / `Minus` |

**趋势的表达纪律**：环比必须显示**方向 + 数值**（`↑2.1%` / `↓0.4%` / `—`），**禁止只用颜色表示涨跌**（同 §3.5 三通道，趋势是语义信息不是装饰）。近 8 周趋势线用单色 `--accent` 15%→0% 填充，与 §7.7 用量页面积图**同一视觉语言**，但那是全公司口径、这是员工口径——**视觉一致但数据边界不同**。

**零成本员工的处理**：占比 0 但仍在册的员工**必须列出**并标注 `Pause` + 「今天没有运行」（同 §8.5 验收标准 10 的两段式渲染原则：折叠即隐藏会让老板误以为漏了人）。

#### 数字对齐纪律（结论句 vs 构成列表的字体分层）

PM 指出「精密仪器」还有一条我未写明的杠杆：**数字的对齐纪律**。经确认确实存在一处规范缺口——我曾分别写过「金额用 `font-body` 不用等宽」与「数字用等宽 tabular-nums」，但**没有说明两者为何不矛盾**。补齐如下：

| 位置 | 字体 | 对齐 | 理由 |
|---|---|---|---|
| **成本结论句**（「生成这份日报，大约花了 1.2 元」） | `font-body` 20px/510 | 不适用（是句子） | 等宽数字 = 账单感。**这段要像同事说的话** |
| **成本构成列表**（¥18.40 / ¥12.10） | **`font-mono` + `tabular-nums`** | **右对齐** | 老板要纵向比对大小，**右对齐 + 等宽是唯一能扫读的方式** |
| **占比百分比**（51%） | `font-mono` + `tabular-nums` | 右对齐 | 同上 |
| **折算人力**（「约 4 小时人工」） | `font-body` | 不适用 | 这是结论不是计量 |

**规则：同一区块内，「结论用 body，计量用 mono」。** 两者不冲突——**结论是给你读的，计量是给你比对的。**

**为什么这个分层是「精密感」的来源之一**：老板扫读成本构成时，眼睛做的是**纵向比对**（谁花得多），不是横向阅读。等宽 + 右对齐让小数点成一条竖线，**比对变成视觉直觉**；如果用比例字体左对齐，每行长度不同，眼睛要重新定位，5 行数据会比对5 次。

> 这条与 §7.7 用量页一致（那里全用等宽），但**此处仅用于构成列表，不用于结论句**——不要因为这条就把整块改成等宽，否则账单感回来。


### 8.2 待确认队列（差异化卖点 3的界面）

**设计目标：让「我停下来问你」看起来像员工的主动汇报，而不是系统的故障告警。**

PM 给的两个风险都真实存在，我的解法是**同时调整三个维度**——光调视觉重量会滑向"太重"，光调文案会滑向"太轻"。

#### 维度一：视觉上「不是告警」——去掉一切告警语汇

这是最关键的一条。系统告警和员工汇报的视觉语汇差异：

| 维度 | 系统告警（禁止模仿） | 员工汇报（采用） |
|---|---|---|
| 图标 | `TriangleAlert` / `CircleAlert` / `!` | **`Hand`（举手）/ `MessageCircleQuestionMark`** |
| 容器 | 红色/黄色左边框 + 告警底色 | `--surface-2` + 1px `--border`，**无彩色边框** |
| 标题 | 「异常」「警告」「错误」 | 「**我停下来问你 3 件事**」 |
| 语气 | 系统被动式：「检测到以下问题」 | **员工主动式：「这 3 处我没把握，想跟你确认」** |
| 顶部横幅 | 有 | **无横幅**。不弹模态、不抢注意力 |

> 特别强调：**不用 `--warn` / `--danger` 作为容器色**。理由是——这是本产品唯一会被「非故障」触发的红色/黄色场景。一旦「红色=有问题」的映射建立，老板看到红色就紧张，而这条队列**不是问题，是协作**。用红色会让一个正向设计变成信任负债。

#### 维度二：内容上「给出上下文」——让停下来显得有依据

老板判断「这员工行不行」的标准不是它问了什么，而是**它问得对不对**。

每条待确认项固定四行结构：

```
┌──────────────────────────────────────────────────┐
│ ① 我没敢填客户等级                    [ 按我这样处理 ]│
│                                                          │
│    原文写的是「战略客户A」，但登记表里这个客户去年    │
│    降级成了普通客户。我不确定该用哪个。             │
│                                                          │
│    依据：客户台账.xlsx 第 3 行 vs 2025年报 第 12 页   │
│                                                          │
│    ─────────────────────────────────────────────    │
│    [ 就按旧等级填 ]  [ 我改：__________ ]  [ 跳过 ]   │
└──────────────────────────────────────────────────┘
```

- **标题写「我没敢填客户等级」而不是「客户等级待确认」**——前者是员工的主语和心理，后者是系统的字段名。
- **必须有一行「依据」**（引用具体文件与位置，11px/muted）。这是把「它不确定」转成「它查过且发现了矛盾」的唯一手段。没有依据行，问问题就等于甩锅。
- 两个动作按钮**权重不等**：`按我这样处理` 是 primary accent（老板点一下就完事）；`我改` / `跳过` 是 ghost。次序符合「默认答案是执行」。
- **禁止**把「跳过」做成和前两个一样重——那会暗示「跳过是正常路径」，鼓励老板无脑略过，把信任机制变成噪音源。

#### 维度三：位置上「是工作台的一部分」——不是独立待办中心

待确认队列**不做成独立的第 6 个顶级导航项**。理由：顶级导航已 6 项（§7.1），再加就违反工作记忆 ≤4 原则。

- **入口**：工作台顶部的一条内联区块（非模态、非横幅），显示「等你确认：3」
- **员工卡片上的状态**：任何有待确认项的员工，其状态点从`CircleCheck` 变为 `Hand` + 文字「等你确认」——这样老板即使不点进工作台，也能在员工列表看到「有几个员工卡住了」
- **空状态**（关键）：没有待确认项时**不显示任何东西**。不要写「太棒了，没有待确认！」。理由——正向的空洞庆祝会让老板觉得这个功能不存在，且暗示"它其实很少用"。

#### 与信任指标的联动

「差异化卖点 3」的信任闭环，靠这个组件积累一个可展示的数字：

> 「本月你的员工停下来问过你 27 次，每次你都做了决定。它们没有一次是猜的。」

这句话在**计费页/首页汇报区**出现（而不是只在待确认页），因为它把「停下来问」从「系统不够智能」重新框定为「系统很可靠」。这是本产品最重要的**语义重构**，设计上的实现方式就是：待确认队列必须**看起来无害**，这样它累积起来才显得可信。

### 8.3 岗位模板卡片墙（5 岗位难度递进）

PM 指出的缺口：UIUX.md §7.4 只讲了「智能体员工管理（密度 6）」，没讲这5 张岗位卡片怎么设计、怎么排序、怎么在难度递进中管理预期。

#### 关键判断：卡片墙不能是同质网格

反模式是「5 张等大卡片 + 图标 + 标题 + 文字」——这正是 §10 禁止的「相同卡片网格无限重复」。**难度递进必须由视觉承载**，否则递进只存在于产品经理的脑子里。

#### 布局：2 + 1 + 2 的分数网格（`grid-template-columns: 1fr 1fr`，首卡跨 2 列）

```
┌───────────────────────────────────────┐
│ ① 竞品监控日报                    ← 首卡，跨 2 列，视觉最重│
│    每天早上 8 点，看完 5 家竞品的价格 │
│    与动作，把变化写成一份日报│
│    [ 无需配置 · 今天就能上岗 ]              │
└───────────────────────────────────────┘
┌──────────────────┐┌──────────────────┐
│ ② 售前方案初稿       ││ ③ 会议纪要         │
│ 上岗前置：品牌资料   ││ 上岗前置：日历授权 │
└──────────────────┘└──────────────────┘
┌──────────────────┐┌──────────────────┐
│ ④ 客户邮件跟进       ││ ⑤ 订单录入          │
│ 上岗前置：邮箱+CRM   ││ 上岗前置：店铺+ERP │
│                  ││ 需完成 2 项授权    │
└──────────────────┘└──────────────────┘
```

**排序不是按难度，而是按「首次成功率」降序**。理由：老板的第一次点击决定他对产品的信心。第一个岗位必须是他**不需要任何配置就能看到产出**的那个。

#### 视觉权重分三级（对应 PRD 的「上岗前置条件」五要素）

| 难度档 | 岗位 | 视觉权重 | 上岗前置条件表达 |
|---|---|---|---|
| **低** | 竞品监控日报 | **最重**：24px 图标 + `--accent` 1px 边框 + 略高内边距 | `无需配置` → 用 `CircleCheck` + **文字**，**绿色**，且是唯一允许成功色的地方 |
| **中** | 售前方案、会议纪要 | 中：20px 图标 + `--border` 边框 | `需授权：品牌资料库` → 用 `LockKeyhole`（**非 `--warn`**）+ 文字 |
| **高** | 订单录入 | **最轻但最清楚**：20px 图标 + `--border`，**但加一条 `--border-strong` 顶边** | `需完成 2 项授权：店铺后台、ERP` → 用 `LockKeyhole` + 文字 + 明确的「2 项」计数 |

> 注意高难度卡片**不用降低透明度或置灰**。置灰会暗示「不可用」，而它们是真实可用的——只是需要先配置。**用边框粗细表达"需要留意"，不用透明度表达。**

#### 预期管理（PM 的核心关切）

难度高的岗位必须在卡片上**预先告知工作量**，而不是等用户失败后才说：

```
⑤ 订单录入
  每天把昨天的订单核对后录入系统，对不上就标出来
  ┌────────────────────────────────────────────┐
  │ 上岗前需要  2 项设置· 约 3 分钟                │
  │  ① 授权店铺后台    [ 去授权 ]                │
  │  ② 关联 ERP 账套    [ 去设置 ]                │
  │  两者都完成后，员工立即上岗，无需重新配置       │
  └────────────────────────────────────────────┘
```

三个要点：
1. 「约 3 分钟」——把未知的成本变成已知的时间，这是降低点击心理门槛最有效的手法
2. 「完成后立即上岗，无需重新配置」——消除「配了半天不知道管不管用」的担忧
3. 按钮是**主动作**（去授权），不是幽灵链接——引导而不是描述

#### 卡片五要素的视觉权重分配（回应 PRD §7.3 F1）

PRD 定义强制五要素：图标 / 岗位名 / 一句话职责 / 上岗前置条件 / 交付物。按视觉权重从上到下：

| 序| 要素 | 字号/样式 | 视觉权重 | 理由 |
|---|---|---|---|---|
| 1 | 图标 | 24px / 20px `currentColor` | **最高** | 第一眼扫过，卡片墙靠它区分 |
| 2 | 岗位名 | `--text-md` 16px/510 | 高 | 扫读锚点，必须一眼可辨 |
| 3 | 一句话职责 | `--text-sm` 13px/`--fg-2`，**最多 2 行截断** | 中 | 解释「干什么」，超长必须截断（破卡片高度= 破网格） |
| 4 | 交付物 | 13px/`--muted`，**必须带图标**（`FileText`/`FileSpreadsheet`） | 中低 | 用图标+ 文件名而非纯文字，这是"真有产出物"的证据 |
| 5 | 上岗前置条件 | 12px/`--fg-2`，**独立成块**（上方 1px `--border`） | 低但**位置重要** | 放最后是因为老板先看「能不能干成」，再看「要付什么」 |

**第4 与第 5 的顺序是刻意的**：PRD 的要素表把「上岗前置条件」列在「交付物」前，但从老板的决策心理看，「有没有东西交给我」比「我要先做什么」更重要。**我把交付物提到了前置条件之前**——这一条建议反馈给 PM 更新 PRD 的要素顺序。

#### 已上岗后的卡片形态

卡片墙是**引导态**。员工上岗后，卡片转为 §7.4 的列表行（表格形态）。禁止把已上岗的岗位继续留在卡片墙——卡片墙只有一次性引导价值，长期占用页面会降低员工列表的扫描效率。

### 8.4 老板汇报页vs 管理员用量页 —— 页面切分裁定

PM 要求我裁定：「老板看的日报」和「管理员看的用量计费页」是同一页的两个视角，还是两个页面。

**裁定：两个独立页面。不是两个视角。**

#### 理由（不是设计偏好，是产品结构问题）

1. **术语体系互斥**。PRD §4.2/§11.2 禁用「Token / 调用 / 会话 / 任务」，改用「处理 / 跑完 / 次数」。而 §7.7 用量计费页的核心恰恰是 Token 明细与成本构成——**它必须用管理员语言，因为它的使用者是懂技术或至少要看账单构成的人**。同一页无法同时满足两套术语。
2. **导航深度不同**。老板的汇报在**一级页面**（每天要看，3 秒内要抓到结论）；管理员的用量构成在**设置类页面的二级/三级**（偶尔看，需要钻取）。放一起会让老板的日常入口被管理员信息稀释。
3. **权限不同**。老板看自己的团队总账；管理员看全公司/多账号构成。数据边界不同就不该同页。
4. **合并会让成本被Token 主导**——PM 的判断我认同，且这是必然结果而非偶然：同一页里 Token 明细信息密度更高，它会自然占据视觉主导位，把老板的第一印象拉向「计费工具」。

#### 页面职责表

| | 老板汇报页 | 管理员用量计费页 |
|---|---|---|
| 路由 | `/`（工作台首页） | `/settings/usage` |
| 核心问题 | 「我的团队今天干得怎么样」 | 「钱花在哪了，为什么涨了」 |
| 术语 | 处理 / 跑完 / 次数 / 省了多少 | Token / 调用次数 / 单价 / 成本构成 |
| 数字字体 | `font-body`，无Token 字样 | **等宽 `font-mono` + tabular-nums** |
| 成本表达 | 「约 36 元/月」（一句话） | 「¥1,240.50」+ 明细表 |
| 密度 | 4 | 7 |
| 主数字 | 今日完成数、本月省下的工时 | 总 Token、总成本、单 Token 均价 |

#### 但共享同一份数据

两页数据同源，**只有表达层不同**。实现要求（给architect）：

- 后端提供**一份**用量数据接口，字段同时含业务口径（`任务数`、`成本分`）与技术口径（`input_tokens`、`output_tokens`、`model`）
- 前端**两个组件**消费它：`OwnerSummaryView`（业务口径）与 `UsageBreakdownView`（技术口径）
- **禁止**在 owner 视图里透传 token 字段——不做「显示不显示」的开关，直接不传，避免泄漏进 DOM

**埋点层面**：PRD §7.3 F4 的 `report_viewed` 应按视图区分（`owner_report_viewed` / `admin_usage_viewed`），否则无法衡量老板是否真的在用汇报页。

| 维度 | 规范 |
|---|---|

#### 四板块的具体规则

**① 今天做完了什么**

- 按员工分组，组内**按产出时间倒序**（最新在上）——老板最关心刚发生的事
- 每条：`员工名 · 完成事项`(16px/510) → 业务语言一行(14px/`--fg-2`) → 产出行（图标 16px + 文件名 + 「查看」）
- **产出行必须带图标**（`FileText`/`FileSpreadsheet`）+ **真实文件名**，这是「真的干了」的证据
- **无产出时**：不隐藏板块，写「今天没有需要产出的活，员工在待命」+ `Pause` 图标。**理由**：静默隐藏会让老板怀疑「是不是坏了」。**用中性措辞，不用庆祝或道歉语气。**
- 折叠规则：单日产出 >6 条时，折叠第 4 条起，显示「还有 8 条产出 ↓」。**永不折叠为0 条状态**（0 条必须显式说明）

**② 要你管**

- 只在**有待确认项时**出现；为0 时**整个板块不渲染**（不是写「一切正常」）
- 内容：数量 + `[ 逐件处理 → ]` primary 按钮，指向 §8.2
- ≥3 条时追加`Hand` 图标 + 「员工已经停下来了」——暗示损失，但不用 `warn` 色（§8.2 同源规则）

**③ 我停下来过（固定板块，PM 明确要求）**

- **无论有无都渲染**。这是本产品的信任指标，不是异常日志
- **有值时**：`CircleCheckBig` + 「今天市场专员停下来问了 2 次，都已经处理好了。客服专员问过 1 次，正在等你回答。」
- **为 0 时**：`CircleCheckBig` + 「今天没有员工打断你。」（PM 采纳的文案）
- **禁止**：把该板块藏在「更多」里、或只在有值时出现。**它的价值恰恰在于「没发生」这个事实本身可见。**
- 数据必须来自 `task_escalated_to_human` × `escalation_resolved` 配对计数（PM 已定的埋点约束），**禁止硬编码**

**④ 花的钱 · 算给你看**

- 三行结构：今日成本 → 月度推算 → **折算人力**（`HandCoins` 图标）
- 折算是这一板块的收尾价值：「省下约 2 小时 40 分钟」比「花了 1.2 元」更能让老板感知价值。**但必须由真实数据推算**，禁止虚构
- 下钻见§8.1 的 [P0] 成本下钻路径规则（同页展开，不跳页）

#### 验收标准 10 的UI 落实：不得静默跳过未执行的员工

PM 的 F4 验收标准 10 要求「不得静默跳过未执行的员工」。这条在UI 上的落实方式是**两段式渲染**：

```
今天 3 名员工在岗，2 名待命        ← 全量计数，先声明总数
  [ 在岗 3 人的产出条目... ]
  2 名待命：市场专员（今日排班已结束）、客服专员（今日无任务）  ← 明确列出，不省略
```

**规则**：
- 顶部**必须先声明总数**（`在岗 X / 待命 Y`），让老板一眼知道分母
- **待命员工必须列出姓名 + 待命原因**（排班结束/ 无任务 / 未配置完成），**禁止省略**
- 禁用「+2 名待命」这种折叠计数——**折叠即等于隐藏**，会让老板误以为漏了人
- 若某员工**本应执行但未执行**（异常），必须显式标出：`CircleAlert + 客服专员今天没有运行：知识库授权在昨天被撤销`

> 这条与 §8.1「有失败项不隐藏」同源：**省略比报错更伤信任。** 老板无法区分「没活干」和「被跳过了」，所以必须显式区分。

#### 折叠与空状态总表

| 板块 | 折叠规则 | 空状态 |
|---|---|---|
| ① 做完了什么 | >6 条折叠第 4 条起，显示「还有 N 条产出 ↓」 | **不隐藏**，写「今天没有需要产出的活，员工在待命」 |
| ② 要你管 | 不折叠 | 为 0 时**整个板块不渲染** |
| ③ 我停下来过 | 不折叠 | 为 0 时渲染「今天没有员工打断你。」 |
| ④ 花的钱 | 不折叠 | 必渲染（成本永远存在，即使为 ¥0.00） |

**成本为 ¥0.00 时**：`Coins` 图标 + 「今天没有产生模型调用费用。」——不用「¥0.00」这种技术写法。

### 8.6 周度汇报页 `/reports/weekly`（密度 3，全产品最松）

PM 裁定：**先做周报，部门汇总放Phase 2**（MVP 多数客户只有 1 个员工，部门汇总无数据意义）。

**密度 3，理由与日报不同**：日报是「扫读」（每天 1 分钟抓结论），周报是「回顾」（花时间看趋势与产出）。密度由信息组织紧度决定——回顾天然比扫读松。**但 §8.5 的两段式渲染与显式区分原则在此继续生效，且周报有一处强化，见下。**

#### 核心差异：周报不是七份日报的堆叠

日报四板块是**日粒度的即时性沟通**（要你管 = 今天要处理的事）。周报若按日组织会退化成七份日报堆叠——**那不是回顾，那是存档**。

周报按「**产出总览 + 趋势**」组织，**按岗位分组而非按时间罗列**。

| 维度 | 日报 §8.5 | 周报 §8.6 |
|---|---|---|
| 密度 | 4 | **3** |
| 组织方式 | 按时间（今日条目） | **按岗位分组 + 趋势** |
| 「要你管」语义 | 今日待办（每日清零） | **本周积压（不清零）** |
| 「停下来过」 | 今日次数 | 累计次数 + **是否仍有未处理** |
| 成本 | 今日 ¥x + 月度推算 | 本周 ¥x + 占预算比例 + 周折算 |
| 趋势 | 无（单日无趋势） | **环比 + 近 8 周趋势线** |
| 进入方式 | 工作台首页 | 日报顶部「看本周」→ `/reports/weekly` |

#### [P0] 板块② 「本周需要你管的」必须显示积压，不做每日清零

PM 提出的这一点是周报与日报的**关键区别**，我确认并强化：

> **日报是每日清零，周报要显示「积压」——如果一周下来还有 5 件事等着老板处理，那是重要信号，日报看不出来。**

**规则**：
- 板块②**统计区间是「本周新增 + 期末仍未处理」**，不是「本周新增」
- 必须显示**最早一件已等几天**（`TriangleAlert` + 「最早一件已等 3 天」）——**等待时长是升级信号**
- **不为 0 时才渲染**：与日报相同（不写「一切正常」）
- **禁止折叠**（同日报原则：折叠即隐藏）

**这条的价值判断**：日清的「要你管」只看当天，**会掩盖一个慢性问题**——如果老板每天只处理 1 件，而每周新增 8 件，日报每天显示「1 件」，看起来很可控；**周报显示「5 件积压，最早等了 3 天」，才是真实信号。**

#### 板块③ 的停下原因分类（口径已与 PRD 对齐）

PM 在 PRD 中把「我停下来过」按**停下原因**分为三类。**这与 §8.5 日报的三通道不同——日报不分类（当天条目少），周报必须分类（周维度才有统计意义）**：

| 类别 | 停下原因 | 图标 | 语气 | 计入积压？ |
|---|---|---|---|---|
| **需要人定** | 员工主动判断不确定（依据充分） | `Hand` | 「我没敢填客户等级」 | **是** |
| **卡住了** | 熔断 / 无进展 / 连续失败 | `CircleDashed` + `CircleAlert` | 「这一趟卡住了，我停下来等你」 | **是** |
| **预算闸门拦住了** | **客户 API 预算**用完 | `Coins` | 「你的 API 预算用完了，我停下来问你了」 | **是** |
| （第四类）**上报了结果** | G4 抓取失败但仍显式上报 | `TriangleAlert` | 「9 月 12 日 检测到 ERP 返回 500，自动重试 2 次后跳过 3 条，已记录」 | 否（已自行处理） |

**为什么周报必须分类而日报不必**：
- 日报是当天 1-2 条，逐条看文字即可判断，分类只是噪音
- 周报是 8-15 条的汇总，**不分类老板无法看出「哪类问题在反复」**——而后者才是他该干预的

**关键判断：第 1 类与第 2 类必须视觉可分（见 §11.5）**。熔断是系统问题，若与「需要人定」混在同一队列，老板会归因为「员工能力不行」。

**第 3 类在纯 BYOK 下的语义已变（2026-10-15 用户裁定：删除平台代付）**：

| | 原（代付） | 新（纯 BYOK） |
|---|---|---|
| 闸门作用 | 平台防止代付额度烧光 | **客户防止自己的 API 账单超支** |
| 文案主语 | 「你的平台额度」 | **「你的 API 预算」** |
| 动作选项 | 充值 / 下月再说 | **「调整预算阈值」/「告诉我不用管」**（不引导充值——平台不经手模型费用） |

**UI 后果（必改）**：**禁止出现任何「充值」「余额」「平台额度」字样**。第 3 类的动作按钮**不得跳转到充值页**（产品已无该功能）。

**这类的语气也从「阻断」转为「帮客户盯着」**——PRD 已明确这是**卖点不是限制**：「我们不赚你模型费的钱，也不碰你的模型账户。**我们只帮你盯着别烧超。**」因此文案**不用 `danger`**，用 `Coins` + `--warn`（超限是提醒，不是故障）。

**第 4 类不计入积压**：员工已自行处理并上报结果，无需老板介入。**但必须显示**（同「不得静默跳过」原则）。



日报的「我停下来过」是当日维度（今天问了几次，都处理好了）。**周维度必须区分两种状态**：

```
本周停下来问过你 8 次，每次你都做了决定。它们没有一次是猜的。
市场专员 3 次 · 内容专员 2 次 · 客服专员 3 次
其中 3 次还在等你  ← `CircleDot` + muted，不与上面同色
```

#### [P0] 信任指标的诚实性约束 —— 只声明系统能保证的事

**这条不是「周维度要注意」，而是一个句式级的硬约束。**

PM 原句：「本月你的员工停下来问过你 27 次，**每次你都做了决定**。**它们没有一次是猜的**。」

问题在于：**「每一次」「没有一次」是绝对承诺，只要任意一次未被处理，整句就是假的**。而产品**无法保证用户处理了每一次**。

**核心判据（本条的核心，Phase 2 不得改动）**：

| 句子成分 | 描述的是谁的行为 | 系统能否保证 | 处置 |
|---|---|---|---|
| **「每次你都做了决定」** | **用户行为** | **不能**——用户可能没看到、没时间处理 | **有未处理项时必须删除** |
| **「它们没有一次是猜的」** | **系统行为**（员工不猜测） | **能**——这是产品设计保证的 | **保留** |

> **只声明系统能保证的事，不声明依赖用户行为的事。**

**四种情形的完整对照（强制）**：

| 情形 | 主句 |
|---|---|
| 全部已处理 | 「本周停下来问过 8 次，**每次你都做了决定**。它们没有一次是猜的。」 |
| **有未处理** | **「本周停下来问过 8 次，其中 3 次还在等你。它们没有一次是猜的。」**——**删除「每次你都做了决定」，保留后半句** |
| N < 5 | 「本周停下来问过 3 次。**样本不足，本周不做判断。**」（不出现任何结论句） |
| N = 0 | 「本周没有员工打断你。」 |

**配套四条**：
- 未处理项**禁止用 `--success` 绿色**（未解决的事不该是成功的绿）
- 未处理项必须显示**已等天数**：「3 次还在等你，最早已等 3 天」比「3 次还在等你」更能触发行动
- 统计区间 = 本周新增 + 期末仍未处理
- **周维度比日维度更严格**（样本大，老板更可能去数）

**违规判定**：任何界面若出现「每次/每一次/全部」+「已决定/已处理」组合，且实际存在未处理项 → **视为P0 缺陷**，与硬编码同等级别（信任指标造假）。

**这条为什么值得升P0**：信任指标一旦被发现不实，**杀伤力远大于不做**——用户会开始怀疑所有其他数字。而它只靠改一句话就能避免，**成本极低、风险极高**。

#### [P0] 样本量不足时不判定（总监裁定）

总监指出一条日报没有的问题：**周维度样本量可能太小。**

> 假设某周只有 3 次「停下来问」，其中 2 次是熔断 → 按规则整周标红。**但 3 次事件的 2 次不构成趋势。**

**规则（强制）**：

周维度信任闭环展示时**必须同时显示分母**：`本周停下来问 N 次`（N 显式写出，不只写百分比）。

| 条件 | 呈现 | 禁止 |
|---|---|---|
| **N ≥ 5** | 正常判定红/黄/绿 + 结论句 | — |
| **N < 5** | **中性状态**（`CircleDot` + `--muted`）+ 「样本不足，本周不做判断」 | **禁止**显示红/黄/绿或任何结论句 |
| **N = 0** | 「本周没有员工打断你。」 | — |

**理由（与日报分母声明同源）**：
-日报「省略比报错更伤信任」——**反过来也成立：样本不足却给结论，是另一种不信任。**
- 一个「2/3 熔断」的数字如果不给N，老板无法判断这是常态还是异常；给了 N 他才知道该不该管。

**这条的连带影响**：板块② 的「最早一件已等 N 天」**不受样本量约束**——**积压天数是绝对量而非比率，1 件等 5 天也是问题**，不需要样本量支撑。**不要把这条规则误用到板块②。**

#### 折算基准（PM 已定义，设计侧落法）

**UI 落法（三条规则）**：

- 焦点样式只走`:focus-visible`，**禁止 `outline:none` 不补偿**
- 所有图标按钮 `aria-label` 必填
- 所有 Loading 态禁止用骨架屏无限循环超过 10s 无超时兜底文案

## 10. 响应式与无障碍

**断点**：`xs <640 / sm ≥640 / md ≥768 / lg ≥1024 / xl ≥1280 / 2xl ≥1536`

| 断点 | 布局 |
|---|---|
| xs | Sidebar 变底部 TabBar（5 项：工作台/员工/任务/资产/更多）；表格降级为**卡片列表**（每字段一行 label:value） |

| lg+ | 完整三栏 |

**触摸目标**：`min 44×44px`，按钮间距 ≥8px。行内小图标按钮用 `padding` 或伪元素扩到 44px 命中区。

**无障碍**：
- 对比度：见 §3 全部实测数据（正文 ≥4.5:1 已全部通过）
- 键盘：`Cmd/Ctrl+K` 全局搜索；`Tab` 顺序符合视觉顺序；表格支持方向键移动；会话区 `aria-live="polite"` 流式播报
- `prefers-reduced-motion` 已规定降级行为
- 状态色三通道（§3.5）——这是本产品最重要的无障碍决策

## 11. 交付可执行性规范（团队配置决定）

>团队配置为「先做原型，后续自己招人」。**本节把设计规范里最容易被新人做错的三处，写成可直接照抄的判定规则。**原则：每条都是**二选一的客观判定**，不含「注意」「建议」「尽量」这类需要主观判断的词。

### 11.1 状态图标选用判定（零主观空间）

**唯一判定动作：给状态找到「图标 + 文字」的字面组合，然后直接用。** 不需要理解设计意图。

| 状态 | 图标（唯一） | 文案（照抄） | 尺寸 |
|---|---|---|---|
| 运行中 | `LoaderCircle`（旋转 1.2s） | 运行中 | 16px |
| 正在中止 | `CircleDashed`（旋转 1.2s） | 正在中止… | 16px |
| 待命 | `Pause` | 待命 | 16px |
| 等你确认 | `Hand` | 等你确认 | 16px |
| 已完成 | `CircleCheck` | 已完成 | 16px |
| 失败 | `CircleX` | 失败 | 16px |
| 需关注 | `TriangleAlert` | 需关注 | 16px |
| API 预算超限 | `CircleDollarSign` | API 预算 NN% | 16px |
| 已跳过 | `BadgeQuestionMark` | 已跳过 | 16px |
| 需授权 | `LockKeyhole` | 需授权 | 16px |

**三条不可协商**：
1. **禁止只显示图标不显示文字**（WCAG 1.4.1 + §3.5 三通道）
2. **禁止自选状态图标**。上表之外没有第二个选项。缺图标时提PR，不要用近义图标替代
3. **禁止用图标单独表达涨跌**（趋势必须带 `↑/↓/—` + 数值）

### 11.2 颜色取用判定（三步，不允许跳步）

```
第 1 步：确认你要的是「文字色」还是「容器底色」
         文字色 → 用 --fg-1 / --fg-2 / --muted
         容器底色 → 用 --surface-1 / --surface-2 / --surface-3
         两者都不是 → 去第 2 步

第 2 步：确认语义（业务语义 → 语义色；品牌强调 → accent）
         业务语义 → --success / --warn / --danger / --info
         品牌强调 → --accent（且必须已确认本屏≤2 处，见下）

第 3 步：在对应的三级表面上验一遍
         文字色必须 ≥4.5:1（用 §3 实测表查，不用自己算）
         输入框描边必须 ≥3:1（--border-input）
```

**三条不可协商**：
1. **禁止组件内写裸 hex**。唯一例外`#fff` / `#000`
2. **`--accent` 每屏 ≤2 处**。第三处必须换中性色。若确实需要第三处强调，说明这个界面需要重新拆分区块
3. **禁止用 alpha 透明度代替语义色**。要浅一点的语义色就用 `--success-bg` / `--warn-bg` 等已定义的底色 token，不自己加`opacity`

### 11.3 密度判定（按页面职能，不允许凭感觉）

```
打开 §4 规则 8 的密度分配表 → 找到当前页面 → 用该密度
表里没有的页面 → 问team-lead，不自行判断
```

| 密度 | 页面 | 一句话判据 |
|---|---|---|
| 4 | 试跑结果页、每日汇报页、成本构成 | 老板在**读** |
| 5 | 工作台 / 会话 | 老板在**读 + 偶尔交互** |
| 6 | 员工管理、知识库、岗位卡片墙 | **浏览 + 偶尔配置** |
| 7 | 任务中心、用量计费、cancel 态| **监看**，要一屏看到 20 条 |

**两条不可协商**：
1. **密度是页面级，不是个体元素级**。禁止在一个密度 4 的页面里塞密度 7 的表格
2. **成本相关区块恒为密度 4**，即使是数据表格形态（见 §8.1硬约束）

### 11.4 语义图标映射的写入流程（与 architect 的 CI 门禁对齐）

architect 已建立 `scripts/verify-icons.sh` 作为发布阻断门禁。设计侧配合规则：

```
第 1 步：把新图标先写进 docs/semantic-icon-map.txt（文本，按 §8.7 格式）
第 2 步：跑 npm run verify:icons，失败则阻断（不跳过）
第 3 步：验证通过后才允许在代码里写 import
第 4 步：升级 lucide 版本后必须重跑
```

**禁止先写 import 再验证**（architect 立的硬约束，设计侧同样遵守）。

### 11.5 `Hand` 图标的视觉疲劳预案（architect 提出，预设判据）

architect 提出一个真实风险：F6-lite 阶段熔断信号收紧，`等你确认`（`Hand`）的出现频率可能远高于预期，导致用户对该图标脱敏。**脱敏的代价是双向的**——既可能「不再注意」，也可能「习惯性忽略」，后者会直接摧毁 §8.2 建立的信任机制。

**设计侧的应对原则：不改图标，改「密度」和「重复抑制」。**

`Hand` 的语义必须保持唯一——它是「AI 员工主动停下来问你」的专属标记。**换图标等于把这个语义重新稀释一次**，所以图标本身不动。

#### 三级降频策略（按单日待确认数自动生效）

| 单日待确认数 | 呈现策略 | 目的 |
|---|---|---|
| 1–2 条 | 完整展示：每条含依据行 + 三个动作按钮 | 正常态，确保老板看得清 |
| 3–5 条 | **合并同类项**：同一员工的多条合并为一张卡，卡内列条目摘要 | 降低视觉块数量，语义不变 |
| **> 5 条** | **降级为汇总条**：`Hand` + 「今天有 8 件事在等你确认」+ [ 逐件处理 → ]，**不逐条展开** | 避免刷屏。**但依然不隐藏**（§8.5 原则） |

#### 熔断场景的特殊处理

architect 提到 F6-lite 阶段「无进展检测」会频繁触发。**关键判断：熔断触发的待确认与员工主动上报的待确认，语义不同，必须分开。**

| 来源 | 标题文案 | 图标 | 处理 |
|---|---|---|---|
| 员工主动判断（「我不确定」） | 「我没敢填客户等级」 | `Hand` | 正常待确认队列 |
| **系统熔断**（无进展/循环重试） | 「这一趟卡住了，我停下来等你」 | `CircleDashed` | **单独分组**，标`CircleAlert` + 技术原因（供管理员排查） |

**为什么必须分开**：熔断是系统问题，不是员工判断。若混在同一队列，老板会误以为「我的员工能力不行」，而实际是配置或数据问题。**这直接损害 §8.2 建立的信任。**

> **[已按 PRD 重构]** 总监裁定：熔断与主动上报**分两组**。PM 已在 PRD 中把停下原因归为「需要人定/ 卡住了 / 预算用完了」三类，本节 §8.6 板块③ 已按该三分类对齐（周报口径）。日报不分三类（当天条目少，分类即噪音），周报必须分类（周维度才有统计意义）。

**给 architect 的 UI 建议**：熔断事件走独立的展示位（如任务行内的内联提示），**不占用待确认队列的名额**。理由同上——它需要技术原因，放进业务队列会污染语义。
