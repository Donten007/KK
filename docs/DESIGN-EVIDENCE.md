## 2. 色觉障碍模拟实测（本项目最重要的无障碍发现）

**方法**：对 5 个状态色分别做deuteranopia / protanopia / tritanopia / achromatopsia 模拟，计算模拟后两两之间的对比度。

### 2.1 关键结论：红绿色盲下 warn 与 danger 完全同色

| 模拟类型 | `--warn #E39A2E` | `--danger #F0555A` | 两者模拟后对比度 | 判定 |
|---|---|---|---|---|
| 正常 | #E39A2E | #F0555A | 1.45:1 | 可区分（靠色相） |
| **红绿色盲deuter** | **#CCD189** | **#C8D19C** | **1.00:1** | **完全同色** |
| 绿色盲 protan | #B4B489 | #9A9A9C | 1.31:1 | 几乎不可分 |
| 蓝色盲 tritan | #E09F38 | #EB653E | 1.42:1 | 勉强 |
| 全色盲 achroma | #A9A9A9 | #8B8B8B | 1.45:1 | 仅靠亮度差 |

**因此定出 P0 约束**：**任何状态必须同时具备「颜色 + 图标 + 文字」三通道**，禁止仅用色点/色条表达状态。

**这不是最佳实践，是这条配色下的必要条件。**

### 2.2 主色色相被 success 绿锁死

| 候选主色 | 色相 | 与 success 绿(150°)色相差 | 结论 |
|---|---|---|---|
| teal | `#14B8A6` | **23°** | **否决**（红绿色盲下与「已完成」不可分） |
| **cyan** | **`#29B6D6`** | **41°** | **采用** |
| indigo（Linear） | `#5E6AD2` | 89° | 可行但「默认靛蓝=一眼 AI」 |

最终 5 色相相��：`success 150°` / `warn 36°` / `danger 358°` / `info 232°` / `accent 191°`，相邻间隔 **114° / 38° / 126° / 41°**，全部 ≥30°。

## 4. 被否决的方案及否决理由

> **让后来者看到「这里曾经错过一次」比只看到「现在这样对」有价值。** 前者能防止重犯，后者只能让人照抄。

### 4.1 teal 主色 `#14B8A6` —— 色相与 success 绿撞车

| 项 | 内容 |
|---|---|
| 原始想法 | teal 更「沉静专业」，适合精密仪器定位 |
| **否决理由** | 色相 173° 与 success 绿 150° **仅差 23°**；红绿色盲下「这个员工的任务完成了吗」不可区分 |
| **为何致命** | 用一个看不清的状态色去做**状态驱动型产品**——而「任务是否完成」是本产品最核心的状态语义 |
| 替代 | 191° 青蓝 `#29B6D6`（间隔 41°） |
| 教训 | **主色不能按品味挑，必须先跑色相间隔。** 品位问题可以商量，可访问性问题不能|

### 4.2 「三套配色候选」（深邃夜航/ 墨玉沉金 / 石墨靛蓝）—— **从未存在**

| 项 | 内容 |
|---|---|
| 来源 | 项目总监某轮消息中提出，要求 PM 准备对比说明 |
| **实际情况** | **系表述错误，该信息系虚构。** PM 核实 UIUX.md 后发现设计部只交付一套配色 |
| PM 处理 | **拒绝编造对比表**，如实上报「设计部只交付了一套」 |
| 裁决 | **维持现有一套青蓝，不另造候选** |
| **更深的结论** | 配色这个决策**本不该以候选集形式存在**——它是「排除一个不安全解」，不是「在几个好看选项里挑一个」。做成候选集**等于把约束问题伪装成偏好问题** |
| 沉淀 | 硬约束锁死主色时，候选集只能是「一套配色的三个变体」，命名体系会掩盖这一点 |

### 4.3 成本下钻第 3 层「这些数字是怎么算出来的？」——绕过自己硬约束的后门

| 项 | 内容 |
|---|---|
| 原始设计 | 试跑页成本句下方留一个折叠入口，通往 token 级明细 |
| 当时的理由 | 「能力不剥夺」——技术人员背景的老板仍需可达 |
| **否决理由** | ① **老板看到「36 元」时想知道的是「这钱值得值不值、该砍谁」，不是 token**——给他一个不需要的技术答案比不给更糟 ② **一个折叠入口不是中性的**：产品语义上它是「用看起来很专业的绕过，来兑现一条亲手定下的硬约束」 |
| 裁决 | **两层到底**：36 元/月 → 同页展开员工维度 → 终点。token 仅侧边栏 `/settings/usage` |
| 教训 | **主动寻路与被动推送是两件事**——前者是用户的选择，后者是产品替他做决定 |

### 4.4 信任指标绝对承诺「每次你都做了决定」——依赖用户行为的声明

| 项 | 内容 |
|---|---|
| 原始文案 | 「本月你的员工停下来问过你 27 次，**每次你都做了决定**。它们没有一次是猜的。」 |
| **否决理由** | 「每一次」是绝对承诺，**只要任意一次未处理，整句就是假的**。而产品无法保证用户处理每一次 |
| **裁决** | 有未处理项时**必须删除**「每次你都做了决定」，**保留**「它们没有一次是猜的」 |
| **核心判据** | **只声明系统能保证的事，不声明依赖用户行为的事**（前者描述系统行为，后者描述用户行为） |
| 教训 | 信任指标造假**杀伤力远大于不做**，而修复成本只是改一句话——**成本极低、风险极高** |

### 4.5 周报复用日报四板块 —— 会退化成七份日报堆叠

| 项 | 内容 |
|---|---|
| 原始想法 | 日报周报结构一致，降低实现与认知成本 |
| **否决理由** | 日报四板块是**日粒度即时性沟通**（要你管 = 今天要处理）。按日组织周报会变成七份日报的堆叠——**那不是回顾，那是存档** |
| 裁决 | 周报按「产出总览 + 趋势」组织，**按岗位而非时间罗列** |
| 附带发现 | 日清模式会**系统性掩盖慢性问题**（每天处理 1 件 / 每周新增 8 件，日报每天显示「1 件」看起来可控，周报显示「5 件积压」才是真实信号）——**这是日报本身的能力边界，不是周报的加分项** |

### 4.6 「Lucide 为主 + Tabler 补缺」双库方案 —— 维护成本复利

| 项 | 内容 |
|---|---|
| 提出方 | **我（设计师）** |
| **否决理由**（架构师提出，我接受） | 两套包 = 两套版本升级节奏 + 两套 tree-shaking + 两套 node_modules；**新人加了 Tabler 的 import 无人拦截** |
| 我的复盘 | 我只想到了视觉一致性，**没算维护成本的复利**。双库共存在第一天看起来是「更灵活」，但它是一笔按月复利的负债 |
| 裁决 | **缺口 > 20 个就整体换 Tabler，不接受双库并存** |
| 规则成立的关键前提 | 两库同为 2px 描边 / 24 网格，**整体切换的视觉成本近乎为零**——所以「切库」代价远低于「共存」代价，**这个不对称性让规则站得住** |

## 5. 复现方式

| 数据 | 复现命令 |
|---|---|
| WCAG 对比度 | WCAG 2.1 相对亮度公式，输入为 sRGB hex。**关键：必须在 bg / s1 / s2 三种表面上各算一次** |
| 色觉模拟 | Brettel/Viénot 标准线性矩阵，对每色做 RGB→线性→矩阵→sRGB，再算对比度 |
| 色相间隔 | HSL 转换取 hue，按 360°环形算相邻最小间隔 |
| 图标可导入性 | `npm pack lucide-react@<version>` → `tar -xzf` → `grep "declare const" dist/lucide-react.d.ts` |

**架构侧已固化**：`scripts/verify-icons.sh` 作为发布阻断门禁（图标必须先进 map 文件，验证通过才允许写 import；升级 lucide 必须重跑）。
